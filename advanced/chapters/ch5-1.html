기준 스택: ARM Trusted Firmware-A (TF-A) + U-Boot + Linux. AArch64 예외 레벨 정의는 ARM ARM (DDI 0487, Armv8-A Architecture Reference Manual). 면접에서 "부팅 좀 안다"와 "bring-up 해봤다"를 가르는 건 이 단계 이름·EL·레지스터입니다.

부팅은 가장 높은 EL3에서 시작해 점점 낮은 EL로 내려가며 권한을 떨군다. 전환은 ELR_ELx(복귀주소)·SPSR_ELx(저장된 상태)를 세팅하고 ERET 명령으로 수행.

  • SCR_EL3.NS 비트로 Secure ↔ Non-secure 세계 구분
  • BL31이 SPSR에 목표 EL(보통 EL2)을 적고 ERET → BL33로 점프

흔한 혼동: "리눅스가 EL3에서 돈다" ❌ — 리눅스 커널은 EL1(하이퍼바이저 있으면 EL2)에서 돕니다. EL3는 secure monitor(BL31) 전용. 숫자가 클수록 권한이 높다는 점도 직관과 반대라 헷갈리기 쉽습니다.

reset vector

RVBAR — CPU가 깨어나 첫 명령을 가져오는 곳

코어가 reset에서 풀리면 PC를 RVBAR_ELx(Reset Vector Base Address Register) 값으로 세팅하고 그 주소에서 첫 명령을 fetch한다. 구현된 최고 EL에 맞춰 RVBAR_EL3/RVBAR_EL2/RVBAR_EL1이 존재. AArch64에서 이 주소는 보통 on-chip BootROM(BL1)을 가리킨다.

// Armv8-A: reset 직후 코어가 하는 일(개념)
if (cold_reset) {
    PC      = RVBAR_EL3;   // 최고 EL의 reset vector
    SCR_EL3 = reset_default;  // NS=0 → Secure 세계
    SP, MMU = off;            // MMU off, 캐시 무효
}                             // → BL1(BootROM) 첫 명령 실행
RVBAR는 read-only(또는 pin/eFuse strap으로 고정). 멀티코어는 보통 primary 코어만 부팅하고 나머지는 WFI/WFE로 park.

x86 비교: x86은 reset 시 0xFFFFFFF0(reset vector)에서 시작하고 16바이트 뒤에 BIOS로 점프. ARM은 그게 RVBAR_ELx 레지스터 값으로 유연하게 지정된다는 점이 다릅니다. 개발자 직관: "엔트리포인트 주소를 하드코딩한 레지스터"입니다.

하드웨어 bring-up

클럭/PLL lock → DDR 트레이닝 순서

BootROM/BL2가 코드를 돌리기 전, 물리 블록을 살려야 한다. 순서가 틀리면 그냥 멈춘다.

2레퍼런스 클럭 → PLL lockPLL 설정 후 lock 비트가 1 될 때까지 폴링. lock 전 클럭 전환 금지

DDR PHY 트레이닝이 면접 핵심: 고속 DDR(예: DDR4/LPDDR4)은 보드마다 트레이스 길이가 달라 데이터-스트로브(DQ-DQS) 타이밍이 미세하게 다르다. 그래서 부팅 시 PHY가 패턴을 써보고 읽어 최적 지연(딜레이 라인)을 자동 탐색한다. 이 결과는 보드·온도에 따라 매번 조금씩 달라질 수 있다.

불변 설정

eFuse / OTP — 한 번 굽고 못 바꾼다

eFuse / OTP(One-Time Programmable)는 칩에 물리적으로 한 번만 굽는 비트들. 보안 부팅의 신뢰 뿌리가 여기 박힌다.

  • RoT 공개키 해시(또는 키) — 서명검증의 앵커
  • Secure boot enable 비트 — 한 번 켜면 영구
  • anti-rollback 카운터(monotonic) — 구버전 거부
  • JTAG disable, 칩 고유 ID/키, 부트 소스 strap

되돌릴 수 없다. secure-boot enable fuse나 잘못된 키 해시를 굽으면 그 칩은 영구히 그 상태. 양산 라인에서 fuse 프로그래밍 버그는 곧 칩 폐기다. 그래서 검증에서 fuse 모델을 정확히 만들어 "굽기 전/후" 부팅 경로를 모두 시뮬한다.

OTP 특성: 비트는 0→1(또는 1→0) 한 방향만 변경 가능. 그래서 anti-rollback은 "이미 구운 비트 수 = 최소 허용 버전" 식의 monotonic 카운터로 구현한다.

Root of Trust

Secure Boot 체인 — 단계마다 다음을 서명검증

전형 알고리즘: 이미지 해시 SHA-256/384 → RSA-2048/4096 또는 ECDSA(P-256/P-384) 서명. TF-A는 인증 체인을 X.509 인증서(CoT, Chain of Trust)로 표현하고 BL2가 이를 파싱·검증한다.

서명검증 + anti-rollback

"왜 안 부팅되나"의 두 갈래

// BL1/BL2의 이미지 인증(의사코드)
load(img, sig, cert);
h = sha256(img);
if (!rsa_verify(h, sig, pubkey_from_RoT))
    panic("BAD_SIGNATURE"); // 위변조/엉뚱한 키

ver = cert.version;
if (ver < otp_min_version())
    panic("ROLLBACK");     // 구버전 거부

jump(img.entry);          // 통과해야 다음 단계
서명검증 = "이 이미지를 우리가 만들었나". anti-rollback = "취약했던 구버전으로 되돌리지 못하게".

개발자 비유: 서명검증은 패키지의 GPG/코드서명 확인, anti-rollback은 npm install pkg@<취약버전>을 막는 minimum-version 락. 차이는 키 앵커가 소프트웨어가 아니라 칩 안 fuse라 공격자가 못 바꾼다는 점.

함정: 서명검증만 있고 anti-rollback이 없으면, 공격자가 정상 서명된 옛 취약 펌웨어를 다시 올려 우회한다. 그래서 monotonic 카운터(OTP)가 필수.

전원 상태

Warm vs Cold boot — 무엇을 다시 하나

Cold bootWarm boot
트리거전원 인가 / POR(Power-On Reset)리셋·웨이크업(전원 유지)
시작점RVBAR → BL1 처음부터플랫폼이 정한 warm reset entrypoint
DDRinit + full PHY 트레이닝self-refresh 유지 → 트레이닝 생략/단축 가능
속도느림(전체 bring-up)빠름(상태 보존)
용도최초 부팅, 전원 차단 후suspend/resume, CPU 핫플러그, PSCI

ARM에서 전원/리셋은 PSCI(Power State Coordination Interface)로 표준화 — CPU_ON, CPU_OFF, SYSTEM_SUSPEND 등을 SMC로 호출하면 EL3의 BL31이 처리. warm boot 진입점도 BL31이 관리.

warm boot에서 DDR을 self-refresh로 보존했다 가정했는데 실제 전원이 빠지면 메모리 깨짐. 전원 시퀀싱(레일 on/off 순서·타이밍) 검증이 중요한 이유.

디버그 진입

JTAG halt — 부팅을 멈춰 세워 들여다본다

bring-up에서 코어가 어디서 죽었는지 보려면 JTAG/디버거로 코어를 halt시키고 PC·레지스터·메모리를 읽는다.

  • halt-on-reset: reset 직후(첫 명령 전) 멈춰 BootROM부터 step
  • CoreSight DAP를 통해 메모리/레지스터 access
  • DDR·클럭이 죽었으면 그 전에 멈춰야 원인 파악 가능

보안의 벽: 양산 secure 칩은 eFuse로 JTAG가 잠겨 있어 임의 halt가 안 된다(키 인증된 디버그만 허용). 그래서 secure-boot 칩의 bring-up 디버깅이 어렵고, 사전 실리콘 단계(시뮬/에뮬)에서 부팅을 최대한 검증해 둬야 한다.

JTAG halt는 실리콘에서의 무기이고, RTL 단계에선 시뮬레이터의 $stop·force·waveform이 같은 역할을 합니다.
검증 엔지니어의 시선

부팅을 어떻게 검증하나 (pre-silicon)

🧩 무엇으로

  • RTL 시뮬에 BootROM 모델(실제 BL1 코드 또는 C/behavioral 모델)을 ROM에 백도어 로드
  • 에뮬레이션(Palladium/Veloce/Protium)로 수백만 사이클의 full 부팅을 실속도 근처로
  • C-test bring-up: 코어에서 도는 작은 C 프로그램으로 PLL/DDR/주변장치를 단계별로 초기화·확인
  • fuse/OTP 모델: 굽기 전/후, secure-on/off 경로를 모두 자극

🎯 무엇을 (커버리지/체크)

  • cold/warm 양쪽 reset 경로, RVBAR 점프 정확성
  • PLL lock 폴링·타임아웃, 클럭 게이팅 시퀀스
  • secure boot: 정상서명/위변조/rollback 3케이스 모두 → 통과·panic 확인
  • SVA assertion: reset 중 버스 quiescent, EL 전이 순서, 전원 레일 순서
  • 전원 시퀀싱 코너(레일 글리치, 늦은 PLL)

DDR 트레이닝 비결정성: 실제 PHY 트레이닝은 아날로그 지연 캘리브레이션이라 RTL 시뮬에서 그대로 돌리면 수억 사이클·비결정적이라 매우 느리다. 그래서 보통 트레이닝을 skip/단축하는 fast-model 모드나 결정적 시드를 써서 부팅을 통과시키고, 실제 트레이닝 알고리즘은 별도 PHY 검증환경에서 본다. "부팅 sim이 DDR 트레이닝에서 멈췄다"는 단골 이슈.

면접 심화 질문

여기까지 답하면 "bring-up 해봤다"로 보인다

TF-A의 BL 단계와 각 EL을 말해보세요.
BL1은 AP Trusted ROM(BootROM)으로 EL3에서 시작해 RoT 앵커가 됩니다. BL2는 Trusted Boot Firmware로 나머지 이미지를 로드·검증하고 DDR을 올립니다. BL31은 EL3 런타임 secure monitor로 부팅 후에도 DRAM에 상주하며 SMC·PSCI를 처리합니다. BL32는 선택적 S-EL1 TEE(OP-TEE 등), BL33은 non-secure 펌웨어(U-Boot/UEFI)로 EL2/EL1에서 커널을 부팅합니다.
RVBAR가 뭐고 reset 시 어떻게 쓰이나요?
RVBAR_ELx(Reset Vector Base Address Register)는 코어가 reset에서 풀린 직후 PC를 세팅할 주소를 담은 레지스터입니다. 구현된 최고 EL에 맞춰 RVBAR_EL3 등이 있고, 보통 on-chip BootROM(BL1)을 가리켜 거기서 첫 명령을 fetch합니다. read-only이며 strap/eFuse로 고정됩니다.
secure boot 체인과 anti-rollback을 설명해 주세요.
불변 앵커(BootROM + eFuse의 RoT 키해시)에서 시작해, 각 단계가 다음 이미지의 서명을 SHA-256+RSA/ECDSA로 검증한 뒤에만 점프하는 chain of trust입니다. 통과 못 하면 부팅을 중단합니다. anti-rollback은 OTP의 monotonic 카운터로 정상 서명된 구버전(취약 펌웨어)을 거부하는 메커니즘입니다.
warm boot와 cold boot의 핵심 차이는?
cold는 전원 인가/POR로 RVBAR→BL1부터 전체 bring-up과 full DDR PHY 트레이닝을 합니다. warm은 전원이 유지된 채 리셋·resume으로, DDR을 self-refresh로 보존했다면 트레이닝을 생략/단축하고 플랫폼이 정한 warm reset entrypoint로 빠르게 복귀합니다. PSCI/BL31이 이를 관리합니다.
핵심 요약

SoC 부팅 정밀 — 한 손에

  • 체인: reset→BL1(EL3,ROM)→BL2→BL31(EL3 monitor,상주)→BL33(U-Boot)→kernel(EL1)
  • EL은 EL3→EL2→EL1로 권한이 내려감, 전환은 ERET
  • RVBAR_ELx = reset vector, 보통 BootROM
  • bring-up: 전원→PLL lock 폴링→클럭→DDR init→PHY 트레이닝
  • RoT = BootROM+eFuse 앵커, 단계마다 서명검증 + anti-rollback(OTP)
  • warm은 DDR self-refresh로 트레이닝 단축, PSCI/BL31이 관리

"부팅은 EL3 불변 앵커(BootROM+fuse)에서 시작해 단계마다 다음을 서명검증하며 권한을 낮춰 커널까지 내려가는 chain of trust입니다. 검증은 BootROM 모델·에뮬 full 부팅·C-test·전원/클럭 assertion으로 하고, DDR 트레이닝 비결정성은 fast-model로 우회합니다."
