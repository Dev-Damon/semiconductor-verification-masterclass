Cache Coherency, 상태 전이까지

개념판에서 "여러 코어가 같은 메모리를 캐싱하면 일관성이 깨진다"를 잡았다면, 이제 면접관이 파고드는 곳 — MESI 전체 전이표, MOESI/MESIF 차이, snoop vs directory, ACE·CHI 채널과 트랜잭션 인코딩까지 정확히 내려갑니다.

"코히런시 안다"에서 "전이로 설명한다"로

✅ 개념판에서 한 것

  • 캐시 일관성 문제의 직관(stale copy)
  • MESI 네 글자가 있다는 것
  • 스누핑으로 서로 엿본다는 그림

🎯 심화판에서 더할 것

  • MESI 전체 상태 전이표(local/remote 이벤트)
  • MOESI(O)·MESIF(F)가 푸는 비효율
  • snoop vs directory 확장성 트레이드오프
  • AMBA ACE 스누프 3채널, CHI flit·트랜잭션

기준 스펙: AMBA ACE / ACE-Lite (ARM IHI 0022, AXI 확장)과 AMBA 5 CHI (ARM IHI 0050). 코히런시 단위는 캐시 라인(coherency granule) — 보통 64바이트(ARM/x86 공통). 면접에서 "MESI 외워봤다"와 "전이를 그릴 수 있다"를 가르는 디테일들입니다.

네 글자의 정확한 정의

MESI — 각 상태의 불변식(invariant)

상태유효?이 캐시만 가짐?메모리와 일치?쓰기 가능?
M (Modified)예예(유일)아니오(dirty)예(즉시)
E (Exclusive)예예(유일)예(clean)예(M으로 silent 전이)
S (Shared)예아니오(공유)예(clean)아니오(먼저 무효화 필요)
I (Invalid)아니오———

핵심 불변식: 한 라인은 어디서든 M/E 둘 중 최대 하나. M·E는 "나만 갖는다", S는 "여럿이 clean 공유", I는 "없음". E→M은 버스 트래픽 없이 silent하게 일어납니다(나만 가졌으니). 쉽게 보면 도서관 책에 비유할 수 있습니다 — M=내가 빌려가 연필로 수정 중인 책(원본과 다름), E=나만 빌렸지만 아직 그대로인 책, S=여러 명이 같은 내용을 복사해 읽는 중, I=내 손엔 없는 상태입니다.

전이표 ① — 로컬 이벤트

내 코어가 읽기/쓰기 할 때

현재Local ReadLocal Write
MM (hit)M (hit)
EE (hit)M (silent, 버스 X)
SS (hit)M · Invalidate(BusUpgr) 방송 후
I (miss)다른 캐시 있으면 S, 없으면 EM · RFO(Read-For-Ownership)로 채움

한 전이를 정확히: 라인이 S 상태인데 내 코어가 쓰면 → 버스에 Invalidate(BusUpgr / ACE의 CleanUnique)를 방송해 다른 모든 사본을 I로 내리고, 내 라인을 S → M으로 올립니다. 데이터를 다시 읽을 필요는 없습니다(이미 valid). I에서 쓰면 데이터까지 받아와야 하므로 RFO(ReadUnique)로 채운 뒤 M이 됩니다.

전이표 ② — 스누프(원격) 이벤트

다른 코어가 읽기/쓰기 해서 내가 스누프당할 때

현재Snoop Read (남이 읽음)Snoop Write/Invalidate (남이 쓰려 함)
MS · 데이터 공급(write-back 또는 직접 전달)I · dirty 데이터 넘기고 무효화
ES (조용히 내려감)I
SS (변화 없음)I
II (관여 없음)I

흔한 오답: "남이 읽으면 내 M이 그대로 M으로 남는다" ❌. 남이 읽는 순간 사본이 둘이 되므로 M→S로 내려가고, dirty였으니 최신 데이터를 공급해야 합니다(미공급 시 stale read 버그).

M에서 스누프 읽기를 받으면 보통 memory update(write-back)까지 같이 합니다. 이 비효율을 없애려고 나온 게 다음 장의 MOESI의 O 상태입니다.

MESI를 넘어서

MOESI의 O · MESIF의 F — 무엇을 푸나

MOESI — Owned

O = dirty인데 공유도 가능. M에서 남이 읽어도 메모리에 안 쓰고 O로 남아, 이후 스누프 요청에 O 보유자가 직접 데이터를 공급합니다.

  • 메모리 write-back을 미룸 → 버스 트래픽↓
  • "이 라인의 최신본 공급 책임자"가 명확
  • AMD(Opteron), ARM 일부, PowerPC가 채택

MESIF — Forward

F = clean 공유본 중 단 하나만 F. 새 읽기 요청에 F 보유자만 응답(나머지 S는 침묵).

  • S가 여럿일 때 중복 응답·메모리 접근을 막음
  • 캐시-투-캐시 전달 책임자를 1명으로 지정
  • Intel QPI/UPI가 채택

O vs F 핵심 구분: O는 dirty 데이터의 공급자(메모리는 stale), F는 clean 데이터의 공급자(메모리도 최신). 둘 다 "여러 공유본 중 누가 데이터를 줄지" 책임을 한 명에게 지정하는 게 목적입니다.

확장성의 갈림길

Snoop vs Directory — 코어 수가 늘면

📡 Snoop (방송)

  • 요청을 모든 캐시에 broadcast, 각자 답
  • 지연 짧음(directory 조회 없음)
  • 트래픽이 코어 수에 ~O(N)로 증가 → 버스/링 포화
  • 소수 코어·SMP에 적합

🗂️ Directory (조회)

  • 각 라인의 공유자 목록(sharer bits)을 디렉터리가 관리
  • 관련 캐시에만 point-to-point 메시지
  • 트래픽↓ → 수십~수백 코어로 확장
  • 디렉터리 저장 오버헤드·조회 1홉 추가

면접 함정: "스누핑이 항상 빠르고 좋다" ❌. 스누프는 모든 코어에 방송하므로 코어가 많아지면 대역폭이 폭증해 확장이 안 됩니다. 그래서 메니코어/서버는 directory(또는 snoop filter)로 갑니다. CHI는 HN(Home Node)에 snoop filter/directory를 두어 필요한 노드만 스누프합니다.

AMBA ACE

ACE = AXI 5채널 + 스누프 3채널

ACE(AXI Coherency Extensions)는 기존 AXI 5채널(AR/R/AW/W/B)은 그대로 두고, 외부에서 이 마스터의 캐시를 들여다보기 위한 스누프 3채널을 추가합니다.

채널이름방향역할
ACSnoop AddressInterconnect→Master스누프 요청·주소(ACSNOOP으로 종류 지정)
CRSnoop ResponseMaster→Interconnect스누프 응답(데이터 있음/dirty/통과 등)
CDSnoop DataMaster→Interconnect스누프로 넘겨주는 캐시 라인 데이터

ACE 트랜잭션 예: ReadShared(S로 받기), ReadUnique(쓰기 위해 배타로), CleanUnique(공유→배타 승격, S→M의 무효화), MakeUnique(데이터 없이 소유권만). ACE-Lite는 캐시 없는 IO 마스터용 — 스누프당하지 않으므로 스누프 데이터 채널 CD는 없습니다(one-way/IO 코히런시). 다만 DVM(TLB/MMU 유지보수) 메시지를 받는 IO 코히런트 마스터는 AC/CR 채널을 DVM 전용으로 가질 수 있습니다.

면접 함정: "ACE는 AXI에 1채널 추가" ❌ → 3채널(AC/CR/CD). AXI4 5채널과 합쳐 총 8채널이고, full ACE는 캐시 마스터, ACE-Lite는 IO 코히런시용으로 구분합니다.

스누프 트랜잭션 흐름

ReadUnique 한 번 — 누가 무엇을 보내나

CPU0가 쓰기 위해 ReadUnique → interconnect가 CPU1에 AC로 스누프 → CPU1이 CR(응답)+CD(dirty 데이터)를 넘기고 자신은 M→I → 최종적으로 CPU0이 R로 데이터를 받아 I→M. 메모리는 이후 정리되거나 O 상태 모델이면 미뤄집니다.
AMBA 5 CHI

CHI — 채널이 아니라 flit·메시지 기반

CHI(Coherent Hub Interface)는 ACE의 와이어 핸드셰이크를 넘어, 패킷화된 flit을 4종류 채널로 보내는 메시지 프로토콜입니다. 메니코어 메시(mesh) NoC를 위해 설계됐습니다.

채널이름나르는 것
REQRequest읽기/쓰기/무효화 요청(ReadShared, ReadUnique …)
RSPResponse완료/승인 응답(데이터 없는 ack류)
SNPSnoopHome Node가 캐시에 보내는 스누프
DATData데이터 flit(캐시 라인 페이로드)

노드 역할: RN(Request Node, 코어/캐시), HN(Home Node, 코히런시 지점·디렉터리), SN(Slave Node, 메모리). HN-F(Fully coherent)가 directory/snoop filter를 들고 필요한 RN에만 SNP를 쏩니다 → 확장성의 핵심.

주요 요청: ReadShared(S/E 목표), ReadUnique(배타·쓰기용), MakeUnique(전체 라인 덮어쓸 때 데이터 안 받고 소유권만), ReadNoSnoop(non-coherent). CHI는 ACE의 ReadShared/ReadUnique 의미를 flit 트랜잭션으로 계승합니다.

캐시 정책과 함정

write-back/through · inclusive/exclusive · false sharing

축한쪽다른 쪽
쓰기 정책Write-back: dirty 보관, 교체 시 메모리에. 트래픽↓(M 상태가 이것)Write-through: 매 쓰기 즉시 하위로. 단순·트래픽↑
레벨 포함Inclusive: L2가 L1 내용 포함(스누프 필터링 쉬움)Exclusive: 중복 없이 용량↑(전이 복잡)

False sharing(거짓 공유): 두 코어가 서로 다른 데이터를 쓰는데 그 둘이 같은 64B 캐시 라인에 들어 있으면, 코히런시는 라인 단위로만 동작하므로 매 쓰기마다 서로 라인을 S/M↔I로 핑퐁시켜 성능이 급락합니다. 해법: 자주 쓰는 데이터를 한 라인에 하나씩 떨어지도록 간격을 띄워(패딩) 배치하는 것입니다. 여러 코어가 같은 메모리 영역을 동시에 다룰 때 가장 흔히 나오는 성능 함정입니다.

그림으로 보는 false sharing

같은 라인 vs 띄워 놓기 — 무엇이 다른가

// ❌ 데이터 A와 B가 같은 64B 캐시 라인 안에 나란히 들어 있음
캐시 라인 #1 (64B): [ A | B | ............비어있음............ ]
// CPU0은 A만, CPU1은 B만 반복해서 고치는데도
// 둘이 한 라인을 공유하므로 라인이 M↔I로 계속 핑퐁(불필요한 무효화 폭증)

// ✅ A와 B를 충분히 띄워 서로 다른 64B 라인에 배치(사이를 빈칸으로 채움=패딩)
캐시 라인 #1 (64B): [ A | ......빈칸(패딩)...... ]
캐시 라인 #2 (64B): [ B | ......빈칸(패딩)...... ]
// A와 B가 서로 다른 라인 → 한쪽을 고쳐도 다른 쪽은 영향 없음
자주 쓰는 데이터 사이에 빈칸(패딩)을 넣어 라인 단위로 떼어 놓으면 불필요한 코히런시 트래픽이 사라집니다.

정밀 포인트: 코히런시 단위는 데이터 1개가 아니라 캐시 라인(보통 64B)입니다. A를 S→M으로 올리려면 라인 전체를 무효화하므로, 같은 라인의 B까지 다른 코어에서 I가 됩니다. 두 데이터가 서로 아무 관련이 없어도 충돌하는 것이 "거짓" 공유라 불리는 이유입니다.

검증 엔지니어의 시선

코히런시를 어떻게 검증하나

🧩 무엇으로

  • ACE/CHI VIP — 캐시 마스터·interconnect BFM, 트랜잭션 자극·스누프 응답
  • UVM에 레퍼런스 캐시 모델(scoreboard)로 MESI 상태 추적
  • 프로토콜 assertion(SVA): 불법 전이·미응답 스누프·dirty 미공급 즉시 검출

🎯 무엇을(커버리지 코너)

  • MESI 전이 곱(cross) 커버리지: 현재상태 × 이벤트(local R/W, snoop R/W) 전 칸
  • 두 코어가 같은 라인 동시 RFO(경쟁)·invalidate race
  • false sharing 패턴, 인접 라인 경계
  • 모든 스누프 타입(ReadShared/Unique, CleanUnique, MakeUnique)

핵심 불변식 체크: "어떤 라인도 두 캐시에서 동시에 M/E일 수 없다", "스누프 읽기에 M 보유자는 최신 데이터를 반드시 공급". 이 둘을 전역 assertion으로 박아두고 회귀를 돌립니다. 기능은 도는데 코히런시를 어긴 경우가 가장 잡기 어렵습니다.

면접 심화 질문

여기까지 답하면 "실무자"로 보인다

MESI 전이 예를 하나 정확히 들어보세요.
라인이 한 캐시에서 M인데 다른 코어가 그 주소를 읽으면(snoop read), 보유 캐시는 M→S로 내려가면서 dirty 최신 데이터를 공급합니다. 만약 다른 코어가 쓰려고 ReadUnique/Invalidate를 보내면 M→I로 무효화하고 데이터를 넘깁니다. 반대로 내 라인이 S인데 내가 쓰면 Invalidate를 방송해 다른 사본을 I로 내리고 S→M이 됩니다.
ACE가 AXI에 더한 채널과, CHI는 무엇이 다른가요?
ACE는 AXI 5채널은 그대로 두고 스누프용 3채널 AC(스누프 주소)·CR(스누프 응답)·CD(스누프 데이터)를 추가합니다(총 8채널). CHI는 와이어 채널 방식이 아니라 flit 기반 메시지로, REQ·RSP·SNP·DAT 4종 채널과 RN/HN/SN 노드 구조를 써서 메시 NoC와 메니코어로 확장합니다.
snoop과 directory의 트레이드오프, 그리고 MOESI의 O는?
snoop은 모든 캐시에 방송이라 지연은 짧지만 트래픽이 코어 수에 비례해 확장이 안 됩니다. directory는 라인별 공유자 목록으로 필요한 노드에만 보내 수십~수백 코어로 확장되지만 저장·조회 오버헤드가 있습니다. MOESI의 O(Owned)는 dirty이면서 공유 가능한 상태로, M에서 남이 읽어도 메모리에 write-back하지 않고 O로 남아 이후 스누프에 직접 데이터를 공급해 메모리 트래픽을 줄입니다.
핵심 요약

Cache Coherency 정밀 — 한 손에

  • 불변식: 한 라인은 어디서든 M/E 최대 1개, S는 clean 공유
  • 전이 핵: snoop read에 M→S(+공급), snoop write에 M→I, local write에 S→M(+invalidate)
  • O=dirty 공유 공급자, F=clean 공유 응답자
  • snoop=방송(소수 코어), directory=조회(메니코어 확장)
  • ACE=AXI+AC/CR/CD, CHI=flit REQ/RSP/SNP/DAT
  • 코히런시 단위=64B 라인 → false sharing 주의

"코히런시는 라인 단위 상태기계입니다. MESI 전이로 정확성을, snoop→directory와 ACE→CHI로 확장성을 얻고, 검증은 전이 cross 커버리지와 불변식 assertion으로 합니다."
