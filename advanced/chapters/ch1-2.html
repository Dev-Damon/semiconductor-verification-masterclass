자료형 ① — 상태

logic(4-state) vs bit(2-state)

타입값비트당 인코딩리셋 초기값용도
logic / reg0 1 X Z (4-state)2비트(val+control)XRTL, DUT 연결, 미초기화/충돌 탐지
bit / int0 1 (2-state)1비트0TB 산술·카운터·스코어보드

logic은 단일 드라이버용 data type이고, 다중 드라이버(버스)면 wire(net) + resolution이 필요합니다. reg는 SV에서 logic과 사실상 동의어(오해 유발 이름이라 SV는 logic 권장).

흔한 오답: "bit는 1비트, logic은 여러 비트" ❌. 둘 다 폭은 [31:0]처럼 선언으로 정함. 차이는 비트당 표현할 수 있는 값(2 vs 4-state)입니다.

자료형 ② — 컨테이너

packed/unpacked · queue · assoc · struct

// packed: 연속 비트(벡터). 산술/슬라이스 가능, 합성 가능
logic [31:0] word;          // 32비트 하나의 묶음
logic [3:0][7:0] bytes;     // packed 2D = 여전히 32비트

// unpacked: 별개 원소 배열(메모리/컬렉션). 합성 제한적
int mem [256];                // 고정 크기 unpacked
int dyn [];                  // dynamic: dyn = new[N];
int q  [$];                  // queue: q.push_back(x); q.pop_front();
int ap [string];            // associative: ap["key"], 희소 메모리

// 합성 구조체 / enum / union
typedef struct packed { logic [7:0] id; logic [31:0] addr; } hdr_t;
typedef enum logic [1:0] { IDLE=0, REQ=1, RESP=2 } state_e;
packed = 비트들이 메모리상 연속 → 통째로 캐스팅·연산. unpacked = 원소 단위 → 동적/연관 배열의 베이스.

struct packed만 벡터처럼 한 번에 대입/슬라이스됩니다. packed 멤버는 모두 integral이어야 하며(실수·동적배열 불가), 멤버 선언 순서가 MSB→LSB로 매핑됩니다.

랜덤화 ① — 클래스+제약

rand / randc / constraint 실코드

class AxiTxn;
  rand  bit [31:0] addr;
  rand  bit [7:0]  len;       // beats-1 (0..255)
  rand  bit [2:0]  size;      // 2^size 바이트
  randc bit [1:0]  burst;     // 매 사이클 전 조합 소진 후 반복

  constraint c_size { size inside {[0:3]}; }            // 1,2,4,8 B
  constraint c_dist { len dist { 0:=50, [1:15]:/30, [16:255]:/20 }; }
  // implication: WRAP이면 len은 1,3,7,15 (2/4/8/16 beats)
  constraint c_wrap { burst==2'b10 -> len inside {1,3,7,15}; }
  // 정렬: addr는 size 경계에 정렬
  constraint c_align { addr % (1 << size) == 0; }
  constraint c_order { solve size before addr; }     // size 먼저 → addr 분포 균형
  constraint c_soft { soft len == 7; }              // 충돌 시 양보
endclass

// 사용
AxiTxn t = new();
if (!t.randomize() with { addr inside {[32'h1000:32'h1FFF]}; })
  `uvm_error("RND", "randomize failed")
:= = 절대 가중치, :/ = 범위 전체에 가중치를 균등 분할. -> = implication(왼쪽 참이면 오른쪽 강제). with{} = 인라인 제약.
랜덤화 ② — 정확한 의미

implication · solve before · randc

-> implication

A -> B는 "A이면 B"일 뿐 양방향이 아님. A가 거짓이면 B는 자유. if(A) B; else C; 형태도 가능.

solve … before …

두 변수의 해 분포를 바꿀 뿐, 해집합 자체는 안 바꿈. 순서를 주면 첫 변수를 먼저 균등 선택 후 둘째를 만족시킴.

randc 주기성

선언 폭의 모든 값을 한 번씩 소진한 뒤에야 같은 값 반복(랜덤 순열). N비트면 주기 = 2^N.

키워드의미
inside집합/범위 멤버십
dist가중 분포(:=, :/)
soft충돌 시 자동 양보

solve-before 오용: 결과를 "강제"한다고 착각 — 실제론 분포만 조정합니다. 또 randc 남용은 위험: 32비트에 randc를 쓰면 솔버가 2^32 순열 상태를 관리하려다 폭증/성능 저하. randc는 좁은 필드(상태·opcode)에만.

커버리지

covergroup · bins · cross

covergroup cg_axi with function sample(AxiTxn t);
  cp_size : coverpoint t.size {
    bins small[] = {[0:2]};       // 1,2,4B 각각 별도 bin
    bins wide      = {3};           // 8B
    illegal_bins bad = {[4:7]};   // 발생 시 즉시 에러
  }
  cp_burst: coverpoint t.burst {
    bins fixed={0}; bins incr={1}; bins wrap={2};
    ignore_bins rsvd = {3};      // 커버리지 계산서 제외
  }
  cp_len  : coverpoint t.len {
    bins lo={[0:15]}; bins hi={[16:255]};
  }
  x_bs : cross cp_burst, cp_size;     // 조합 커버리지(곱집합)
endgroup

cg_axi cg = new();
... cg.sample(t);   // 트랜잭션마다 호출
bins x[](array bins)=값마다 별도 bin, illegal_bins=발생 즉시 에러, ignore_bins=분모에서 제외. cross=각 coverpoint bin의 곱집합.

cross 폭증: coverpoint bin 수가 곱해집니다(예 16×8=128). 의미 없는 조합은 ignore_bins/binsof() 표현식으로 잘라내야 커버리지 닫기(closure)가 현실화됩니다.

인터페이스 ① — race 제거

clocking block — 샘플/드라이브 타이밍을 못 박다

interface axi_if(input bit clk);
  logic [31:0] addr;
  logic        valid, ready;

  // 테스트벤치 시점: skew로 샘플/드라이브를 클럭에서 떼어냄
  clocking cb @(posedge clk);
    default input #1step output #1;   // 입력은 직전 안정값, 출력은 +1 후
    input  ready;                       // DUT→TB : 샘플
    output addr, valid;                 // TB→DUT : 드라이브
  endclocking

  modport TB (clocking cb, input clk);   // 검증측
  modport DUT(input addr, valid, output ready, input clk);
endinterface

// 드라이버에서: 신호를 직접이 아니라 cb를 통해 움직인다
task drive(axi_if.TB vif);
  vif.cb.addr  <= 32'h40; // output skew(#1)만큼 늦게 드라이브
  vif.cb.valid <= 1'b1;
  @(vif.cb);                  // 다음 clocking 이벤트까지 대기
  wait(vif.cb.ready);          // #1step로 샘플된 안정값
endtask

race가 제거되는 이유: input #1step은 클럭 엣지 바로 직전(Preponed region)의 안정된 값을 샘플 → DUT가 같은 엣지에 바꾸는 값과 경합하지 않습니다. output #1은 엣지보다 늦게 드라이브 → DUT 입력 셋업과 충돌 없음. 즉 샘플=엣지 전, 드라이브=엣지 후로 분리됩니다.

인터페이스 ② — clocking 없을 때

왜 직접 신호를 건드리면 안 되나

// ❌ clocking block 없이 직접
always @(posedge clk)
  if (vif.ready)        // DUT도 같은 엣지에
    do_something();    // ready를 바꾸는 중!
// → TB가 새 값 본 건지 옛 값 본 건지
//   시뮬레이터 스케줄 순서에 의존 (race)

Verilog 이벤트 큐에서 같은 시각의 Active region 안 실행 순서는 비결정적입니다. TB의 샘플과 DUT의 갱신이 같은 엣지에 얽히면 읽는 값이 시뮬레이터/최적화에 따라 달라집니다.

  • #1step 샘플 = Preponed(엣지 직전 안정값)
  • 드라이브 = NBA/Reactive 이후 적용
  • 그래서 결과가 재현 가능(deterministic)

clocking block 없이 race: "내 시뮬에선 됐는데 회귀/다른 툴에선 깨진다"의 대표 원인. blocking =로 인터페이스 신호를 같은 엣지에 읽고 쓰면 거의 확정적으로 race. TB는 cb를 통해서만 신호를 만지는 게 표준 패턴입니다.

인터페이스 ③ — 연결 다리

virtual interface — class와 신호를 잇다

interface는 static(컴파일 시 인스턴스 고정)이고, class 기반 TB는 dynamic(new()로 런타임 생성). 클래스 안에서 정적 인터페이스를 직접 참조할 수 없으므로 핸들(포인터)이 필요합니다 — 그게 virtual interface.

// 드라이버(class)는 어떤 물리 인터페이스인지 모른 채 핸들만 보유
class AxiDriver;
  virtual axi_if.TB vif;          // 가상 인터페이스 핸들
  task run(); vif.cb.valid <= 1; @(vif.cb); endtask
endclass

// top: 실제 인터페이스 인스턴스를 핸들에 바인딩
axi_if dut_if(clk);
AxiDriver d = new();
initial d.vif = dut_if;          // 동적 class ↔ 정적 if 연결
// UVM이면: uvm_config_db#(virtual axi_if)::set/get 으로 전달

한 클래스를 여러 인터페이스 인스턴스에 재사용할 수 있고, 테스트마다 다른 DUT 포트에 같은 드라이버를 꽂을 수 있습니다(reusability).

virtual interface가 null인 채 사용 = 런타임 fatal. config_db get 실패(이름/타입 mismatch)가 단골 원인. build_phase에서 null 체크는 필수.

단언 — SVA

concurrent assertion: |-> · |=> · ##n · throughout

// 클럭마다 평가되는 concurrent assertion (RTL과 병렬)
property p_req_ack;
  @(posedge clk) disable iff (!rst_n)        // 리셋 중엔 비활성
    req |-> ##[1:3] ack;                  // req 후 1~3클럭 내 ack
endproperty
assert_req: assert property(p_req_ack)
  else `uvm_error("SVA", "ack not seen in 1..3")

// |->(overlap): 같은 클럭에서 consequent 시작
// |=>(non-overlap): 다음 클럭에서 시작  ==  |-> ##1
property p_stable;
  @(posedge clk)
    valid && !ready |=> $stable(data);   // stall 동안 data 유지
endproperty

// throughout: 시퀀스 진행 내내 조건이 참이어야
property p_burst;
  @(posedge clk)
    $rose(start) |-> (!abort) throughout (##[1:8] done);
endproperty
|->=overlap(같은 클럭), |=>=non-overlap(다음 클럭, |-> ##1과 동일), ##n=n클럭 지연, ##[a:b]=범위, throughout=구간 내내 참, $rose/$stable=엣지/유지.
단언 — 동작 모델

concurrent assertion은 어떻게 평가되나

clock 엣지마다 antecedent 매칭을 시도합니다. antecedent가 참이면 그 시점에서 스레드 하나가 출발해 consequent를 추적. 여러 시점에서 동시에 여러 스레드가 진행될 수 있습니다(파이프라인).

  • 샘플은 Preponed 값(clocking과 동일 원리 → race 없음)
  • antecedent 불일치 = vacuous 성공(실패 아님)
  • immediate assertion은 절차문처럼 그 즉시 1회 평가(조합)

X 처리: 부울 자동이 X/Z면 의도와 다른 vacuous/실패가 날 수 있어, 입력에 $isunknown() 가드를 넣기도 합니다. 또 disable iff 없이 리셋 중 단언이 깨지는 거짓양성도 단골.

동시성 · 통신

fork-join · mailbox · semaphore · DPI

// fork variants
fork a(); b(); join        // 둘 다 끝나야
fork a(); b(); join_any    // 하나라도 끝나면
fork a(); b(); join_none   // 안 기다리고 진행

// 생산자-소비자: mailbox(typed queue)
mailbox #(AxiTxn) mb = new();
mb.put(t);  mb.get(t);   // blocking

// 자원 N개 보호: semaphore
semaphore sem = new(1);
sem.get(1); ... sem.put(1);

program block은 모든 코드를 Reactive region에서 돌려 design과의 race를 줄이려 도입(UVM 시대엔 clocking block + class로 대체되는 추세).

// DPI-C: C 함수 호출
import "DPI-C" function int ref_model(
  input int a, input int b);
// SV에서 그냥 호출
exp = ref_model(x, y);

mailbox = thread-safe queue, semaphore = counting lock, DPI = SV↔C FFI. 멀티스레드 서버 코드의 채널/뮤텍스/네이티브 바인딩과 1:1 대응.

검증 엔지니어의 시선

이 기능들이 UVM 환경에서 어떻게 합쳐지나

🧩 어디에 쓰이나

  • class+rand+constraint → sequence_item / sequence
  • virtual interface → driver/monitor가 DUT 핀과 통신
  • clocking block → driver의 race-free 드라이브/샘플
  • covergroup → 기능 커버리지(coverage closure 목표)
  • SVA → 프로토콜·인터페이스 assertion(항상 ON)

🎯 무엇을 측정하나

  • code coverage(line/toggle/FSM) + functional coverage(covergroup)
  • 제약랜덤으로 자극 다양화 → 커버리지 구멍 보고 제약 보강
  • SVA로 "기능은 돌지만 프로토콜 위반"을 즉시 검출
  • 스코어보드(mailbox로 expected vs actual 비교)

면접 핵심 흐름: 제약랜덤 자극 → 커버리지 측정 → 구멍을 제약/시퀀스로 메움(closure) → assertion으로 정합성 보증. 이 루프를 자기 말로 설명할 수 있으면 합격선입니다.

면접 심화 질문

여기까지 답하면 "실무자"로 보인다

clocking block의 목적과 race를 어떻게 없애나요?
샘플과 드라이브 타이밍을 클럭 엣지에서 분리해 race를 제거합니다. input #1step은 엣지 직전(Preponed)의 안정값을 샘플하고, output #1은 엣지보다 늦게 드라이브해 DUT 갱신과 경합하지 않습니다. 그래서 결과가 재현 가능해집니다.
virtual interface는 왜 필요한가요?
interface는 컴파일 시 고정되는 static이고 class 기반 TB는 new()로 생성되는 dynamic이라, 클래스가 정적 인터페이스를 직접 못 가집니다. virtual interface는 그 인터페이스를 가리키는 핸들이라 class와 신호를 잇고, 한 드라이버를 여러 인스턴스에 재사용하게 해줍니다.
constraint의 ->와 solve before 차이, randc 주의점은?
->는 "A이면 B"의 단방향 implication으로 해집합을 좁힙니다. solve A before B는 해집합은 그대로 두고 A를 먼저 균등 선택해 분포만 바꿉니다. randc는 폭의 모든 값(2^N)을 순열로 소진하므로 좁은 필드에만 쓰고, 넓은 필드엔 솔버 폭증 때문에 피합니다.
핵심 요약

SystemVerilog 검증 기능 — 한 손에

  • logic=4-state(0/1/X/Z, 미초기화·충돌 탐지), bit=2-state(빠름, TB 산술)
  • packed=연속 비트(연산), unpacked=원소 배열(queue/assoc/dynamic)
  • rand/randc + inside/dist/->/solve before/soft로 자극 제어
  • covergroup·cross·bins로 기능 커버리지 측정
  • clocking block=race 제거, virtual interface=class↔신호
  • SVA |-> |=> ##n throughout=프로토콜 정합성

"SV의 검증 기능은 제약랜덤(class+rand)으로 자극을, covergroup으로 측정을, clocking/virtual if로 race-free 연결을, SVA로 정합성을 책임집니다. 이 넷이 UVM에서 하나의 검증 루프를 이룹니다."
