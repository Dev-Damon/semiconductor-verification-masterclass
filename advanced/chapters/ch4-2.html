VCS 실제 흐름

vlogan / vhdlan → vcs → simv

VCS는 보통 3-step으로 씁니다. SystemVerilog는 vlogan, VHDL은 vhdlan으로 analyze해 라이브러리에 적재하고, vcs로 elaborate해 실행 바이너리 simv를 만든 뒤 실행합니다.

# ① analyze: SV 소스 분석 → work 라이브러리 적재
vlogan -full64 -sverilog -ntb_opts uvm -timescale=1ns/1ps \
       -f filelist.f
# (VHDL이 섞이면)  vhdlan -full64 dut.vhd

# ② elaborate: 계층 펼쳐 simv 빌드 (디버그+KDB 켜기)
vcs -full64 -sverilog -ntb_opts uvm \
    -debug_access+all -kdb -lca \
    top_tb -o simv -l comp.log

# ③ simulate: 테스트 실행 (런타임 옵션은 여기서)
./simv +UVM_TESTNAME=axi_wr_test -l sim.log

-f filelist.f: 소스 목록 파일 · -ntb_opts uvm: UVM 라이브러리 링크 · -l: 로그 파일.

-debug_access+all은 신호 force/덤프/메모리 접근까지 전체 디버그 가시성을 엽니다. -kdb는 Verdi가 RTL을 역추적할 Knowledge DB를 elaborate 때 같이 생성 — 이게 있어야 Verdi가 소스까지 trace합니다.

FSDB 덤프 활성화

$fsdbDumpvars — 파형을 어떻게 켜나

Verdi용 FSDB 파형은 테스트벤치 안에서 시스템태스크로 켭니다. 대안으로 런타임 UCLI나 do 스크립트로도 켤 수 있습니다.

// TB 안: 계층 전체를 FSDB로 덤프
initial begin
  $fsdbDumpfile("wave.fsdb");
  // 0 = 모든 깊이, top_tb 이하 전체
  $fsdbDumpvars(0, top_tb);
  // 메모리/MDA·SV struct도 함께
  $fsdbDumpvars("+all");
  $fsdbDumpMDA();
end

$fsdbDumpvars(N, scope)의 첫 인자 N=덤프 깊이: 0=무한(하위 전체), 1=해당 스코프만, 2=한 단계 아래까지. 실무 팁: 관심 블록만 $fsdbDumpvars(0, dut.core)로 좁히면 파일이 급격히 작아집니다.

# UCLI로 런타임에 켜기 (TB 수정 없이)
./simv -ucli -do dump.do +UVM_TESTNAME=axi_wr_test
# dump.do 내용:
fsdbDumpfile wave.fsdb ; fsdbDumpvars 0 top_tb ; run

UCLI = Unified Command-Line Interface. 실행 중인 simv를 마치 동영상 재생기처럼 멈추고(stop)·이어가며(run)·특정 신호 값을 강제로 바꿔(force) 보는 대화형 명령 창입니다.

덤프의 함정

"전 신호 덤프"가 회귀를 죽인다

파형 덤프는 공짜가 아닙니다. 매 시각 변화하는 모든 신호를 디스크에 쓰므로, 범위가 넓을수록 시뮬레이션 자체가 느려지고 파일이 거대해집니다.

  • $fsdbDumpvars(0, top_tb)를 대규모 SoC 회귀에 그대로 켜면 → 수십~수백 GB FSDB + 2~10배 슬로다운
  • 그래서 회귀는 덤프 off, FAIL만 골라 덤프 켜고 재현(replay)하는 게 표준
  • 꼭 켜야 하면 관심 스코프·시간 윈도로 한정

흔한 실수 ① 수천 개 회귀 잡에 전 신호 FSDB를 켜둠 → 디스크 폭발·잡 시간 폭증.
흔한 실수 ② 회귀 동시 실행 수를 라이선스 토큰보다 크게 잡음 → 잡들이 토큰 대기에 줄 서며 throughput 붕괴. 토큰은 곧 돈이자 병목입니다.

실무 패턴: 1차 회귀는 no-dump로 빠르게 → FAIL 시드/테스트를 모아 같은 시드로 덤프 켜 재실행해 파형을 얻습니다. 시드를 고정하면 동일 파형이 재현되기 때문입니다.

UVM 런타임 제어

+UVM_TESTNAME · +UVM_VERBOSITY · 시드

UVM 환경은 한 번 컴파일해 두고, 어떤 테스트를 돌릴지·로그를 얼마나 뱉을지·랜덤 시드를 런타임 플러스아규먼트로 바꿔 수백 개 테스트를 굴립니다.

# 같은 simv로 테스트만 바꿔 실행 (재컴파일 X)
./simv +UVM_TESTNAME=axi_burst_test \
       +UVM_VERBOSITY=UVM_LOW \
       +ntb_random_seed=12345 \
       -l axi_burst_test.log

# Xcelium도 동일한 +arg를 xrun 실행단에 전달
xrun -R +UVM_TESTNAME=axi_burst_test +UVM_VERBOSITY=UVM_HIGH \
     -svseed 12345

+UVM_TESTNAME은 run_test()가 받아 그 이름의 test 클래스를 팩토리로 생성합니다(코드의 run_test("xxx") 인자보다 우선). 시드는 VCS +ntb_random_seed / Xcelium -svseed. random을 주면 시각 기반 무작위, 정수면 고정(재현용).

+UVM_VERBOSITY 단계: UVM_NONE < UVM_LOW < UVM_MEDIUM < UVM_HIGH < UVM_FULL < UVM_DEBUG. uvm_info의 verbosity가 설정값 이하면 출력. 회귀는 UVM_LOW로 로그를 줄이고, 디버그 때만 UVM_HIGH로 올립니다.

Xcelium 흐름

xrun — 한 명령으로 묶기 vs 3-step

Xcelium은 xrun 하나로 compile+elaborate+simulate를 통합합니다. 큰 프로젝트에선 분리 명령(xmvlog → xmelab → xmsim, 구 irun의 후신)도 씁니다.

# 통합: 한 방에 빌드+실행 (UVM, 접근권한, 파형)
xrun -64bit -sv -uvm \
     -access +rwc \
     -f filelist.f top_tb \
     +UVM_TESTNAME=axi_wr_test -svseed 1

# 분리 3-step (대규모 incremental 빌드에 유리)
xmvlog -sv -f filelist.f          # compile
xmelab -access +rwc top_tb       # elaborate
xmsim  top_tb +UVM_TESTNAME=axi_wr_test  # simulate

-access +rwc = read/write/connectivity 가시성(디버그용). VCS의 -debug_access+all에 대응하는 개념.

디버그 접근권한을 안 켜면(+rwc/-debug_access 누락) 파형에 신호가 안 보이거나 force가 막혀 "왜 안 덤프되지?"로 시간을 날립니다. 단, 접근권한을 풀로 켜면 시뮬레이션 성능이 떨어지므로 회귀에선 끄고 디버그 빌드에서만 켜는 게 정석.

VCD가 느린 이유: 신호 변화 하나하나를 사람이 읽는 아스키 텍스트로 풀어 쓰고 압축이 없습니다. FSDB/VPD/SHM은 바이너리+압축+인덱스라 쓰기 부담이 작고 디버거가 임의 시각으로 빠르게 점프합니다. 비유하자면 VCD는 모든 사건을 시간순으로 길게 풀어 쓴 손글씨 일지, FSDB는 색인이 달린 압축 사진첩 같아서 데이터가 커질수록 차이가 압도적으로 벌어집니다. 그래서 여러 벤더의 파형을 한 도구로 보려고 FSDB를 공통 분모로 쓰는 팀이 많습니다.

커버리지 수집·병합

커버리지 켜기 → merge → 리포트

커버리지는 컴파일/엘라보 때 계측(instrument)을 켜고, 각 시뮬레이션이 결과 DB를 남기면, 수백 개를 merge해 하나의 리포트로 만듭니다.

# VCS: 커버리지 종류 선택 (line/cond/fsm/tgl/branch + 그룹)
vcs ... -cm line+cond+fsm+tgl+branch -cm_dir cov.vdb
./simv -cm line+cond+fsm+tgl+branch +UVM_TESTNAME=t1
# 여러 테스트 결과 합치고 HTML 리포트
urg -dir test1.vdb -dir test2.vdb -report cov_report

# Xcelium: -coverage 로 켜고 imc로 merge/리포트
xrun ... -coverage all -covworkdir cov
imc -execcmd "merge cov/*/ -out merged; load -run cov_work/scope/merged/; report_metrics -out rpt -summary"

VCS 커버리지 = -cm, 리포트 도구 = urg(Unified Report Generator). Xcelium = -coverage, 도구 = imc(Integrated Metrics Center). SV의 covergroup(기능 커버리지)는 별도 옵션 없이도 수집되지만, 코드 커버리지는 위 플래그로 켜야 합니다.

서로 다른 elaborate(다른 코드 버전)에서 나온 DB를 merge하면 불일치/경고가 납니다. merge는 같은 빌드의 결과끼리만 깔끔합니다. 또 커버리지 계측을 켜면 시뮬레이션이 느려지므로 회귀 정책에 따라 on/off를 나눕니다.

성능과 회귀

save/restore · 2-state · 파티션 컴파일

💾 save / restore

긴 부팅·초기화 구간을 한 번 돌려 스냅샷으로 저장하고, 테스트마다 그 지점에서 restore해 시작. 동일 init을 매번 다시 안 돌려 회귀를 단축.

⚡ 2-state

4값(0/1/X/Z) 대신 2값(0/1)으로 굴려 속도↑·메모리↓. 단 X 전파를 못 봐 리셋버그를 놓칠 수 있어 신중히.

🧩 파티션 컴파일

설계를 단위로 나눠 바뀐 부분만 재컴파일(incremental). 큰 SoC의 빌드 턴어라운드를 크게 줄임.

회귀 자동화: vManager 같은 도구가 테스트 리스트(vsif/계획)를 받아 수천 잡을 LSF/SGE 같은 그리드에 뿌리고, PASS/FAIL과 커버리지를 모아 대시보드로 보여줍니다. nightly/weekly 회귀가 검증의 심장.

2-state로 성능을 얻으려다 리셋 전 X 상태를 0/1로 뭉개 실제 X-비결정 버그를 가립니다. 그래서 기능 회귀는 4-state, 일부 성능 회귀만 2-state로 분리 운용하는 게 안전합니다.

검증 엔지니어의 시선

이 도구 흐름을 어떻게 "검증"하나

🔁 재현성·회귀 신뢰

  • 시드 고정(+ntb_random_seed/-svseed)으로 FAIL을 동일 파형으로 재현
  • no-dump 회귀 → FAIL만 덤프 켜 replay
  • build/seed/툴버전을 로그에 박아 비트정확 재현 보장

📊 커버리지 클로저

  • covergroup·assertion 커버리지를 회귀마다 누적 merge
  • 구멍(coverage hole) → 새 시드/제약/테스트로 메움
  • SVA로 프로토콜 위반을 런타임 즉시 검출(VIP 동봉 checker 포함)

핵심: 시뮬레이터는 도구이고, 검증의 신뢰는 "재현 가능한 회귀 + 닫힌 커버리지 + 켜진 assertion"에서 나옵니다. 면접에서 "도구 써봤다"를 넘어 이 운영 체계를 말하면 실무자로 보입니다.

면접 심화 질문

여기까지 답하면 "실무자"로 보인다

VCS와 Xcelium의 컴파일·실행 흐름을 명령줄로 말해보세요.
VCS는 3-step입니다. vlogan -sverilog으로 SV를 analyze하고(VHDL은 vhdlan), vcs -debug_access+all -kdb top_tb -o simv로 elaborate해 simv를 만든 뒤 ./simv로 실행합니다. Xcelium은 xrun 단일 명령으로 compile+elab+sim을 묶거나, 대규모에선 xmvlog→xmelab→xmsim으로 분리합니다. 디버그 가시성은 VCS -debug_access+all, Xcelium -access +rwc로 켭니다.
FSDB 덤프를 어떻게 켜고, VCD는 왜 안 쓰나요? 커버리지는요?
TB에서 $fsdbDumpfile("w.fsdb")와 $fsdbDumpvars(0, top_tb)로 켭니다(N=깊이, 0=하위 전체). 또는 UCLI -ucli -do로 런타임에 켭니다. VCD는 텍스트 표준이라 크고 느려 큰 설계엔 부적합하고, FSDB는 압축 바이너리라 작고 빨라 표준입니다. 커버리지는 VCS는 -cm line+cond+fsm+tgl+branch로 켜고 urg로 merge·리포트, Xcelium은 -coverage all 후 imc로 처리합니다.
+UVM_TESTNAME은 무엇이고, KDB는 왜 필요한가요?
+UVM_TESTNAME=foo는 런타임 플러스아규먼트로, run_test()가 받아 팩토리로 foo test 클래스를 생성합니다. 한 번 컴파일한 simv로 테스트만 바꿔 수백 개를 돌릴 수 있고, 코드의 run_test("...") 인자보다 우선합니다. KDB(Knowledge DB)는 -kdb로 elaborate 때 생성하는 설계 지식 DB로, Verdi가 파형의 신호를 RTL 소스까지 역추적(trace)하는 데 필요합니다.
핵심 요약

시뮬레이터 정밀 — 한 손에

  • VCS: vlogan/vhdlan → vcs -debug_access+all -kdb → simv, 런타임은 +arg
  • Xcelium: xrun 통합 또는 xmvlog/xmelab/xmsim, 가시성 -access +rwc
  • FSDB: $fsdbDumpvars(0, scope) / UCLI / VCD는 느려 비표준
  • UVM: +UVM_TESTNAME·+UVM_VERBOSITY·시드(+ntb_random_seed/-svseed)
  • 커버리지: VCS -cm+urg / Xcelium -coverage+imc, 같은 빌드끼리 merge
  • 성능: save/restore·2-state·파티션 컴파일, 회귀는 vManager+그리드, 라이선스=병목
