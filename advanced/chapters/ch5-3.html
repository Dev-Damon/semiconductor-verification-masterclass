기준: UPF = IEEE 1801(Unified Power Format, Tcl 기반 DSL). 명령 이름은 1801 표준 그대로입니다. 면접에서 "UPF 안다"와 "UPF 짜봤다"를 가르는 건 명령 인자와 clamp/shifter 인코딩을 정확히 말하느냐입니다.

UPF의 뼈대

전력 인프라를 세우는 명령들

UPF는 RTL을 건드리지 않고 별도 파일(Tcl)로 전력 구조를 기술합니다. 도메인 → 공급 → 스위치 → 보호셀 순서로 쌓습니다.

명령무엇을 정의
create_power_domain전력 도메인(같은 공급으로 켜지고 꺼지는 RTL 묶음)
create_supply_port설계 경계의 공급 포트(외부에서 들어오는 전압)
create_supply_net도메인 내부 공급 배선(VDD/VSS 네트)
connect_supply_netnet을 port/도메인의 primary supply에 연결
create_power_switch전력 스위치(MTCMOS 헤더/풋, ack 신호 포함)
set_isolation / set_isolation_control도메인 경계 isolation 셀 + 그 제어신호·위치
set_level_shifter전압 다른 도메인 간 level shifter
set_retention / map_retention_cellretention flop 전략 + 실제 셀 매핑
add_power_state / PSTsupply/도메인 상태와 합법 조합표(power state table)

흔한 오답: "UPF는 RTL 안에 pragma로 쓴다" ❌ → UPF는 RTL과 분리된 사이드카 파일. 같은 RTL에 UPF만 바꿔 다른 전력 구조를 입힐 수 있다는 게 핵심입니다.

실제 코드 ①

도메인 · isolation · retention을 진짜로 적으면

# ===== UPF (IEEE 1801) : CPU 코어 도메인 정의 =====
create_power_domain PD_CPU -elements {u_cpu}
create_power_domain PD_TOP -include_scope          # always-on 최상위

# ----- 공급 net/port 및 연결 -----
create_supply_port VDD_SW ; create_supply_net VDD_CPU -domain PD_CPU
connect_supply_net VDD_CPU -ports VDD_SW

# ----- 전력 스위치(MTCMOS 헤더) : ack로 켜짐 확인 -----
create_power_switch sw_cpu -domain PD_CPU \
   -output_supply_port {vout VDD_CPU} -input_supply_port {vin VDD_SW} \
   -control_port {sleep pmu.cpu_sleep} -ack_port {ack pmu.cpu_ack} \
   -on_state  {ON  vin {!sleep}} -off_state {OFF {sleep}}

# ----- ISOLATION : 꺼진 도메인 출력을 0으로 clamp -----
set_isolation iso_cpu -domain PD_CPU \
   -isolation_power_net VDD_AON -isolation_ground_net VSS \
   -clamp_value 0 -applies_to outputs
set_isolation_control iso_cpu -domain PD_CPU \
   -isolation_signal pmu.iso_en -isolation_sense high -location parent

# ----- RETENTION : 상태 유지 플롭(SRPG) + save/restore -----
set_retention ret_cpu -domain PD_CPU \
   -retention_power_net VDD_AON -retention_ground_net VSS \
   -save_signal  {pmu.save  high} \
   -restore_signal {pmu.restore low}
map_retention_cell ret_cpu -domain PD_CPU -lib_cell_type RSDFF_LH
도메인 → 스위치(ack) → isolation(clamp 0) → retention(save/restore) 순. retention 전원은 always-on(VDD_AON)이어야 도메인이 꺼져도 상태가 남는다.

-clamp_value 0 = 꺼진 동안 출력을 0으로 고정. retention의 save/restore는 전원이 끊기기 직전 save, 복귀 직후 restore — 순서가 핵심이라 다음 슬라이드에서 파형으로 봅니다.

경계를 지키는 두 셀

Isolation clamp 값 · Level shifter LH/HL

Isolation clamp

clamp의미
0꺼진 동안 출력을 logic 0으로 고정
1logic 1로 고정(active-low 핸드셰이크 보호)
latch꺼지기 직전 값을 래치로 유지

목적: 도메인이 꺼지면 출력이 부정(floating/X)이 되는데, 켜진 쪽 로직이 이 X를 받으면 오염. isolation이 알려진 값으로 묶어줌.

Level shifter 방향

방향의미
LHLow→High: 낮은 V 도메인 → 높은 V 도메인
HLHigh→Low: 높은 V 도메인 → 낮은 V 도메인
both양방향 모두 삽입 허용

전압이 다른 두 도메인이 직접 연결되면 신호 레벨이 안 맞아 오동작/관통전류. shifter가 스윙을 맞춰줌.

혼동 주의: isolation과 level shifter는 목적이 다르다. isolation은 "꺼짐 vs 켜짐" 경계(전원 유무), level shifter는 "전압 차이" 경계. 한 경계가 둘 다 필요한 경우(꺼지기도 하고 전압도 다름) — ELS(Enable Level Shifter, isolation+shifter 통합셀)를 씁니다.

전력 도메인 경계 한눈에

Power domain · Isolation · Level shifter 구조

읽는 법: CPU 출력이 always-on으로 나갈 땐 ISO(clamp 0)로 꺼짐 시 X를 막고, AON→CPU로 들어가는 신호는 0.9V→0.7V level shifter(HL)로 레벨을 맞춥니다. retention FF는 백업 전원으로 도메인이 꺼져도 상태를 보존.
retention의 타이밍

Save → Power-off → Restore 파형

순서가 곧 정확성: ① SAVE(상태 래치) → ② ISO_EN(출력 clamp) → ③ 전원 OFF … 복귀 시 ④ 전원 ON → ⑤ RESTORE(상태 복원) → ⑥ ISO_EN 해제. retention은 always-on 백업 전원(VDD_AON)으로 동작하므로 메인 VDD_CPU가 0이어도 상태가 살아있습니다(SRPG=State-Retention Power Gating).

치명적 실수: save를 isolation보다 늦게 걸거나, restore를 전원이 안정되기 전에 걸면 복원값이 쓰레기가 됩니다. 또 retention 셀을 RTL/검증에서 모델링하지 않으면 시뮬은 그냥 0/X로 부팅해 버그를 못 잡습니다(아래 pitfall 슬라이드 참고).

power-aware 시뮬의 핵심

simstate — 전원이 꺼지면 로직은 어떻게 되나

power-aware 시뮬레이터는 각 supply의 상태에 따라 그 도메인 로직을 simstate로 분류합니다. 이게 "꺼짐"을 시뮬에서 표현하는 방식입니다.

simstate의미로직 동작
NORMAL전압·전류 정상정상 평가(0/1)
CORRUPT전원 off/불충분레지스터·출력을 X로 강제
CORRUPT_ON_
ACTIVITY		전압 부족 + 토글 시토글하면 X로 오염

CORRUPT의 의미: 도메인이 꺼지면 그 안의 모든 플롭/래치/조합 출력이 X(unknown)로 바뀝니다. 단, retention 셀로 지정된 플롭과 isolation으로 보호된 출력은 예외 — 그래서 retention/isolation을 안 적으면 켤 때 X가 그대로 쏟아집니다.

개발자 직관: free()한 메모리를 다시 읽으면 쓰레기가 나오는 것과 같습니다. CORRUPT = "이 영역은 전원이 없으니 값을 신뢰하지 마라"는 X 표식. retention = 명시적으로 백업해 둔 변수, isolation = 경계에서 안전한 기본값으로 막은 출력입니다.
합법 조합표

Power State Table (PST) · add_power_state

각 supply가 가질 수 있는 상태를 정의(add_power_state)하고, 시스템이 동시에 가질 수 있는 합법 조합만 PST로 못박습니다. 정의되지 않은 조합으로 가면 위반.

# supply set 상태 정의
add_power_state PD_TOP.primary -state {AON_ON  -supply_expr {power == FULL_ON}}
add_power_state PD_CPU.primary -state {CPU_ON  -supply_expr {power == FULL_ON}} \
                                -state {CPU_OFF -supply_expr {power == OFF}}

# 시스템 합법 조합 (PST 역할) — add_power_state -state로 명시
add_power_state PD_TOP -domain \
   -state {RUN     -logic_expr {AON_ON && CPU_ON }} \
   -state {CPU_SLP -logic_expr {AON_ON && CPU_OFF}}
# RUN / CPU_SLP 두 조합만 합법. "AON_OFF && CPU_ON" 같은 건 정의 안 됨 → 위반
레거시 UPF 1.0의 add_port_state/create_pst/add_pst_state 대신, 1801-2013 이후엔 add_power_state로 supply·도메인 상태와 합법 조합을 함께 기술합니다.

PST는 검증과 정전검사의 기준표입니다. 합법 조합만 시뮬레이션하고, 도구는 "이 조합에서 켜진 쪽이 꺼진 쪽 신호를 받는데 isolation이 없다" 같은 위반을 PST 기준으로 점검합니다.

정적으로 잡아내기

PA 정전검사 (Power-Aware Static Check)

시뮬을 돌리기 전에 UPF + 넷리스트를 정적으로 훑어 전력 구조 실수를 잡습니다. 동적 시뮬보다 빠르고 빠짐없이 커버.

🔎 PA-static이 잡는 것

  • 누락 isolation: off 도메인 → on 도메인 경로에 ISO 없음
  • 누락 level shifter: 전압 다른 도메인 직결
  • 잘못된 방향(HL 자리에 LH), clamp 값 불일치
  • isolation/retention 제어신호가 always-on이 아님
  • retention 전원이 도메인과 함께 꺼짐(상태 못 지킴)

⚡ PA-dynamic(시뮬)이 잡는 것

  • save/restore·iso 순서(시퀀스) 오류
  • CORRUPT된 X가 실제로 전파되는지
  • 전력 전환 중 기능 깨짐(부팅·트래픽)
  • PST에 없는 불법 조합 진입

실무 순서: PA-static을 먼저 깨끗하게(누락 셀 0) 만든 뒤 PA-dynamic으로 시퀀스를 검증합니다. static을 건너뛰고 시뮬만 돌리면, isolation 누락은 특정 전환 시점에만 X가 새어 회귀에서 간헐적으로만 보여 디버그가 지옥이 됩니다.

★ 자주 깨지는 곳 ★

전력 검증 3대 함정

① isolation 누락 → X 누출
off 도메인 출력에 ISO를 안 걸면 simstate CORRUPT의 X가 on 도메인으로 전파 → 멀쩡한 블록이 X로 오염. 정전검사가 1순위로 잡아야 할 항목.

② retention 미모델
retention flop을 UPF/셀에 안 적으면 도메인 복귀 시 모든 상태가 X 또는 reset 값. "복귀 후 깨짐"인데 RTL은 맞아 보여 버그를 못 잡는 위양성 통과가 됨.

③ 에뮬 가시성 낮음
에뮬은 빠르지만 내부 신호 full waveform 덤프가 비싸고 느림. "여기서 깨졌다"를 안 뒤 그 구간만 다시 캡처/시뮬로 좁혀야. 무작정 trigger 전체 덤프는 비현실적.

한 줄 정리: ①②는 UPF를 정확히 적었는가의 문제(static+dynamic으로 방어), ③은 어디서 검증하는가의 문제. 그래서 sim/emu/FPGA/formal을 역할별로 나눠 쓰는 매트릭스가 필요합니다 → 다음 슬라이드.

속도가 필요할 때

에뮬레이션 — Palladium · ZeBu · Veloce

RTL 시뮬은 정확하지만 수 Hz~수십 kHz로 느려 OS 부팅·장시간 SW는 불가능. 에뮬레이터는 설계를 전용 HW에 매핑해 MHz급으로 돌립니다.

플랫폼벤더방식
PalladiumCadence커스텀 프로세서 기반 에뮬레이션
ZeBuSynopsysFPGA 기반 에뮬레이션
VeloceSiemens EDA커스텀 에뮬레이션 HW

SCE-MI / DPI: 에뮬(HW) ↔ 테스트벤치(SW, 워크스테이션)를 잇는 표준 인터페이스. SCE-MI(Standard Co-Emulation Modeling Interface)로 트랜잭션을 주고받고, DPI(SystemVerilog Direct Programming Interface)로 C/C++ 모델을 호출. 핀 단위 대신 트랜잭션 단위 통신이라 빨라짐.

hybrid emulation: CPU 같은 성숙 IP는 virtual platform(SW 모델, fast)로, 새로 만든 RTL은 에뮬로 — 둘을 붙여 돌립니다. "이미 검증된 건 빠른 모델, 새 RTL만 정밀 HW"라는 분업. 부팅·드라이버 같은 SW를 며칠이 아니라 시간 단위로 돌릴 수 있게 됩니다.

더 빠른 길과 그 대가

FPGA 프로토타이핑 — HAPS · S2C

🏎️ FPGA proto (HAPS, S2C)

  • 설계를 상용 FPGA에 매핑 → 에뮬보다도 빠름(수십~수백 MHz)
  • 실리콘 전 SW 개발·시연(near-real-time)에 유리
  • HAPS(Synopsys), S2C 등 상용 보드

🔍 대가 — 디버그가 약하다

  • 내부 신호 가시성·덤프가 에뮬보다 떨어짐
  • compile/partition 시간 길고, 변경 반영 느림
  • RTL을 FPGA에 맞게 손봐야 할 때도(메모리/클럭)

경험칙: 에뮬=디버그 가시성 우수 + bring-up/하드웨어 검증, FPGA proto=최고 속도 + SW 팀에 빠른 타깃 제공. 둘 다 capacity(게이트 용량)·컴파일 시간·비용이라는 제약을 공유합니다.

흔한 오답: "FPGA proto가 에뮬보다 항상 우월" ❌ → 속도는 빠르지만 디버그 가시성·반영 속도가 약해 버그 사냥엔 에뮬이 보통 낫습니다. 둘은 경쟁이 아니라 용도 분담.

UPF의 isolation·level shifter·retention 명령과 핵심 인자는?
isolation은 set_isolation(+set_isolation_control)으로, -clamp_value(0/1/latch)와 제어신호·sense·location을 지정합니다. level shifter는 set_level_shifter로 방향(LH=저→고, HL=고→저)을 줍니다. retention은 set_retention으로 -save_signal/-restore_signal을 정하고 map_retention_cell로 실제 셀에 매핑하며, 백업 전원은 always-on이어야 합니다(SRPG).
power-aware 시뮬의 simstate CORRUPT는 무슨 뜻인가요?
도메인 전원이 꺼지면 그 안의 플롭·래치·조합 출력을 시뮬레이터가 X(unknown)로 강제하는 상태가 CORRUPT입니다. 단 retention으로 지정한 플롭과 isolation으로 보호한 출력은 예외입니다. 그래서 retention/isolation을 안 적으면 복귀 시 X가 그대로 전파됩니다. NORMAL은 정상 평가, CORRUPT_ON_ACTIVITY는 전압 부족 상태에서 토글하면 오염되는 변형입니다.
PA 정전검사가 잡는 것, 그리고 에뮬레이션 vs FPGA 프로토타입의 차이는?
PA-static은 누락 isolation(off→on 경로), 누락/오방향 level shifter, isolation·retention 제어가 always-on이 아닌 경우 등 구조적 실수를 시뮬 전에 잡습니다. 에뮬(Palladium/ZeBu/Veloce)은 MHz급으로 부팅·장시간 SW를 돌리며 디버그 가시성이 좋고, FPGA proto(HAPS/S2C)는 더 빠르지만(수십~수백 MHz) 내부 가시성과 반영 속도가 약해 SW 조기 개발·시연에 쓰고 버그 사냥은 에뮬이 유리합니다. 둘은 SCE-MI/DPI로 테스트벤치와 연결합니다.
핵심 요약

UPF·에뮬레이션 정밀 — 한 손에

  • UPF=IEEE 1801 Tcl. create_power_domain→create_power_switch→set_isolation→set_retention
  • isolation clamp 0/1/latch, shifter LH/HL, retention=save/restore·SRPG·always-on 백업
  • simstate CORRUPT=전원 off 시 로직을 X로 강제(retention/iso는 예외)
  • add_power_state/PST로 합법 조합표, PA-static이 누락 iso/shifter 정전검사
  • 에뮬(Palladium/ZeBu/Veloce) MHz급·부팅, SCE-MI/DPI·hybrid
  • FPGA proto(HAPS/S2C)는 더 빠르나 디버그 약함 → 용도 분담

"UPF로 도메인·isolation(clamp)·retention(save/restore)을 RTL과 분리해 적고, simstate CORRUPT가 X를 주입하는 power-aware sim과 PA-static으로 검증합니다. 부팅·장시간 SW는 에뮬로, 더 빠른 시연은 FPGA proto로 — 엔진을 역할별로 나눠 씁니다."
