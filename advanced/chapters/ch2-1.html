컴포넌트 계층

testbench 트리 — 누가 누구를 만드나

트리는 build_phase에서 위→아래로 만들어지고(top-down), connect_phase에서 포트가 연결됩니다(bottom-up 완료 후).
노란 화살표 = sequencer↔driver 핸드셰이크, 청록 = monitor의 analysis port → scoreboard/coverage.

핵심 코드 ①

driver — get_next_item / item_done 루프

class my_driver extends uvm_driver#(my_item);
  `uvm_component_utils(my_driver)        // factory 등록
  virtual my_if vif;                       // DUT 핀과 연결

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    // config_db에서 virtual if 받기 (못 받으면 fatal)
    if (!uvm_config_db#(virtual my_if)::get(this, "", "vif", vif))
      `uvm_fatal("NOVIF", "virtual interface not set")
  endfunction

  task run_phase(uvm_phase phase);
    forever begin
      seq_item_port.get_next_item(req);   // ① sequencer에 다음 item 요청(blocking)
      drive_item(req);                  // ② 핀 토글로 DUT 구동
      seq_item_port.item_done();        // ③ 완료 통지 → finish_item 해제
    end
  endtask
endclass
// get_next_item ↔ item_done 가 1:1. 사이에 응답을 채우면 item_done(rsp)로 돌려줄 수도 있음.

대안: get(req)(blocking get, 내부적으로 get_next_item+item_done 묶음) / 파이프라인엔 get_next_item+item_done 분리가 표준. driver는 절대 req를 스스로 randomize하지 않습니다 — 자극 생성은 sequence의 책임.

핵심 코드 ②

sequence & monitor — 자극 만들기 / 관찰 내보내기

class my_seq extends uvm_sequence#(my_item);
  `uvm_object_utils(my_seq)
  task body();
    my_item tr;
    repeat(10) begin
      tr = my_item::type_id::create("tr");
      start_item(tr);              // 슬롯 요청
      assert(tr.randomize());     // 자극 랜덤화
      finish_item(tr);             // driver의 item_done까지 block
    end
  endtask
endclass
// sequence는 component가 아닌 object → uvm_object_utils
class my_monitor extends uvm_monitor;
  `uvm_component_utils(my_monitor)
  uvm_analysis_port#(my_item) ap;   // 관찰 출구
  virtual my_if vif;

  function void build_phase(uvm_phase ph);
    ap = new("ap", this);
  endfunction

  task run_phase(uvm_phase ph);
    forever begin
      my_item t = collect();    // 핀에서 복원
      ap.write(t);              // 구독자 전원에 broadcast
    end
  endtask
endclass
// ap.write → scoreboard/coverage의 imp가 받음

new()로 직접 객체를 만들면 factory override가 먹지 않습니다. 반드시 type_id::create(). monitor의 ap는 analysis_port(1:N broadcast)라 구독자가 0개여도, N개여도 동작합니다.

objection 메커니즘

run_phase는 언제 끝나나

run_phase는 objection 카운터가 0이 되는 순간 종료됩니다.

  • 자극 시작 전 phase.raise_objection(this) → 카운터 +1
  • 자극이 끝나면 phase.drop_objection(this) → 카운터 −1
  • 모든 컴포넌트의 objection이 0이 되면 phase가 끝나고 다음 phase로
  • set_drain_time으로 drop 후 여유 시간을 줄 수 있음
task run_phase(uvm_phase phase);
  phase.raise_objection(this);  // "아직 끝내지 마"
  seq.start(env.agt.sqr);          // 자극 실행(block)
  phase.drop_objection(this);   // "이제 끝나도 됨"
endtask
// raise/drop 짝이 안 맞으면 sim이 안 끝나거나 조기 종료

개발자 직관: 참조 카운트(RC)와 같습니다. raise=retain, drop=release. 0이 되면 GC(=phase 종료)가 일어납니다.

objection 누락이 1순위 함정: raise를 안 하면 자극이 돌기도 전에 run_phase가 0시간에 끝나 테스트가 "그냥 통과"합니다. 반대로 drop을 빠뜨리면 timeout까지 매달려 hang.

의존성 주입

uvm_config_db — virtual interface 전달

DUT의 핀(interface)을 클래스 세계(TB)로 넘기는 표준 통로. top에서 set, 컴포넌트에서 get.

// ── top module (정적 세계) ──────────────────────────
module tb_top;
  my_if dut_if(.clk(clk));                       // SystemVerilog interface 인스턴스
  dut u_dut(.i(dut_if));

  initial begin
    // 트리 어디서든 "vif"로 받을 수 있게 등록 (scope: 전역 "*")
    uvm_config_db#(virtual my_if)::set(null, "*", "vif", dut_if);
    run_test("my_test");                          // +UVM_TESTNAME으로 덮어쓰기 가능
  end
endmodule

// ── driver build_phase (동적 세계) ─────────────────
if (!uvm_config_db#(virtual my_if)::get(this, "", "vif", vif))
  `uvm_fatal("NOVIF", "vif not set for")        // get 실패 시 즉시 중단
// set(context, instance_name, field, value) / get(this, "", field, var) · 타입 #(virtual my_if)가 정확히 일치해야 함

scope 매칭은 full hierarchical path + 와일드카드(*)로 동작. 더 구체적인 path가 우선합니다.

vif를 config_db로 안 넘기면 driver/monitor의 vif가 null → 핀 접근 시 null handle 런타임 에러. set/get의 타입과 키 문자열이 한 글자라도 다르면 get이 조용히 실패합니다.

factory

type_id::create 와 override 종류

`uvm_*_utils` 매크로가 클래스를 factory에 등록 → create()로 만들면 코드 수정 없이 타입을 갈아끼울 수 있습니다.

// 1) 타입 전역 교체: 트리의 모든 my_driver를 err_driver로
set_type_override_by_type(my_driver::get_type(), err_driver::get_type());

// 2) 인스턴스 한정 교체: 이 path의 driver만 교체
set_inst_override_by_type("env.agt.drv", my_driver::get_type(), err_driver::get_type());

// 3) 문자열 기반(이름으로)
factory.set_type_override_by_name("my_driver", "err_driver");

// 적용 조건: err_driver 는 반드시 my_driver를 extends 해야 함(LSP)
// override는 build_phase의 create() 시점에 적용 → test의 build에서 미리 등록해야 함
메서드범위전형적 용도
set_type_override해당 타입 전부error injection driver, 변형 transaction
set_inst_override특정 인스턴스 path한 agent만 다른 동작 주입

override가 안 먹는 3대 이유: ① 객체를 new()로 만듦(create 아님) ② override를 create 이후에 등록 ③ 자식이 부모를 extends 안 함(타입 비호환).

field 자동화

class my_item extends uvm_sequence_item;
  rand bit [31:0] addr, data;
  `uvm_object_utils_begin(my_item)
    `uvm_field_int(addr, UVM_ALL_ON)
    `uvm_field_int(data, UVM_ALL_ON)
  `uvm_object_utils_end
endclass
// 매크로가 copy/compare/print/pack을 자동 생성

성능이 중요하면 매크로 대신 do_copy/do_compare를 직접 오버라이드(매크로는 편하지만 무겁다). UVM_ALL_ON은 비교/프린트/팩 전부 on, UVM_NOCOMPARE 등으로 끌 수 있음.

레지스터 추상화

RAL — 주소가 아니라 이름으로

RAL(Register Abstraction Layer)은 DUT 레지스터를 클래스 모델로 들고, 주소·필드를 추상화합니다.

  • uvm_reg / uvm_reg_field / uvm_reg_block 계층
  • read()/write()가 내부에서 버스 트랜잭션(adapter)로 변환
  • mirror(예측값) vs desired vs actual 값 추적
  • 예측: explicit(monitor) / implicit prediction
// 주소를 몰라도 이름으로 접근
ral.ctrl_reg.write(status, 32'h1, .map(map));
ral.ctrl_reg.read(status, rdata, .map(map));

// 필드 단위 비교/체크
ral.ctrl_reg.mirror(status, UVM_CHECK);
// adapter가 uvm_reg_bus_op ↔ AXI/APB 트랜잭션 변환

RAL이면 자동 시퀀스 uvm_reg_hw_reset_seq, uvm_reg_bit_bash_seq 등으로 리셋값·R/W 비트를 한 번에 점검할 수 있습니다.

실행 제어

+UVM_TESTNAME · verbosity — 컴파일 없이 바꾼다

플래그/매크로효과
+UVM_TESTNAME=my_testrun_test()가 factory로 그 test를 생성(재컴파일 X)
+UVM_VERBOSITY=UVM_HIGH로그 상세도 전역 설정
`uvm_info(ID, MSG, UVM_MEDIUM)verbosity ≤ 임계일 때만 출력
+uvm_set_config_int=...커맨드라인에서 config 값 주입

verbosity 단계: UVM_NONE < LOW < MEDIUM < HIGH < FULL < DEBUG. uvm_info는 임계 이하만 출력하고, uvm_warning/error/fatal은 verbosity와 무관하게 항상 나오며 fatal은 즉시 종료. error 카운트가 0이면 회귀 PASS로 집계하는 흐름이 일반적입니다.

메시지를 $display로 찍으면 verbosity/카운트 집계 밖이라 회귀 판정에 안 잡힙니다. UVM에선 반드시 `uvm_info/error를 쓰세요.

검증 엔지니어의 시선

이 구조를 어떻게 점검·재사용하나

🧩 재사용 / 주입

  • factory override로 error-injection driver를 코드 변경 없이 끼움
  • config_db로 agent를 active/passive 전환(monitor만 동작)
  • VIP/agent를 그대로 다른 프로젝트에 재사용

🎯 점검 포인트

  • SVA assertion으로 핸드셰이크·프로토콜 위반 즉시 검출
  • covergroup을 monitor의 write에 sample
  • scoreboard에서 compare로 기대 vs 실제
  • objection drain/timeout으로 hang 조기 검출

UVM의 가치는 "동작"보다 재사용·제어 가능성입니다. factory + config_db + phase가 그 세 축이라, 면접에서 이 셋을 코드로 설명할 수 있으면 강합니다.

면접 심화 질문

여기까지 답하면 "실무자"로 보인다

objection 메커니즘을 설명해보세요.
run_phase는 raise/drop objection으로 만든 카운터가 0이 되면 종료됩니다. 자극 시작 전 phase.raise_objection(this)로 +1, 끝나면 drop_objection으로 −1, 모든 컴포넌트 합이 0이면 다음 phase로 넘어갑니다. raise를 빼면 0시간에 끝나 테스트가 헛통과하고, drop을 빼면 timeout까지 hang합니다.
sequencer–driver 핸드셰이크는?
driver가 seq_item_port.get_next_item(req)로 다음 아이템을 요청(blocking), 구동 후 item_done()으로 완료 통지합니다. sequence 쪽은 start_item/finish_item이 짝이고, finish_item은 driver의 item_done까지 블록됩니다. 1:1 핸드셰이크라 백프레셔처럼 자연스럽게 속도가 맞춰집니다.
config_db와 factory override는 각각 무엇이고, override 종류는?
config_db는 virtual interface나 설정값을 트리에 주입하는 통로로 top에서 set, 컴포넌트 build에서 get합니다. factory는 type_id::create로 만든 객체의 타입을 교체하는 메커니즘으로, 전역 교체 set_type_override_by_type과 인스턴스 한정 set_inst_override_by_type(+이름 기반)이 있습니다. 자식이 부모를 extends해야 적용됩니다. RAL은 레지스터를 uvm_reg 클래스 모델로 추상화해 주소 대신 이름으로 read/write·mirror하는 계층입니다.
핵심 요약

UVM 정밀 — 한 손에

  • driver: get_next_item → drive → item_done forever 루프
  • sequence: start_item / randomize / finish_item
  • monitor: ap.write()로 1:N analysis broadcast
  • phase: build(top-down)→connect→...→run(task)
  • objection: raise/drop 카운터=0 → run 종료
  • config_db로 vif 주입, factory create+override로 교체
  • field 매크로 / RAL / +UVM_TESTNAME · verbosity

"UVM은 phase로 생명주기를, objection으로 종료를, config_db·factory로 재사용·주입을 표준화한 검증 프레임워크입니다. driver–sequencer는 get_next_item/item_done 핸드셰이크로 묶입니다."
