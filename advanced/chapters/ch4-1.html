시뮬레이션
Analyze/Compile: 파일 단위로 파싱·문법 검사 후 라이브러리에 중간 표현을 적재. Elaborate: top을 기준으로 디자인 전체를 한 덩어리로 조립(인스턴스화·파라미터 확정·연결 해결). Run: 만들어진 이미지로 시간을 진행.

개발자 비유: compile은 .o 오브젝트 만들기(파일별), elaborate는 link 단계(심볼·인스턴스 해결해 실행파일 생성), run은 그 바이너리 실행. 다만 HDL의 elaboration은 "하드웨어 계층을 펼치는" 작업이라 링크보다 훨씬 구조적입니다.

VCS 플로우 ①

Synopsys VCS — 3-step 정석

# 1) Analyze : SV 소스를 파싱해 라이브러리에 적재
vlogan -full64 -sverilog +incdir+./rtl+./tb \
       +define+SIM+WIDTH=32 -timescale=1ns/1ps \
       ./rtl/dut.sv ./tb/top_tb.sv -l vlogan.log

# 2) Elaborate : top을 잡아 디자인 조립 → simv 실행이미지 생성
vcs    -full64 -debug_access+all top_tb \
       -P novas.tab pli.a            # (PLI 링크 예시: Verdi/FSDB novas.tab+pli.a) \
       -l vcs_elab.log

# 3) Simulate : 만들어진 실행이미지 실행
./simv +UVM_TESTNAME=my_test +ntb_random_seed=7 \
       -l sim.log
vlogan=분석, vcs=엘라보+링크(simv 생성), ./simv=런타임. VHDL은 vhdlan 사용.

vlogan이 만든 산출물은 보통 ./AN.DB 라이브러리에 쌓이고, vcs 단계에서 top 모듈명을 인자로 받아 elaboration을 수행합니다. +incdir은 \`include 탐색 경로, +define은 매크로 정의 — 둘 다 분석(compile) 단계의 입력입니다.

VCS 플로우 ②

통합 1-step 호출 vs 3-step, 언제 뭘 쓰나

# 통합(single-call) : vcs 한 번이 내부에서 분석+엘라보를 함께
vcs -full64 -sverilog +incdir+./rtl \
    +define+SIM ./rtl/dut.sv ./tb/top_tb.sv \
    -debug_access+all -l build.log
./simv +UVM_TESTNAME=my_test -l sim.log
구분3-step (vlogan→vcs→simv)통합 (vcs ... → simv)
분석/엘라보 분리명시적으로 분리vcs가 내부에서 둘 다 수행
증분 컴파일강함 — 바뀐 파일만 다시 vlogan제한적(전체 재처리 경향)
대형 회귀/CI라이브러리 재사용에 유리소규모·단발 빌드에 간단
전형적 사용처UVM 검증 환경, 야간 회귀빠른 스모크 테스트

"통합 호출은 항상 더 편하다" ❌ — 파일 수백 개의 검증 환경에서 한 파일만 고쳐도 매번 전체를 재분석하면 빌드가 폭발합니다. 그래서 실무 회귀는 대개 vlogan으로 증분 분석 → vcs로 재엘라보 패턴을 씁니다.

Xcelium 플로우

Cadence Xcelium — xrun 2-step / single-step

# single-step : xrun 한 번에 compile+elab+sim
xrun -sv -64bit +incdir+./rtl +define+SIM \
     -uvmhome CDNS-1.2 +UVM_TESTNAME=my_test \
     ./rtl/dut.sv ./tb/top_tb.sv -l xrun.log

# 2-step (정밀 제어) : 컴파일 / 엘라보를 분리한 하위 툴
xmvlog  -sv +incdir+./rtl ./rtl/dut.sv ./tb/top_tb.sv  # 분석
xmelab  -access +rwc top_tb                            # 엘라보 → snapshot
xmsim   top_tb +UVM_TESTNAME=my_test                  # 런타임
xrun=올인원 프런트엔드. 내부적으로 xmvlog(분석)·xmelab(엘라보)·xmsim(런)을 호출. 산출물은 simv 같은 파일이 아니라 snapshot(worklib.top:module).

VCS는 simv 실행이미지(독립 바이너리), Xcelium은 snapshot(라이브러리 안의 엘라보 결과)을 만듭니다. 이름·산출물 형태가 다르지만 "엘라보 결과를 저장해 재실행"이라는 개념은 동일합니다.

-access +rwc(xmelab) / -debug_access+all(vcs)는 신호 가시성 옵션 — 파형 덤프·force·read 권한을 엘라보 시점에 결정합니다. 끄면 빨라지지만 디버깅이 막힙니다.
엘라보레이션의 정체

Elaboration이 "실제로" 하는 일

  • 인스턴스화(instantiation): top부터 모듈/인터페이스/프로그램을 재귀적으로 펼쳐 유일한 인스턴스 트리를 만든다.
  • 파라미터 확정: parameter/localparam, #(.WIDTH(32)) override, defparam을 해결해 상수값을 고정한다(엘라보 후엔 못 바꿈).
  • generate 펼치기: for/if generate를 조건에 맞게 전개 — 코드가 실제 인스턴스/논리로 확정된다.
  • bind 삽입: bind 문으로 모듈에 외부 모듈(주로 checker/assertion)을 붙인다.
  • $unit·이름 해석: 컴파일 단위 스코프($unit), 계층 이름(top.u_dut.reg) 참조를 해결한다.
  • 연결·폭 해결: 포트 연결, net 폭, 타입 정합성을 확정한다.
  • PLI/VPI/DPI 링크: C 모델·세이버/덤퍼·DPI import "DPI-C"를 심볼 해결해 실행이미지에 묶는다.

한 줄 요약: "파라미터·generate·연결·이름·외부코드를 전부 확정해, 시간이 0인 정적 하드웨어 그림을 완성"하는 단계입니다. 그래서 엘라보 후엔 디자인 구조가 바뀌지 않습니다.

파라미터·제너레이트

엘라보 타임에 결정되는 코드 — 예시

module fifo #(parameter int DEPTH = 16, parameter int W = 8)
  (input clk, ...);
  // 폭·깊이는 엘라보 시점에 상수로 박힘
  logic [W-1:0] mem [DEPTH];

  generate
    if (DEPTH > 32) begin : g_big   // 조건이 엘라보 때 평가
      big_ctrl u_ctrl (.*);
    end else begin : g_small
      small_ctrl u_ctrl (.*);
    end
  endgenerate
endmodule

// 상위에서 override → 두 인스턴스가 서로 다른 하드웨어로 펼쳐짐
fifo #(.DEPTH(64), .W(32)) u_big   (.clk, ...);  // g_big 선택
fifo #(.DEPTH(8),  .W(8))  u_small (.clk, ...);  // g_small 선택
DEPTH>32 분기는 런타임이 아니라 엘라보 타임에 평가되어 인스턴스 자체가 달라진다.

가장 흔한 오개념: "파라미터를 시뮬 중에 plusarg로 바꾸면 폭이 바뀐다" ❌ — 파라미터는 엘라보 타임 상수라 런타임 +ARG로 못 바꿉니다. 폭/깊이를 바꾸려면 재엘라보(재빌드)가 필요. 런타임에 바꿀 수 있는 건 $value$plusargs로 읽는 변수·설정값뿐입니다.

bind — 침투 없이 붙이기

bind: RTL을 안 건드리고 checker/커버리지 삽입

bind는 대상 모듈을 수정하지 않고 외부 모듈(주로 SVA assertion/커버리지/모니터)을 그 안에 인스턴스화하는 엘라보-타임 문법입니다.

  • RTL 소유자와 검증자가 분리돼도 RTL 파일 불변
  • 주로 checker·protocol assertion·formal property 주입
  • 대상의 내부 신호에 계층 이름으로 접근 가능
// dut.sv 는 한 글자도 안 고침
module fifo_sva(input clk, full, push);
  a_no_push_when_full: assert property(
    @(posedge clk) full |-> !push);
endmodule

// tb 어딘가에서 바인딩(엘라보 때 삽입)
bind fifo  fifo_sva u_chk (
  .clk(clk), .full(full), .push(push));

bind <대상모듈> <삽입모듈> <인스턴스명> (...). 엘라보 타임에 대상의 모든 인스턴스에 자동 삽입됩니다(또는 특정 인스턴스 지정 가능). 면접 단골: "RTL을 못 만지는데 assertion을 넣으려면?" → 정답이 bind.

"UVM도 일종의 elaboration 아니냐"는 말은 반쯤만 맞습니다. UVM의 "엘라보"는 비유일 뿐 — 실제로는 런타임 객체 생성(build_phase)이라 HDL의 정적 elaboration과 시점·메커니즘이 전혀 다릅니다. 이 둘을 정확히 구분하면 면접에서 깊이가 드러납니다.

SystemVerilog 핵심

이벤트 스케줄링 영역 — 한 타임슬롯의 7단계

한 시뮬레이션 시각(time slot) 안에서 이벤트는 정해진 영역(region) 순서로 평가됩니다. 레이스를 막기 위해 LRM이 순서를 못박아 둔 것.

대표 7영역: Preponed → Active → Inactive → NBA → Observed → Reactive → Postponed. (LRM은 이 사이에 Pre-/Post- 보조 영역도 정의하지만, 면접은 이 7개를 묻습니다.)
영역이 왜 중요한가

blocking vs non-blocking, 그리고 레이스

영역여기서 일어나는 일관련 구문
Preponed샘플링(값을 "이전" 시점으로 캡처)@(...), SVA 샘플, $sampled
Activeblocking 대입, RHS 평가=, $display
Inactive#0 지연 이벤트 처리#0
NBAnon-blocking 대입의 실제 갱신<=
Observedconcurrent assertion property 평가assert property
Reactiveprogram block / SVA action block(pass·fail 코드)program, SVA pass/fail action block
Postponed안정된 최종값 읽기(쓰기 금지)$strobe, $monitor

클래식 레이스: 클럭 엣지에서 RTL은 <=(NBA 영역에서 갱신)로 쓰는데, TB가 =(Active 영역)로 같은 신호를 읽으면 갱신 전 옛값을 보게 됩니다. 그래서 TB 샘플링은 program/Reactive나 $sampled(Preponed)에 맞춰 설계합니다 — UVM이 clocking block을 쓰는 이유.

에러 3종

compile-time vs elaboration-time vs run-time

📝 Compile-time

파일 단위 문법·타입 오류. 한 파일만 봐도 잡힘.

  • 세미콜론 누락, 키워드 오타
  • 타입 불일치, 미선언 식별자
  • vlogan/xmvlog가 보고

🔗 Elaboration-time

여러 파일을 조립할 때만 드러나는 오류.

  • 모듈/인스턴스 미해결
  • 포트 폭·개수 불일치
  • 파라미터 충돌, 중복 정의
  • vcs/xmelab이 보고

⏱️ Run-time

시간이 흐를 때 값에 의존해 터지는 오류.

  • 배열 OOB, null 핸들 역참조
  • 0 나눗셈, X 전파
  • assertion fail, timeout
  • simv/xmsim 중 발생

분리 기준: "한 파일만 보면 아나?" → compile. "파일들을 합쳐 top을 조립해야 아나?" → elaboration. "실행해서 값이 흘러야 아나?" → run-time. 면접에서 port width mismatch를 어디서 잡느냐 물으면 elaboration-time이 정답.

증분 빌드와 재처리

재컴파일 vs 재엘라보 — 무엇이 무엇을 트리거하나

바뀐 것필요한 작업이유
한 모듈의 내부 RTL그 파일만 재분석 + 재엘라보증분 컴파일이 변경 파일만 vlogan
파라미터 override 값재엘라보(재분석은 불필요할 수도)param은 엘라보-타임 상수
+incdir/+define 매크로재분석 필요전처리·\`include는 분석 단계 입력
런타임 plusarg(+SEED 등)아무것도 재빌드 안 함$value$plusargs로 런타임에 읽음

실무 함정: "테스트 케이스(시드/플러그)만 바꿨는데 매번 풀 빌드를 돌린다" — 시간 낭비입니다. plusarg·UVM_TESTNAME 변경은 simv 재실행만 하면 됩니다. 반대로 +define 매크로를 바꾸고 재분석을 안 하면, 이전 빌드가 그대로 돌아 "고쳤는데 안 바뀐다"는 유령 버그가 납니다.

검증 엔지니어의 시선

빌드·스케줄링을 어떻게 검증·진단하나

🧩 무엇으로

  • bind로 SVA/모니터를 RTL 침투 없이 주입
  • UVM build_phase에서 env 동적 구성, clocking block으로 샘플 영역 고정
  • VCS/Xcelium elab 로그에서 param·generate 해석 결과 확인
  • 커버리지 빌드는 vcs -cm / xrun -coverage 옵션으로 계측

🎯 무엇을(코너)

  • 모든 파라미터 조합이 엘라보 성공하는지(generate 분기 전체)
  • 샘플링 레이스: $sampled/clocking block으로 옛값/새값 일치
  • NBA vs blocking 순서 의존 버그
  • 증분 빌드 후 결과가 풀 빌드와 동일한지(빌드 무결성)

"기능은 도는데 빌드 플로우가 틀린" 경우가 의외로 많습니다 — 옛 라이브러리 재사용, 매크로 미반영, 샘플 영역 레이스. 그래서 회귀는 클린 빌드 검증 + clocking 기반 샘플링 + assertion always-on을 묶어 돌립니다.

VCS 2-step(통합)과 3-step의 차이는?
3-step은 vlogan(분석)→vcs(엘라보+링크, simv 생성)→./simv(런)로 단계를 분리합니다. 분석 산출물을 라이브러리에 쌓아두니 한 파일만 고치면 그 파일만 재분석하는 증분 컴파일이 가능해 대형 회귀에 유리합니다. 통합 호출은 vcs 한 번이 분석+엘라보를 함께 해 소규모 빌드엔 간단하지만 증분에 약합니다. Xcelium은 xrun 단일 호출 또는 xmvlog→xmelab→xmsim 2-step입니다.
Elaboration에서 정확히 뭐가 일어나나요?
top부터 모듈을 재귀 인스턴스화해 유일한 계층 트리를 만들고, 파라미터/override/defparam을 확정하며, generate를 조건에 맞게 펼치고, bind를 삽입하고, 포트 연결·net 폭·계층 이름($unit 포함)을 해결하고, PLI/VPI/DPI 외부 코드를 링크해 실행이미지(simv) 또는 snapshot을 만듭니다. 끝나면 디자인 구조는 불변입니다.
SV 이벤트 영역을 순서대로, NBA가 왜 중요한가요?
한 타임슬롯은 Preponed→Active→Inactive→NBA→Observed→Reactive→Postponed 순입니다. blocking(=)은 Active에서, non-blocking(<=)의 갱신은 NBA에서 일어나죠. RTL이 NBA로 쓴 값을 TB가 Active에서 읽으면 옛값을 보는 레이스가 생기므로, 샘플링은 Preponed($sampled)나 Reactive(program/clocking block)에 맞춥니다.
bind가 무엇이고 왜 쓰나요?
대상 모듈을 수정하지 않고 외부 모듈(보통 SVA assertion·커버리지·모니터)을 엘라보 타임에 그 안으로 인스턴스화하는 문법입니다. RTL 파일을 못 건드리는 상황에서 protocol checker를 주입할 때 표준 해법입니다.
compile / elaboration / run-time 에러를 어떻게 구분하나요?
한 파일만 봐도 잡히는 문법·타입 오류는 compile-time(vlogan/xmvlog), 파일을 합쳐 top을 조립할 때 드러나는 포트 폭 불일치·미해결 인스턴스·파라미터 충돌은 elaboration-time(vcs/xmelab), 실행 중 값에 의존해 터지는 배열 OOB·null 역참조·assertion fail은 run-time(simv/xmsim)입니다.
핵심 요약

Compile·Elab 정밀 — 한 손에

  • VCS 3-step: vlogan→vcs(simv)→./simv · 통합은 vcs 한 번
  • Xcelium: xrun 단일 또는 xmvlog→xmelab→xmsim(snapshot)
  • Elaboration = param·generate·연결·bind·DPI 링크 확정(이후 불변)
  • HDL elab(빌드타임 정적) ≠ UVM build_phase(런타임 동적)
  • 이벤트 영역: Preponed→Active→Inactive→NBA→Observed→Reactive→Postponed
  • 에러 3종: 파일별=compile · 조립=elab · 값 의존=run-time
