왜 Git만으론 부족한가

Git의 모델 = "전부 복제"

Git은 분산 VCS라 clone 시 전체 히스토리를 가져옵니다. 텍스트 소스엔 최고지만, 파형 덤프·암호화된 IP·합성 라이브러리 같은 대용량 바이너리가 들어오면 무너집니다.

측면텍스트 RTL/TB대용량 바이너리(파형·lib·GDS)
diff/merge줄 단위로 깔끔불가능(바이너리는 line diff 없음)
delta 압축잘 됨 → 저장소 작음거의 안 됨 → 버전마다 통째 저장
저장소 크기수십 MB금방 수십~수백 GB, clone 수 시간
권한레포 단위면 충분IP별 파일 단위 접근 통제 필요

핵심 함정: Git은 한 번 커밋한 큰 파일을 히스토리에서 지워도 객체는 .git에 영구히 남습니다. "다음 커밋에서 지우면 되지" ❌ — clone 비용은 영원히 남습니다. 그래서 처음부터 LFS/외부 VCS로 갈라놔야 합니다.

Git LFS 메커니즘 ①

포인터 파일 — 실제 내용은 "주소"만 커밋된다

LFS는 추적 대상 파일을 커밋할 때, 진짜 바이너리를 별도 LFS 스토어로 보내고, Git 저장소에는 작은 텍스트 포인터만 남깁니다. 포인터는 콘텐츠 해시(oid sha256)와 크기를 담은 3줄짜리 파일입니다.

# Git에 실제로 커밋되는 "포인터 파일"의 전체 내용 (sim.vcd)
version https://git-lfs.github.com/spec/v1
oid sha256:4d7a214614ab2935c943f9e0ff69d22eadbb8f32b1258daaa5e2ca24d17e2393
size 134217728
실제 134 MB 파형은 LFS 스토어에 있고, Git이 추적하는 건 이 ~130바이트 텍스트뿐. git diff도 이 세 줄에 대해서만 돕니다(해시가 바뀌면 내용이 바뀐 것).

동작 순서: checkout/pull 시 LFS smudge 필터가 포인터를 읽어 → 해당 oid의 실제 파일을 LFS 서버에서 받아 작업트리에 채웁니다. commit/push 시 clean 필터가 반대로 바이너리를 떼어내 포인터로 치환합니다. 둘 다 Git의 clean/smudge filter 메커니즘 위에 얹혀 있습니다.

Git LFS 메커니즘 ②

.gitattributes — 무엇을 LFS로 보낼지 선언

# 1) 어떤 확장자를 LFS로 추적할지 등록 (.gitattributes에 줄 추가)
git lfs track "*.vcd" "*.fsdb" "*.lib" "*.gds" "*.db"

# 2) 그 결과로 .gitattributes에 생기는 줄 (이 파일은 반드시 커밋!)
*.vcd  filter=lfs diff=lfs merge=lfs -text
*.fsdb filter=lfs diff=lfs merge=lfs -text
*.gds  filter=lfs diff=lfs merge=lfs -text

# 3) 이후 평소처럼 add/commit/push — 자동으로 포인터화
git add sim.vcd .gitattributes
git commit -m "add nightly waveform"
git push

filter=lfs가 clean/smudge를, diff=lfs merge=lfs가 LFS 인식 diff/merge를, -text가 "줄바꿈 변환 금지(바이너리)"를 뜻합니다.

가장 흔한 실수: .gitattributes를 커밋 안 함 → 다른 팀원/CI는 추적 규칙을 몰라 실제 바이너리가 그대로 Git에 들어감. 또 track을 나중에 걸면 이미 커밋된 파일은 LFS로 안 옮겨짐(별도 git lfs migrate 필요).

대용량 바이너리 처리 전략

무엇을 버전관리하고 무엇을 버릴 것인가

자산성격권장 처리
RTL / TB / 스크립트텍스트, diff 가능일반 Git

판단 기준: "스크립트+입력으로 재생성 가능하면 커밋하지 말고, 입력만 핀(pin)으로 고정"이 원칙. 재현불가하고 외부에서 받은 거대 입력(foundry deck)만 LFS/외부 VCS로 보존합니다.

멀티레포 통합 ①

submodule vs subtree — Git 내장 두 방식

# submodule: 자식 레포를 "특정 커밋 SHA"로 참조(포인터). 내용은 별도 레포에 있음
git submodule add git@server:ip/aes_core.git ip/aes_core
git submodule update --init --recursive   # clone 후 자식 받아오기

# 부모는 .gitmodules + 자식의 고정 SHA만 저장 → 자식 버전을 정확히 핀
cat .gitmodules:
[submodule "ip/aes_core"]
    path = ip/aes_core
    url  = git@server:ip/aes_core.git

# 자식 버전 올리기: 자식에서 체크아웃 → 부모에서 그 SHA를 커밋
cd ip/aes_core && git checkout v2.3 && cd -
git add ip/aes_core && git commit -m "bump aes_core to v2.3"

submodule: 자식 히스토리 분리, 부모엔 SHA 핀만. IP별 독립 레포·권한에 적합. subtree: 자식 코드를 부모에 병합해 넣음 → clone 한 방에 다 옴, 대신 두 히스토리가 섞임.

detached HEAD 함정: submodule update는 자식을 특정 SHA에 detached 상태로 체크아웃합니다. 그 안에서 수정하고 커밋하면 어느 브랜치에도 안 붙어 나중에 사라질 수 있음. 자식에서 작업할 땐 먼저 브랜치로 체크아웃하세요.

멀티레포 통합 ②

repo(Android) · west(Zephyr) — manifest 방식

수십~수백 개 레포를 묶을 땐 submodule 중첩이 지옥이 됩니다. 그래서 manifest XML/YAML 한 파일이 "어떤 레포를 어느 리비전으로 가져올지" 선언하고, 전용 툴이 일괄 동기화합니다.

<!-- Google repo: default.xml manifest (Android식) -->
<manifest>
  <remote name="soc" fetch="git@server:"/>
  <default remote="soc" revision="main"/>
  <project name="ip/aes_core" path="ip/aes"  revision="v2.3"/>
  <project name="ip/uart"     path="ip/uart" revision="a1b2c3d"/>
</manifest>

# 동기화 — manifest에 적힌 모든 레포를 그 리비전으로
repo init -u git@server:manifest.git -b main
repo sync -j8

# Zephyr west는 west.yml(YAML) manifest로 동일 개념을 수행
west init -m git@server:manifest.git ;  west update

submodule vs manifest tool: submodule은 핀이 부모 커밋 트리 안(SHA)에 박혀 Git 네이티브. repo/west는 핀이 별도 manifest 파일에 모여 있어 수백 레포를 한눈에·한 번에 다루기 쉽고, manifest 자체를 버전·태깅합니다.

구조 선택

모노레포 vs 멀티레포 — 트레이드오프

모노레포(한 레포에 전부)멀티레포(IP별 분리)
원자적 변경한 커밋으로 교차 IP 수정레포마다 따로 → 버전 정합 신경
버전 핀커밋 SHA 하나면 전체 일관submodule/manifest로 명시 핀
권한레포 통째 → 세밀 통제 어려움IP별 접근 통제 쉬움
clone/CI거대 → 느림(부분 체크아웃 필요)필요한 IP만 → 가벼움
리팩터/검색전역 grep·일괄 변경 쉬움흩어져 어려움
현실의 SoC 팀은 혼합형이 많습니다: 공용 인프라/플랫폼은 모노레포, 외부 IP·라이선스 묶음은 멀티레포(+manifest 핀). 선택 기준은 "원자성이 중요한가 vs 권한·분리가 중요한가".
브랜치 & CI

release/IP 브랜치와 회귀 훅

feature/…
→
main
→
release/IP-r1

push/PR → CI 트리거 → lint·smoke sim → merge → nightly 전체 회귀

  • feature: 작업 단위, PR로 리뷰
  • main: 항상 "회귀 통과" 상태 유지
  • release/IP: 양산·delivery용 안정 브랜치(버그픽스만 cherry-pick)
# CI 회귀 훅: push → Jenkins → sim regression (개념 흐름)
on push/PR  →  Jenkins job
   ├─ lint (spyglass/verible)        # 빠른 게이트
   ├─ smoke regression (수십 테스트)  # PR 게이트, ~분
   └─ nightly: full regression + coverage merge  # ~시간

바이너리 머지 함정: 두 브랜치가 같은 .gds/.fsdb를 고치면 Git은 자동 머지 불가 → conflict. 바이너리는 "한 사람만 수정(lock)" 또는 regen 후 재핀 정책이 필요합니다(그래서 외부 VCS의 파일 락이 쓰임).

tape-out 정밀

annotated/signed tag로 "그 순간"을 박제

# lightweight tag: 단순 이름표(메타 없음) — tape-out엔 부적절
git tag tapeout-a0

# annotated tag: 작성자·날짜·메시지가 든 "객체"로 저장 → 추적 가능
git tag -a tapeout-a0 -m "AES SoC A0 tapeout 2026-06-12, DRC/LVS clean, rev a1b2c3d"

# signed tag: GPG 서명으로 "누가" 승인했는지 암호학적 증명
git tag -s tapeout-a0 -m "signed-off for mask order"
git tag -v tapeout-a0          # 서명 검증
git push origin tapeout-a0     # 태그는 자동 push 안 됨 → 명시

annotated는 태거·타임스탬프·메시지를 담은 별도 Git 객체. signed는 거기에 GPG 서명을 더해 "마스크 발주 승인"의 부인방지(non-repudiation)를 제공합니다. 감사 추적이 필수인 tape-out엔 annotated 이상을 씁니다.

lightweight tag만 쓰면 누가·언제·왜가 안 남습니다. 또 git push는 기본적으로 태그를 안 올리니 명시 push를 빠뜨려 "릴리스 태그가 서버에 없는" 사고가 흔합니다.

재현성

manifest lock — "6개월 뒤 똑같이 빌드"

tape-out 칩에 버그가 나면 정확히 그 비트스트림을 재현해야 합니다. 태그 하나로는 부족 — 모든 IP·툴·deck의 버전이 한 곳에 고정돼야 합니다.

고정 대상방법
모든 서브레포submodule SHA 핀 / repo·west manifest의 고정 revision
manifest 자체manifest 레포에 annotated tag → "이 태그 = 전체 BOM"
EDA 툴 버전스크립트/도커 이미지로 버전 박제(예: VCS 2025.x)
foundry deckLFS/외부 VCS의 라벨로 핀
# repo: 현재 모든 레포의 정확한 SHA를 박제한 manifest 스냅샷 생성
repo manifest -r -o tapeout-a0-lock.xml   # -r = revision을 실제 SHA로 고정
# 6개월 뒤: 이 lock 파일로 init/sync 하면 비트 동일 재현

BOM(Bill of Materials) = lock 파일. "tape-out 태그를 풀면 전체 컴포넌트 버전이 자동 복원"되는 상태가 재현성의 목표입니다. 면접에서 "재현성 어떻게 보장?"엔 annotated tag + manifest lock + 툴 버전 핀 3종을 말하세요.

왜 HW는 Perforce/DesignSync인가

중앙형 VCS를 택하는 진짜 이유

🐘 초대용량

P4/DesignSync는 거대 바이너리 + 부분 동기화가 네이티브. 필요한 디렉터리만 받음(전체 히스토리 clone 불필요).

🔒 파일 락

p4 lock/exclusive checkout으로 바이너리 동시수정 차단. 머지 불가 파일의 충돌을 원천 봉쇄.

🛂 세밀 권한

경로·파일 단위 ACL. 외부 IP를 라이선스 범위 내 인원만 접근 — 레포 단위 Git으론 어려움.

P4(Helix Core): 중앙 depot, changelist 단위 atomic 커밋, exclusive lock(+l filetype). DesignSync(Synopsys)·ClearCase(IBM): EDA 친화, 파일락·세밀 권한·대용량 특화로 반도체에서 오래 쓰임.

"HW도 그냥 Git 쓰지 왜?" ❌ — 파형/암호화 IP/GDS는 diff·merge가 불가하고 락이 필수이며 부분 동기가 필요합니다. Git의 분산·전체복제 모델과 정면 충돌. 그래서 RTL은 Git, 거대 자산은 P4/DesignSync 혼용이 흔합니다.

검증 엔지니어의 시선

저장소·재현성을 어떻게 "검증"하나

🧪 회귀 재현성

  • 회귀 결과에 커밋 SHA·seed·manifest lock을 함께 기록
  • "이 fail을 정확히 재현" → SHA 체크아웃 + 같은 seed
  • nightly 후 coverage DB 머지(merge across runs)

🪝 게이트 자동화

  • PR pre-merge 훅: lint + smoke 회귀 통과해야 merge
  • .gitattributes·대용량 파일 금지 검사(pre-commit hook)
  • tape-out 태그는 회귀·DRC/LVS clean 증빙과 묶어 승인

검증 관점에선 저장소가 "실험 노트"입니다. 어떤 RTL·TB·seed·툴로 어떤 결과가 났는지 SHA로 못 박아야 회귀가 과학이 됩니다. 재현 불가한 fail은 디버그가 불가능합니다.

면접 심화 질문

여기까지 답하면 "운영해봤다"로 보인다

Git LFS는 정확히 어떻게 동작하나요?
.gitattributes에 filter=lfs로 추적 패턴을 걸면, 커밋 시 clean 필터가 실제 바이너리를 LFS 스토어로 보내고 Git엔 version/oid sha256/size 세 줄짜리 포인터 파일만 들어갑니다. checkout 시 smudge 필터가 그 oid로 실제 파일을 받아 채웁니다. 그래서 저장소는 가볍고 clone이 빨라집니다.
submodule과 repo/west(manifest)의 차이는?
submodule은 자식 레포의 커밋 SHA를 부모 트리 안에 핀으로 박는 Git 네이티브 방식이라 소수 레포에 적합합니다. repo/west는 수백 개 레포의 버전을 별도 manifest 파일(XML/YAML)에 모아 선언하고 전용 툴이 일괄 sync하며, manifest 자체를 태깅·lock해 대규모 SoC에 적합합니다.
HW가 Perforce/DesignSync를 쓰는 이유와 tape-out 재현성은?
파형·암호화 IP·GDS는 diff/merge가 불가하고 동시수정 충돌을 막을 파일 락, 부분 동기화, 파일 단위 권한이 필요한데 이는 P4/DesignSync의 강점이고 Git의 분산·전체복제 모델과 충돌합니다. 재현성은 annotated(또는 signed) tag로 시점을 박고, manifest lock으로 모든 IP의 SHA와 툴·deck 버전을 고정해 BOM 전체를 복원 가능하게 만들어 보장합니다.
핵심 요약

HW팀 Git 정밀 — 한 손에

  • LFS: .gitattributes filter=lfs → 포인터(oid sha256/size)만 커밋
  • 대용량: 재생성 가능하면 커밋 X(아티팩트), 재현불가 입력만 LFS/외부VCS 핀
  • 멀티레포: submodule(SHA 핀) vs repo/west(manifest 선언) vs subtree(병합)
  • 모노 vs 멀티: 원자성 vs 권한·분리 트레이드오프
  • tape-out: annotated/signed tag + manifest lock = 재현성
  • Perforce/DesignSync: 초대용량·파일락·세밀 권한 → HW에서 Git과 혼용

"HW 저장소는 텍스트는 Git, 거대 바이너리는 LFS/외부 VCS로 가르고, 멀티레포를 manifest로 핀하며, tape-out을 annotated tag와 lock으로 박제해 재현 가능한 실험 노트로 만드는 일입니다."
