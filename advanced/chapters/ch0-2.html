FF의 시간 규칙

setup / hold — 데이터가 안정해야 하는 창

FF는 클럭 엣지를 점이 아니라 창(window)으로 봅니다. 엣지 직전 Tsu부터 직후 Th까지 D가 흔들리면 출력이 보장되지 않습니다.

  • Tsetup: 엣지 전 데이터가 고정돼 있어야 하는 시간
  • Thold: 엣지 후 데이터가 유지돼야 하는 시간
  • Tcq(clk→Q): 엣지 후 출력이 바뀌는 지연
setup 위반 → 데이터가 너무 늦게 도착(주기가 짧음). hold 위반 → 데이터가 너무 빨리 바뀜(엣지 직후). 둘은 서로 다른 원인의 위반입니다.
타이밍의 두 부등식

setup·hold 식 — 면접 핵심 공식

Setup (max-delay)

Tclk ≥ Tcq + Tcombmax + Tsetup + Tskew

가장 느린 경로가 한 주기 안에 도착해야 함. 어기면 → 주기를 늘리거나(주파수↓) 경로를 줄인다.

Hold (min-delay)

Tcq + Tcombmin ≥ Thold + Tskew

가장 빠른 경로가 너무 일찍 도착하면 안 됨. 주파수와 무관 — 느려도 못 고침. 버퍼를 넣어 지연을 늘린다.

흔한 오답: "hold 위반은 클럭을 늦추면 풀린다" ❌. hold는 같은 엣지 기준 min-delay 문제라 주기와 무관합니다. 또 setup slack = Tclk − (Tcq+Tcomb+Tsu+Tskew)가 양수여야 timing closure. 음수 slack = 위반.

Tskew는 부호 있는 양(= capture clk 도착 − launch clk 도착)입니다. 위 +Tskew는 capture clk가 먼저 와 마진을 깎는 worst-case를 보수적으로 잡은 것. 반대로 capture clk가 늦게 오는 positive(useful) skew는 setup 마진을 늘려 주파수를 더 올릴 수 있습니다 — 다만 같은 부호가 hold는 악화시킵니다(위 hold 식의 +Tskew도 같은 보수적 관점). 그래서 STA 툴은 의도적으로 스큐를 조정하는 clock skew scheduling / useful skew를 씁니다.

FF vs Latch

엣지 트리거 vs 레벨 센서티브(투명성)

특성Flip-Flop (DFF)Latch
민감도클럭 엣지(edge)클럭/enable 레벨(level)
투명성없음 — 엣지에만 캡처투명(transparent) — enable=1 동안 D가 그대로 통과
타이밍 분석표준 STA로 깔끔time-borrowing 등 분석 어려움
면적/전력큼작음(트랜지스터 적음)
RTL에서의도적으로 추론대개 사고로 추론됨(위험)

FPGA/ASIC 동기 설계에선 기본적으로 FF만 씁니다. latch는 STA를 복잡하게 하고 글리치에 취약해 합성 리포트에서 "inferred latch" 경고가 뜨면 거의 항상 버그로 봅니다.

실제 코드 ①

비동기 리셋 DFF — 정석 템플릿

// 비동기 active-low 리셋, 동기 enable DFF
module dff_ar (input clk, rst_n, en, d, output reg q);
  always @(posedge clk or negedge rst_n) begin
    if (!rst_n)      q <= 1'b0;   // 리셋이 sensitivity에 있어야 비동기
    else if (en)     q <= d;
    // else 생략 OK: q는 자기값 유지(FF라 latch 아님)
  end
endmodule

posedge clk or negedge rst_n → 리셋은 클럭과 무관하게 즉시 걸림(asynchronous assert).

함정: 리셋을 sensitivity list에서 빼면(@(posedge clk)만) 동기 리셋이 됩니다 — 둘은 다른 회로. 또 =(blocking) 대신 순차 로직엔 반드시 <=(non-blocking)를 써야 시뮬↔합성 불일치를 막습니다.

실제 코드 ②

불완전 if/case → latch 추론 함정

// ❌ latch 추론됨
always @(*) begin
  if (sel) y = a;
  // else 없음 → sel=0일 때
  // y가 "이전 값 유지" = latch!
end
// ✅ 완전 분기 → 순수 조합
always @(*) begin
  y = b;        // 기본값 먼저
  if (sel) y = a;
end

조합 블록(always @(*))에서 모든 경로에 출력이 대입되지 않으면 합성기는 "값 유지"를 위해 latch를 만듭니다.

예방 3종: ① 기본값을 블록 맨 위에 대입 ② if엔 else, case엔 default ③ case는 모든 출력을 매 분기 대입. 리포트의 "Inferred latch" 경고를 절대 무시하지 마세요.

조합 루프(combinational loop): assign a = b; assign b = a;처럼 조합 출력이 자기 입력으로 되돌면 발진/X. 합성도 STA도 깨집니다. 모든 피드백은 반드시 FF를 거쳐야 합니다.

위험의 정체

메타스테이빌리티 — 0도 1도 아닌 상태

비동기 신호가 setup/hold 창을 어기면 FF 출력이 중간 전압에서 머뭇거리다 임의 시점에 0 또는 1로 떨어집니다. 이게 메타스테이빌리티.

  • 출력이 정해질 때까지 해결 시간(resolution time)이 걸림
  • 그 사이 다운스트림이 값을 읽으면 다른 FF가 0, 다른 FF가 1로 봄 → 시스템 불일치
  • 확률적 현상이라 "완전 제거"는 불가, 발생률을 낮춤
핵심: 결과가 0인지 1인지, 언제 정해질지 예측 불가. 그래서 비동기 입력은 "한 박자 늦더라도 안정될 시간을 준 뒤" 쓴다 — 이게 동기화기의 발상.
정량화

MTBF — 메타 안정성을 숫자로

MTBF = e^(tr/τ) / (T0 · fclk · fdata)

  • tr: 해결에 허용된 시간(동기화 FF 사이 여유) — 지수로 들어가 가장 강력
  • τ: FF의 시정수(metastability resolution time constant, 기술 의존)
  • T0: 메타 진입 윈도 폭, fclk: 샘플 클럭, fdata: 비동기 토글 빈도

tr가 분모가 아닌 지수라 한 박자(FF 하나)만 더 줘도 MTBF가 수십~수백만 배 좋아집니다. 그래서 동기화 FF를 1단 더 쌓는 게 효과적.

오답: "동기화기를 쓰면 메타가 사라진다" ❌. 첫 FF는 여전히 메타에 빠질 수 있습니다. 동기화기는 해결 시간을 벌어 두 번째 FF가 안정값을 잡을 확률을 키울 뿐 — 확률을 0이 아닌 충분히 낮은 MTBF로 만듭니다.

실제 코드 ③

2-FF 동기화기 — 1비트 CDC의 표준

// 비동기 1비트 → clk 도메인 동기화
module sync2 (input clk, rst_n, async_in,
              output sync_out);
  reg ff1, ff2;
  always @(posedge clk or negedge rst_n)
    if (!rst_n) {ff2, ff1} <= 2'b0;
    else       {ff2, ff1} <= {ff1, async_in};
  assign sync_out = ff2;   // 2단 뒤 안정값
endmodule

ff1은 메타 가능 → ff2가 한 박자 더 기다려 안정값만 내보냄.

single-FF CDC는 금지. FF 1단만 쓰면 메타가 그대로 로직으로 전파됩니다. 또 2-FF 동기화기는 1비트(단일 제어 비트)에만 유효 — 다비트 버스엔 못 씀(다음 장).

CDC와 해저드

다비트는 왜 2-FF로 안 되나

여러 비트를 각자 2-FF로 넘기면, 비트마다 메타 해결 시점이 달라 같은 엣지에 일부는 새 값, 일부는 옛 값으로 잡힙니다 → 비트 불일치(data incoherency).

예) 3'b011 → 3'b100 전이가 한 비트씩 어긋나면 111이나 000 같은 없던 값이 한 박자 보임.

다비트 CDC 처방

  • 그레이 코드 카운터: 전이마다 딱 1비트만 바뀜 → 어긋나도 ±1 (FIFO 포인터의 정석)
  • 핸드셰이크(req/ack): 데이터 안정 후 1비트 req만 동기화
  • 비동기 FIFO: 듀얼 클럭, 그레이 포인터로 full/empty 판정

면접 함정: "버스도 각 비트에 2-FF 박으면 되죠?" ❌. 그건 비트 정합성을 깨뜨립니다. 다비트 데이터는 한 비트만 변하게(그레이) 만들거나, 데이터를 고정한 뒤 1비트 제어로 넘기는 방식이어야 합니다.

리셋 설계

리셋 동기화 — async assert, sync deassert

리셋도 비동기로 풀면(deassert) 위험합니다. 풀리는 순간이 클럭 엣지의 recovery/removal 창을 어기면 FF가 메타에 빠집니다.

  • Assert는 비동기: 전원/사고 시 즉시·확실히 리셋
  • Deassert는 동기: 클럭에 맞춰 한꺼번에 풀어 메타·부분리셋 방지

recovery=리셋 deassert 후 다음 엣지까지 setup 격, removal=hold 격. 이 둘을 만족시키려 deassert를 동기화합니다.

// 리셋 동기화기: 비동기 인가, 동기 해제
module rst_sync(input clk, arst_n,
                output rst_n);
  reg r1, r2;
  always @(posedge clk or negedge arst_n)
    if (!arst_n) {r2,r1} <= 2'b0; // async 인가
    else        {r2,r1} <= {r1,1'b1};// sync 해제
  assign rst_n = r2;
endmodule

리셋 트리를 동기화 없이 한 큰 net으로 분배하면, 칩 곳곳에서 서로 다른 클럭 박자에 풀려 일부 FF만 리셋된 상태로 출발 → 재현 안 되는 버그.

FSM 인코딩

Moore vs Mealy · one-hot vs binary

구분선택지 A선택지 B

검증 엔지니어의 시선

타이밍·CDC를 어떻게 검증하나

🧩 무엇으로

  • STA(PrimeTime 등): setup/hold slack을 정적 분석 — 시뮬 아님
  • CDC 툴(SpyGlass-CDC, Conformal/Questa-CDC): 동기화 누락·재수렴(reconvergence) 자동 검출
  • SVA assertion: one-hot 불변식·핸드셰이크 규칙 검사
  • 게이트 시뮬에 SDF back-annotation으로 실제 지연 반영
// FSM one-hot 불변식 assertion
assert property (@(posedge clk) disable iff(!rst_n)
   $onehot(state));   // 항상 정확히 1비트 hot

// 메타 모델링: 시뮬에서 동기화 FF에
// 랜덤 1싸이클 지연 주입 → CDC 견고성 확인

CDC 버그는 RTL 시뮬에서 안 보이는 경우가 많습니다(0-지연 모델). 그래서 정적 CDC 툴 + 메타 주입(metastability injection)을 함께 돌립니다.

면접 심화 질문

여기까지 답하면 "타이밍을 닫아본 사람"

setup과 hold 부등식을 써보세요. hold 위반은 클럭을 늦추면 풀리나요?
setup: Tclk ≥ Tcq + Tcomb_max + Tsetup + Tskew. hold: Tcq + Tcomb_min ≥ Thold + Tskew. hold는 같은 엣지 기준 min-delay 문제라 주기와 무관 — 클럭을 늦춰도 안 풀립니다. 빠른 경로에 버퍼를 넣어 지연을 늘려야 합니다.
메타스테이빌리티가 뭐고, 2-FF 동기화기가 왜 효과적인가요? 완전히 없앨 수 있나요?
비동기 입력이 setup/hold를 어겨 FF 출력이 중간 전압에 머무는 현상입니다. MTBF에서 해결시간 t_r이 지수로 들어가, FF 한 단을 더 줘 t_r을 늘리면 MTBF가 기하급수적으로 커집니다. 다만 확률적 현상이라 0으로는 못 만들고, 충분히 낮은 발생률로 줄이는 것입니다.
다비트 버스를 다른 클럭 도메인으로 넘기려면? 그리고 리셋은 왜 동기화하나요?
버스는 각 비트에 2-FF를 박으면 비트 불일치가 생기므로 그레이 코드(전이당 1비트)나 핸드셰이크/비동기 FIFO를 씁니다. 리셋은 비동기 deassert가 recovery/removal을 어겨 메타·부분리셋을 일으키므로, async assert·sync deassert 방식으로 동기화합니다.
핵심 요약

타이밍·CDC 정밀 — 한 손에

  • setup: Tclk ≥ Tcq+Tcomb+Tsu+Tskew / hold: Tcq+Tcomb ≥ Th+Tskew
  • hold는 주기 무관(min-delay), slack≥0이어야 closure
  • FF=엣지, latch=레벨(투명)·사고추론 위험
  • 메타→MTBF의 tr은 지수: 2-FF로 해결시간 확보
  • 1비트=2-FF, 다비트=그레이/핸드셰이크/async FIFO
  • 리셋: async assert · sync deassert
  • FSM: Moore(상태) vs Mealy(상태+입력), one-hot vs binary

"동기 설계는 setup/hold 부등식으로 타이밍을 닫고, 비동기 경계는 메타스테이빌리티 MTBF를 충분히 키우는 동기화로 다룹니다. 검증은 시뮬이 아니라 STA·CDC 정적 분석 + assertion으로 합니다."
