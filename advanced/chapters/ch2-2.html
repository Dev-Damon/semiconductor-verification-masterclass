핵심: 검증 엔지니어는 RTL 시뮬레이터(VCS/Xcelium/Questa) 안에서 실제 CPU RTL(또는 ISS)이 명령어를 fetch/execute하게 만들고, 그 위에서 진짜 베어메탈 바이너리를 돌립니다. 가짜 자극이 아니라 "소프트웨어가 본 그대로"를 검증.

ISS(Instruction Set Simulator) = CPU의 빠른 C/C++ 행위 모델. RTL core보다 수십~수백배 빠르지만 사이클-정확하지 않음. bring-up 초기엔 RTL core, 회귀 가속엔 ISS(또는 하이브리드)를 씁니다.

툴체인 ①

크로스컴파일 — arm-none-eabi-gcc

# target triple: arm-none-eabi  (CPU-vendor-(no)OS-ABI)
# none = OS 없음(베어메탈), eabi = Embedded ABI
arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb \
    -ffreestanding -nostdlib -nostartfiles \
    -O2 -g -Wall \
    -T link.ld \                 # 링커 스크립트 지정
    startup.s main.c -o test.elf

# ELF에서 순수 메모리 이미지 추출 → Verilog 로드용 hex
arm-none-eabi-objcopy -O verilog test.elf test.hex
arm-none-eabi-objdump -d test.elf > test.dis   # 디스어셈블(디버깅)
freestanding/nostdlib/nostartfiles → 호스트 OS·libc·CRT 시작코드 없이 우리 startup만 쓴다는 뜻.

흔한 실수: 호스트 gcc로 빌드해 x86 바이너리를 만든 뒤 "왜 CPU가 안 도냐"고 함. 타깃이 Arm이면 크로스 툴체인이 필수. 또 -mthumb 빠뜨리면 ARM/Thumb 상태 불일치로 리셋 벡터에서 곧장 hard fault.

툴체인 ②

링커 스크립트 — 주소맵을 코드에 박는다

/* link.ld — SoC 메모리맵과 1:1 */
MEMORY {
  FLASH (rx)  : ORIGIN = 0x00000000, LENGTH = 256K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 64K
}
SECTIONS {
  .vectors : { KEEP(*(.vectors)) } > FLASH
  .text    : { *(.text*) }          > FLASH
  .rodata  : { *(.rodata*) }        > FLASH
  .data    : { *(.data*) } > RAM AT> FLASH  /* LMA≠VMA */
  .bss     : { *(.bss*)  } > RAM
  _estack = ORIGIN(RAM) + LENGTH(RAM);
}

VMA vs LMA: .data는 실행 시 RAM에 있어야 하지만(VMA=0x2000…), 초기값은 FLASH에 저장(LMA). AT>가 LMA를 정합니다. startup이 부팅 때 FLASH→RAM으로 복사하고 .bss를 0으로 클리어해야 C가 정상 동작.

링커 스크립트의 주소가 RTL 주소맵과 어긋나면 코드가 엉뚱한 곳에 놓여 fetch 실패. 벡터 테이블이 0x0에 안 오면 리셋 즉시 죽습니다.

로드 메커니즘

Frontdoor 부팅 vs Backdoor preload

Backdoor (preload)Frontdoor (bus)
방법$readmemh("test.hex", mem) — 메모리 배열에 직접 주입JTAG/부트로더가 버스 트랜잭션으로 한 워드씩 기록
속도즉시(0 시뮬타임)느림(실제 사이클 소모)
검증 범위메모리 내용만 — 버스·부트 경로 안 거침실제 부트 경로까지 검증
용도대부분의 C-test 회귀(빠르게)부트로더/플래시 컨트롤러 자체 검증
// TB에서 backdoor preload (계층 경로로 메모리에 직접)
initial begin
  $readmemh("test.hex", dut.u_soc.u_mem.ram);  // @주소 + 데이터워드
  $display("[TB] preload done");
end

대표 함정: backdoor preload는 부트 초기화(클럭/PLL/플래시 컨트롤러 설정)를 건너뜁니다. 실제 칩에선 부트로더가 해주던 일이 시뮬에선 안 되어, "시뮬 통과·실리콘 실패"의 단골 원인. 부트 경로는 frontdoor로 별도 검증해야 함.

레지스터 두드리기

베어메탈 C — 메모리맵 I/O

// 메모리맵 레지스터: volatile 필수 (컴파일러 최적화로 접근 제거 방지)
// SCRATCH = TB와 약속한 mailbox 주소
#define UART_BASE   0x40001000u
#define UART_TX     (*(volatile uint32_t *)(UART_BASE + 0x00))
#define UART_STAT   (*(volatile uint32_t *)(UART_BASE + 0x04))
#define SCRATCH     (*(volatile uint32_t *)0x4000F000u)

int main(void) {
    SCRATCH = 0x1;                    // TB에게 "테스트 시작"
    while (!(UART_STAT & 0x1)) { }     // TX FIFO 빌 때까지 폴링
    UART_TX = 'A';                    // 레지스터 write = 버스 트랜잭션

    volatile uint32_t *dst = (uint32_t *)0x20002000u;
    for (int i = 0; i < 16; i++) dst[i] = i * 4;  // DUT에 패턴 쓰기

    SCRATCH = 0xC0DE600D;             // 매직값 = PASS, TB가 폴링해서 종료
    for (;;) { }                      // spin (베어메탈엔 exit() 없음)
}

volatile 누락이 1순위 버그: 컴파일러가 "읽어도 안 바뀌는 값"으로 보고 폴링 루프를 무한루프로 최적화하거나 write를 통째로 삭제합니다. 또 캐시 있는 코어면 MMIO 영역은 device/non-cacheable로 매핑해야 진짜 버스로 나갑니다.

TB ↔ SW 동기

mailbox / scratch 레지스터로 손잡기

두 가지 관찰 방식: ① TB가 버스 모니터로 SCRATCH write 트랜잭션을 보거나 ② backdoor로 메모리 배열을 직접 poll. 보통 0xC0DE600D(PASS)/0xBAADxxxx(FAIL) 같은 매직값 프로토콜을 정해둡니다.

캐시 일관성: CPU가 SCRATCH를 캐시에 쓰고 플러시 안 하면 TB(메모리쪽)는 옛 값을 봅니다. mailbox 영역은 non-cacheable로 두거나, write 후 DSB/캐시 클린을 넣어야 함.

DPI-C ①

import "DPI-C" — SV가 C 함수를 호출

// ── C 쪽 (model.c) : SV가 부를 함수를 구현
#include "svdpi.h"
int ref_crc32(const unsigned char *data, int len) {
    unsigned int crc = 0xFFFFFFFFu;
    /* ... 참조 모델 계산 ... */
    return (int)~crc;
}

// ── SV 쪽 : C 함수를 import 하면 일반 함수처럼 호출 가능
import "DPI-C" function int ref_crc32(input byte data[], input int len);

initial begin
  int exp = ref_crc32(packet, packet.size());  // C가 골든 레퍼런스
  if (dut_crc !== exp) $error("CRC mismatch");
end
import = "SV → C로 들어간다". C가 검증의 골든 모델/체커/스코어보드 역할.

SV↔C 타입 매핑: SV int↔C int, byte↔char, bit(2-state)↔비트벡터, logic(4-state)는 svLogicVecVal로. 배열·open array는 svdpi.h의 svOpenArrayHandle API로 접근.

DPI-C ②

export "DPI-C" + context / pure

// export: C가 거꾸로 SV task/function 호출
export "DPI-C" task sv_drive;
task sv_drive(input int v);
  ... @(posedge clk); bus.send(v);
endtask

// import + context: C 안에서 export된 SV를 부르려면 필수
import "DPI-C" context task c_run();
// C 쪽: import한 c_run 안에서 export된 sv_drive 호출
extern void sv_drive(int v);   // export된 SV
void c_run(void) {
    for (int i=0;i<4;i++) sv_drive(i*16);
}

import vs export: import=SV가 C를 부름, export=C가 SV를 부름. 둘이 합쳐져야 양방향 co-sim.

  • context: 그 C 함수가 SV 컨텍스트(인스턴스 위치)를 알아야 할 때 — export 호출·svGetScope·시간소비에 필수.
  • pure: 출력이 입력에만 의존하고 side-effect/시간소비 없음 → 시뮬레이터가 호출 최적화 가능.

함정: side-effect 있는 함수에 pure를 붙이면 시뮬레이터가 호출을 합치거나 생략해 디버깅 지옥. 그리고 시간을 소비하는 건 task만 가능(function은 0-time).

C-test vs UVM — 자극의 레이어가 다르다

UVM (IP/블록)C-test (SoC/시스템)
자극 주체외부 BFM/agent가 핀을 흔듦CPU가 실행하는 코드가 자극
관점프로토콜·핀 레벨 정밀"소프트웨어가 본" 시스템 동작

약점전체 SoC 시나리오 표현이 장황핀 레벨 코너 자극이 어려움(느림)

실무 결론: IP 단위는 UVM, 통합·시스템 시나리오는 C-test가 정석. 둘은 경쟁이 아니라 레이어입니다. 종종 C-test가 mailbox로 TB를 트리거하고 UVM agent가 외부 인터페이스를 흔드는 혼합 구조를 씁니다.

한 걸음 더

PSS — 한 모델, 여러 플랫폼

PSS(Portable Stimulus Standard, Accellera)는 테스트 의도(시나리오)를 추상적으로 한 번 기술하면, 도구가 여러 타깃(시뮬·에뮬·실리콘)용 자극을 자동 생성하는 표준입니다.

  • 핵심 단위: action, activity, component, resource pool
  • 제약(constraint)·스케줄링·자원 충돌을 그래프로 풀어 합법 시나리오 산출
  • 같은 모델 → UVM 시퀀스, C-test, 에뮬 자극으로 컴파일
// PSS 개념 스케치 (DSL)
component dma_c {
  action xfer {
    rand bit[31:0] src, dst, len;
    constraint { len in [4..4096];
                 src % 4 == 0; }
  }
}
// activity: 여러 action을 엮어 시나리오

한 줄 정의: "테스트 의도를 한 번 모델링해 여러 플랫폼용 자극으로 재사용(portable)하는 Accellera 표준." 이 한 문장이 면접 정답.

검증 엔지니어의 시선

C-test/co-sim을 어떻게 검증하나

🧩 무엇으로

  • End-of-test 프로토콜: mailbox 매직값(PASS/FAIL) + 타임아웃 watchdog
  • C 골든모델을 DPI import로 SV 스코어보드에 연결
  • RTL core ↔ ISS 비교(lockstep): PC·레지스터·메모리 트레이스 일치 검사
  • 버스 트랜잭션 SVA로 프로토콜 위반 즉시 검출

🎯 무엇을(커버리지)

  • 부팅·리셋·인터럽트·예외 경로
  • 드라이버 시퀀스·IP 간 데이터 흐름(DMA→메모리→IP)
  • frontdoor 부트 경로(backdoor와 별도)
  • endianness·정렬·캐시 클린/인밸리데이트 코너

endianness 함정: C가 uint32_t로 쓴 워드와 TB가 $readmemh로 본 바이트 순서가 다르면 같은 데이터를 다르게 해석합니다. Arm은 보통 little-endian — TB 체크/HEX 변환 시 바이트 순서를 반드시 맞춰야 함.

면접 심화 질문

여기까지 답하면 "SoC 검증자"로 보인다

DPI-C의 import와 export 차이는?
import "DPI-C"는 SV가 C 함수를 호출하는 방향(골든모델/체커), export "DPI-C"는 C가 거꾸로 SV의 task/function을 호출하는 방향입니다. C 안에서 export된 SV를 부르거나 SV 컨텍스트가 필요하면 import에 context를, side-effect 없는 순수 계산이면 pure를 붙입니다. 시간을 소비하는 건 task만 가능합니다.
베어메탈 C 테스트는 TB와 어떻게 동기·종료하나요?
메모리맵에 약속한 mailbox/scratch 주소를 둡니다. C가 시작·완료를 매직값으로 쓰고(예: 0xC0DE600D=PASS), TB는 버스 모니터나 backdoor로 그 값을 폴링해 $finish합니다. 무한 hang 방지용 watchdog 타임아웃을 함께 둡니다. 단, mailbox는 non-cacheable로 두거나 캐시를 플러시해야 일관성이 유지됩니다.
언제 C-test, 언제 UVM을 쓰나요?
IP/블록 단위의 프로토콜·코너·제약랜덤은 UVM이 강하고, 부팅·드라이버·여러 IP가 얽힌 시스템 시나리오는 CPU가 코드를 실행하는 C-test가 적합합니다. 경쟁이 아니라 레이어가 다른 도구라, 보통 C-test가 시나리오를 몰고 UVM agent가 외부 인터페이스를 흔드는 혼합으로 씁니다.
핵심 요약

C-test · DPI · bring-up — 한 손에

  • 빌드: arm-none-eabi-gcc + 링커 스크립트(VMA/LMA, 주소맵 1:1)
  • 로드: backdoor $readmemh(빠름, 부트 스킵) vs frontdoor(실제 부트 경로)
  • 동기: 메모리맵 mailbox/scratch + 매직값 PASS/FAIL + watchdog
  • co-sim: import(SV→C) / export(C→SV), context·pure
  • 선택: IP=UVM, SoC 시나리오·부팅=C-test, 의도 재사용=PSS
  • 함정: volatile 누락 · 캐시 일관성 · endianness · backdoor가 부트 init 스킵

"SoC 검증은 진짜 CPU가 진짜 베어메탈 바이너리를 돌리게 만드는 일입니다. 크로스컴파일·링커로 빌드하고, frontdoor/backdoor로 로드하고, mailbox로 TB와 손잡고, DPI-C로 양방향 co-sim을 엮습니다."
