기준 스펙: IEEE 1364 (Verilog, specify·타이밍체크) + IEEE 1497 (SDF, Standard Delay Format). GLS는 post-synth와 post-PnR 두 단계에서 돌리며, 후자는 실제 배선 지연(SDF)을 어노테이트합니다.

언제·왜 돌리나

GLS의 3가지 모드

모드지연SDF주로 잡는 것
zero-delay0 (functional)없음합성 후 기능 동치, 리셋/초기화, X 전파
unit-delay게이트당 1 단위없음이벤트 순서·간이 레이스 확인
full-timingSDF 실제값있음타이밍 위반·glitch·async 경로·DFT 시프트
실무 순서: 보통 post-synth zero-delay로 기능·리셋부터 깔끔히 잡고 → post-PnR full-timing(SDF)로 넘어갑니다.

full-timing GLS는 느립니다(이벤트 폭증). 그래서 전체 회귀가 아니라 리셋·모드전환·DFT·async FIFO 같은 핵심 시퀀스만 돌리는 게 일반적입니다.

지연을 주입한다

$sdf_annotate — SDF를 네트리스트에 입히기

// testbench 또는 wrapper의 initial 블록에서 호출
initial begin
  $sdf_annotate(
    "./sdf/cpu_top.max.sdf",  // ① SDF 파일
    dut,                       // ② 어노테이트할 스코프(인스턴스)
    ,                          // ③ config file (보통 생략)
    "sdf_anno.log",           // ④ 로그 파일
    "MAXIMUM",                  // ⑤ 코너: MIN|TYP|MAX 중 하나 선택
    ,                          // ⑥ scale_factors "1.0:1.0:1.0"
    "FROM_MTM"                  // ⑦ scale_type
  );
end

SDF 한 항목 예: (IOPATH A Y (0.21:0.34:0.51) (0.19:0.30:0.47)) → (min:typ:max), 앞=rise, 뒤=fall.

⑤에서 MAXIMUM을 고르면 SDF의 세 값 중 max만 골라 setup 위반에 민감하게, MINIMUM은 빠른 경로(hold 위반)에 민감하게 시뮬합니다.

SDF 어노테이트 누락이 1순위 함정: 호출이 빠지거나 인스턴스 경로가 틀리면 전 경로가 zero-delay가 되어 race가 사라지고 "통과"로 위장됩니다. 반드시 sdf_anno.log에서 annotated count를 확인하세요.

코너의 정확한 의미

min / typ / max — 세 숫자가 말하는 것

SDF의 모든 지연은 (min:typ:max) 삼중값입니다. 이는 PVT(Process·Voltage·Temperature) 코너의 산포를 담습니다.

코너대략 조건지연주로 위반
MIN (fast)fast-process, 고전압, 저온가장 짧음hold(데이터가 너무 빨리 옴)
TYPnominal중간참고용
MAX (slow)slow-process, 저전압, 고온가장 김setup(데이터가 너무 늦게 옴)

흔한 오해: "max 코너만 돌리면 된다" ❌. hold 위반은 min(fast) 코너에서 드러나고, 게다가 hold는 전압을 낮춰도 잘 안 풀려 전압 무관(VT-invariant)에 가깝습니다. setup은 MAX, hold는 MIN으로 둘 다 봐야 합니다.

타이밍체크의 심장

specify 블록 — $setuphold 실제 문법

module DFF (Q, D, CK, RN);   // 라이브러리 셀의 timing 모델(.v)
  ...
  specify
    // (조건 ?=> ) 데이터 경로 지연: CK↑ → Q
    (CK => Q) = (0.12:0.18:0.27);

    // setup/hold를 한 번에: ref=CK↑, data=D
    $setuphold(posedge CK, D, 0.05, 0.03, notifier);
    //           ref        data tSU   tH   ↑위반시 토글

    // 비동기 리셋 해제 타이밍
    $recovery(posedge RN, posedge CK, 0.06, notifier);
    $removal (posedge RN, posedge CK, 0.04, notifier);

    // 최소 펄스폭
    $width(posedge CK, 0.20, 0, notifier);
  endspecify
endmodule

SDF의 (TIMINGCHECK (SETUPHOLD ...)) 값이 위 0.05/0.03 자리에 어노테이트되어 덮어쓰입니다.

데이터 경로 지연(=>)과 타이밍체크($...)는 같은 specify 블록 안에 함께 산다 — 둘 다 SDF가 채웁니다.
setup / hold 윈도우

체크 메커니즘 — 클럭엣지 기준 한 점이 아닌 "창"

메커니즘: 시뮬레이터는 ref 엣지(CK↑) 시각을 기준으로 [-tSU, +tH] 윈도우를 잡고, 그 구간에 data 신호 변화가 있으면 위반으로 판정합니다. 위반 시 notifier 레지스터가 토글되고, 셀 모델은 이를 보고 Q를 X로 강제합니다(보수적 처리).

async 전용 체크

$recovery / $removal — 리셋 해제 타이밍

⏪ $recovery

비동기 리셋이 해제(deassert)된 뒤 다음 클럭 엣지까지 최소 시간. setup의 async 버전 — "너무 늦게 풀리면" 안 됨.

⏩ $removal

클럭 엣지 이후 리셋이 유지돼야 하는 최소 시간. hold의 async 버전 — "너무 일찍 풀리면" 안 됨.

리셋을 비동기로 걸되 동기로 해제하는 reset synchronizer가 필요한 이유가 바로 이 두 체크입니다. 해제 시점이 클럭 엣지와 겹치면 플롭이 metastable해질 수 있습니다. GLS full-timing은 $recovery/$removal 위반으로 이를 잡아냅니다.

$width 위반(클럭/리셋 펄스가 SDF 최소폭보다 짧음)은 클럭 게이팅 셀(ICG) 주변에서 자주 터집니다 — 게이팅 enable이 늦게 떠 클럭 펄스가 깎이는 케이스.

GLS 1순위 골칫거리

X-pessimism vs X-optimism

구분X-pessimism (비관)X-optimism (낙관)
방향실제론 결정될 값을 X로 과하게 전파실제 X여야 할 곳을 0/1로 덮어버림
원인같은 X 소스가 양 입력에 들어가도 시뮬은 모름 (X & ~X → X)RTL의 case/3항/우선순위가 X를 0·1로 매핑
위험도가짜 X 범람 → 디버그 시간 낭비버그 은폐 → 실리콘에서 터짐(더 위험)

X-pessimism 범람: 리셋 안 된 플롭 하나의 X가 트리 전체로 번져 화면이 X 바다가 됩니다. 진짜 원인 한 곳을 찾기 어려워짐 → 리셋 커버리지와 $display 트레이스로 소스부터 차단.

대응: 게이트 GLS는 X-pessimism, RTL은 X-optimism 경향. 그래서 RTL에서 통과한 X가 GLS에서 터지는 게 정상이며, 이를 위해 GLS를 돕니다. $assertoff가 아니라 X-prop 모드(시뮬레이터의 Xprop)를 켜 RTL의 낙관도 줄입니다.

리셋·초기화의 함정

RTL엔 있던 initial이 게이트엔 없다

RTL의 initial/변수 초기값은 합성되지 않습니다. 게이트 네트리스트의 모든 플롭은 시작 시 X이고, 리셋이 실제로 모든 플롭에 도달해야만 값이 정해집니다.

// 리셋이 없는 플롭(자유 실행 카운터 등)을 GLS에서 깨우는 흔한 기법
initial begin
  $display("force init at t=%0t", $time);
  force dut.cnt_reg.Q = 1'b0;   // X를 0으로 강제
  #5 release dut.cnt_reg.Q;       // 이후 정상 동작에 맡김
end

리셋 미도달이 GLS 3순위 함정: RTL에선 변수 초기값 덕에 멀쩡했는데, 게이트에선 그 플롭이 X로 남아 다운스트림이 전부 X. "RTL은 통과인데 GLS만 X"의 90%는 리셋 누락 + initial 비합성 조합입니다.

정적 vs 동적

STA vs GLS — 무엇을 커버하나

축STA (정적 타이밍 분석)GLS (게이트 시뮬)
방식자극 없이 모든 경로 수식 계산자극(테스트)으로 실제 토글시켜 관찰
커버리지경로는 전부, 단 자극받은 값 무관자극이 닿은 경로·시퀀스만
강점setup/hold 슬랙을 전수, 빠름기능+타이밍 동시, X 전파, 동적 동작
약점기능·X·리셋·async를 못 봄, false path 수동 처리느림, 자극 안 닿으면 못 봄
대표 잡이경로 지연, 슬랙, 클럭 스큐리셋, DFT 시프트, async FIFO, glitch, X

핵심: 둘은 경쟁이 아니라 상보(complementary)입니다. STA는 "모든 경로의 타이밍 마진"을, GLS는 "실제 자극에서의 기능+타이밍 동작"을 봅니다. STA가 못 보는 multicycle/false path의 진짜 동작, X 전파, 리셋 도달, 비동기 도메인 교차를 GLS가 메웁니다.

DFT 동작 확인

GLS에서 scan / DFT 패턴 검증

스캔 체인은 RTL에 없고 합성·삽입(DFT) 후에야 생깁니다. 그래서 ATPG 패턴의 동작은 게이트 레벨에서만 검증할 수 있습니다.

  • scan shift: scan_en=1로 체인을 통해 패턴 시프트인/아웃 — 체인 연결·순서 확인
  • capture: scan_en=0 한 클럭, 조합 응답을 캡처
  • at-speed(transition): 캡처 구간만 빠른 클럭 → full-timing GLS로 타이밍까지 확인

ATPG가 만든 패턴을 실제 SDF 지연으로 GLS 재현해 "시뮬-실리콘 불일치"를 사전에 잡습니다. 특히 at-speed 패턴은 capture 윈도우의 setup이 빡빡해 full-timing이 필수입니다.

scan shift는 보통 저속인데 SDF max로 돌리면 hold 위반이 보일 수 있음 — DFT는 shift 시 hold-safe로 설계하므로, GLS에서 위반이 뜨면 설계 미스 신호입니다.

검증 엔지니어의 시선

GLS를 어떻게 검증·운용하나

🧩 환경·자극

  • RTL 시뮬과 동일 TB 재사용(UVM도 게이트 DUT에 붙임)
  • $sdf_annotate + Xprop 모드 ON
  • 리셋·모드전환·DFT·async 시퀀스를 핀포인트 자극

🎯 무엇을 체크

  • SDF annotated count가 기대치인지(누락 0)
  • 타이밍 위반($setuphold 등) 로그 0건
  • X 잔존 0 — 리셋 후 모든 관측점 비-X
  • RTL vs 게이트 출력 비교(동치성)

SVA assertion은 게이트에서도 동작합니다. 단 $setuphold 같은 셀 내부 체크는 라이브러리 모델이 하고, 프로토콜·기능 체크는 TB의 SVA가 합니다. 회귀는 "위반 0 + X 0 + 동치 PASS"를 게이트로 통과해야 sign-off에 가깝습니다.

면접 심화 질문

여기까지 답하면 "실무자"로 보인다

SDF의 코너(min:typ:max)가 뭐고, setup/hold 검증과 어떻게 연결되나요?
SDF의 모든 지연은 (min:typ:max) 삼중값으로 PVT 산포를 담습니다. $sdf_annotate에서 MAX(slow)를 고르면 경로가 길어져 setup 위반에, MIN(fast)을 고르면 데이터가 빨라져 hold 위반에 민감합니다. 그래서 setup은 MAX, hold는 MIN으로 둘 다 돌립니다. hold는 전압을 낮춰도 잘 안 풀려 별도 코너가 필요합니다.
게이트 시뮬에서 setup/hold 위반은 어떻게 검출·표현되나요?
라이브러리 셀의 specify 블록에 $setuphold(posedge CK, D, tSU, tH, notifier)가 있고, 시뮬레이터가 CK 엣지 기준 [-tSU,+tH] 윈도우 안에서 D 변화를 감지하면 위반으로 판정합니다. 위반 시 notifier 레지스터가 토글되고 셀 모델이 출력 Q를 X로 강제해 보수적으로 전파합니다.
STA를 다 했는데 왜 또 GLS를 돌리나요? X-pessimism은요?
STA는 자극 없이 모든 경로의 타이밍 마진은 보지만, 기능·X 전파·리셋 도달·비동기 교차·DFT 동작·initial 비합성 문제는 못 봅니다. GLS는 실제 자극으로 그걸 메웁니다. X-pessimism은 같은 X 소스가 상쇄될 경로도 시뮬이 X로 과하게 전파하는 비관적 현상으로, 리셋 누락 한 곳이 X 바다를 만들곤 합니다. 반대로 X-optimism은 X를 0/1로 덮어 버그를 은폐하므로 더 위험하며, Xprop 모드로 줄입니다.
핵심 요약

GLS·SDF·타이밍 — 한 손에

  • GLS 모드: zero / unit / full-timing(SDF). 기능은 zero, 타이밍은 full
  • $sdf_annotate(file, scope, …, "MAXIMUM"/"MINIMUM", …)
  • SDF = (min:typ:max); setup↔MAX, hold↔MIN
  • specify: $setuphold/$width/$recovery/$removal + notifier → Q=X
  • X-pessimism(과전파) vs X-optimism(은폐, 더 위험)
  • RTL initial 비합성 → 리셋 도달 필수, force/release
  • STA=전경로 정적, GLS=자극 동적 — 상보

"GLS는 SDF로 실제 지연을 입힌 게이트 네트리스트를 자극해, STA가 못 보는 리셋·X 전파·async·DFT를 잡습니다. setup은 MAX, hold는 MIN 코너로 돌리고, 위반은 notifier가 Q를 X로 만들어 알립니다."
