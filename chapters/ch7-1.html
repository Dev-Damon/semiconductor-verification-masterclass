좋은 소식: 당신은 이미 Git을 안다. 이번엔 새 도구를 배우는 게 아니라, "산출물이 무겁고, 잘못 머지하면 수십억짜리 칩이 잘못 나간다"는 무게의 차이만 익히면 됩니다.

왜 배우나 · 한 문장 정의

"RTL도 결국 코드다" — 그래서 하드웨어 팀도 Git을 쓴다

RTL(Verilog/SystemVerilog)과 검증 코드(UVM testbench)는 텍스트 소스입니다. 텍스트인 이상 버전 관리·리뷰·브랜치가 그대로 필요합니다.

다만 두 가지가 다릅니다. ① 함께 굴러다니는 산출물이 거대합니다(파형, 라이브러리, 넷리스트가 수백 MB~수 GB). ② 빌드 산출물이 소프트웨어처럼 "다시 배포"되는 게 아니라 물리적 실물 칩으로 굳어버립니다 — 한 번 제조하면 못 고칩니다.

RTL 버전관리재현성(reproducibility) .gitignoreGit LFS브랜치 전략 코드 리뷰tape-out tag서브모듈/IP 통합 Perforce / SVN
면접에서 "Git 쓸 줄 아냐"가 아니라, "하드웨어 팀의 무게를 이해하느냐"를 봅니다. 그 차이가 이 챕터의 전부입니다.
개발자 직관으로 번역

당신은 이미 다 안다 — 단지 단어만 바꿔 끼우면 된다

당신이 SW에서 하던 그대로, 매핑만 갈아끼우세요.

당신의 SW 세계하드웨어 팀
소스 코드 (.py/.js)RTL (.v/.sv) · UVM 테스트벤치
대용량 에셋(이미지/모델) → Git LFS파형(FSDB)·라이브러리·넷리스트 → LFS
릴리스 v1.2.0 태깅tape-out 스냅샷 태깅
CI 통과해야 머지회귀(regression) 통과해야 머지
빌드 산출물 = 배포 가능빌드 산출물 = 실물 칩(못 고침)

모노레포를 운영해 본 경험이 그대로 통합니다.

  • 여러 IP(CPU·GPU·메모리 컨트롤러)가 각자 repo → SoC repo가 서브모듈로 묶음
  • 생성물은 절대 커밋 안 함 → .gitignore
  • 꼭 버전 관리할 큰 바이너리만 → LFS

즉 새 워크플로를 배우는 게 아니라, 당신의 좋은 습관을 "칩 무게"에 맞춰 더 엄격하게 적용하는 것뿐입니다.

핵심 개념 ① · 무엇을 넣고 무엇을 빼나

소스는 Git, 큰 바이너리는 LFS, 생성물은 .gitignore

가장 흔한 사고는 생성물을 통째로 커밋하는 것입니다. 파형 한 번에 GB 단위라 repo가 순식간에 부풀어 clone이 불가능해집니다.

판단 기준 한 줄: "사람이 손으로 썼나(→Git), 다시 못 만드는 큰 바이너리인가(→LFS), 명령 한 번에 재생성되나(→ignore)"
핵심 개념 ② · Git LFS

대용량 파일은 어떻게? — "포인터만 커밋"하는 LFS

Git은 텍스트의 줄 단위 diff엔 천재지만, GB짜리 바이너리엔 약합니다. 매 커밋마다 통째로 새 사본을 저장해 히스토리가 폭발하죠.

Git LFS(Large File Storage)는 실제 큰 파일은 별도 서버에 두고, repo 안에는 작은 텍스트 포인터(해시)만 커밋합니다. checkout할 때 필요한 버전만 내려받습니다.

  • repo는 가벼워지고 clone이 빨라짐
  • 버전별로 어떤 큰 파일이 쓰였는지 이력은 그대로 남음
  • SW의 이미지·ML 가중치 관리와 완전히 같은 도구·같은 명령
# 어떤 패턴을 LFS로 다룰지 등록
git lfs track "*.lib" "*.fsdb" "*.db"

# .gitattributes에 규칙이 기록됨 → 이건 커밋
git add .gitattributes

# 큰 파일은 포인터로 커밋됨 (실파일은 LFS 서버)
git add models/ref_model.db
git commit -m "add ref model"

정확히 SW에서 대용량 에셋·ML 모델을 LFS로 다루던 그 방식입니다. 파일 종류만 .png → .fsdb로 바뀌었을 뿐.

주의: LFS는 "꼭 보존해야 하는 입력 자산"용입니다. 매번 재생성되는 파형·로그는 LFS가 아니라 .gitignore로 빼야 합니다 — 안 그러면 LFS 서버까지 부풀어 버립니다.

핵심 개념 ③ · 재현성

특정 커밋 = 특정 칩의 RTL 스냅샷

SW에서 "이 커밋으로 빌드하면 이 바이너리가 나온다"는 재현성을 챙기듯, 하드웨어 팀에선 "이 커밋 = 이 시점의 칩 설계 그 자체"입니다. 버그 리포트가 오면 그 커밋으로 checkout해 똑같은 상태를 재현합니다.

🔁 왜 결정적이어야 하나

같은 RTL + 같은 테스트 + 같은 시드(seed) = 같은 결과여야 합니다. 그래야 "어제 실패한 그 케이스"를 오늘 똑같이 재현해 고칠 수 있습니다. 재현 안 되는 버그는 못 잡습니다.

SW의 lockfile(package-lock·go.sum)로 의존성을 못 박는 감각과 같습니다. 커밋 SHA가 "이 칩은 이 코드로 만들어졌다"를 못 박는 락(lock)인 셈이죠.

핵심 개념 ④ · 협업 워크플로

브랜치 · 코드 리뷰 · 회귀 결과를 커밋에 연결

🌿 브랜치 전략

  • IP별 브랜치: CPU팀·메모리팀이 각자 작업
  • release / stable 브랜치: tape-out 후보가 모이는 곳
  • feature 브랜치 → 리뷰 → main 머지 (SW와 동일)

규모 큰 SoC는 IP마다 별도 repo로 쪼개고 상위에서 통합하는 게 일반적입니다.

👀 코드 리뷰

RTL 리뷰는 SW PR 리뷰보다 무게가 큽니다. 잘못 머지된 한 줄이 실리콘에 그대로 굳어 리스핀(re-spin) 비용 수억~수십억으로 돌아오니까요.

  • 합성 가능성, 타이밍, 클럭 도메인까지 본다
  • 2인 이상 승인 + 회귀 통과를 머지 게이트로 강제

SW의 "CI 초록불 + 리뷰 승인 = 머지"와 정확히 같은 게이트. 다만 CI 자리에 회귀(regression)가 들어갑니다 — 특정 커밋의 회귀 결과를 항상 추적 가능하게 묶어 둡니다.
핵심 개념 ⑤ · 출하 스냅샷 고정

tape-out은 git tag로 박제한다

tape-out(설계를 제조 공장에 넘기는 순간)은 절대 흔들리면 안 되는 시점입니다. 그래서 정확히 그 상태를 tag로 못 박아, 언제든 그 칩의 소스로 되돌아갈 수 있게 합니다.

# tape-out 스냅샷을 영구 고정
git tag -a tapeout-A0 -m "ChipX A0 to fab"
git push origin tapeout-A0

# 1년 뒤, 그 칩과 100% 동일한 RTL 복원
git checkout tapeout-A0

실리콘에서 버그가 나오면 이 태그로 돌아가, 출하된 칩과 똑같은 RTL에서 디버깅합니다.

🧩 여러 IP repo 통합

SoC는 보통 여러 repo의 합입니다. 상위 repo가 각 IP를 서브모듈로 가리키되 특정 커밋에 핀(pin) 고정합니다.

  • tape-out 시: 모든 서브모듈 커밋이 함께 고정됨
  • = "이 칩은 CPU IP의 이 커밋 + 메모리 IP의 저 커밋"으로 완전 명세

SW의 모노레포/서브모듈·고정 의존성과 같은 그림입니다.

SW의 릴리스 태깅(v1.2.0) 감각 그대로입니다. 차이는 단 하나 — 이 릴리스의 "빌드 산출물"은 다시 배포 가능한 바이너리가 아니라 되돌릴 수 없는 실물 칩이라는 무게.

현실 · 왜 아직도 Perforce?

일부 반도체 팀은 여전히 Perforce / SVN을 쓴다

Git이 표준이 되어가지만, 큰 반도체 회사 상당수는 Perforce(P4)·SVN·과거엔 ClearCase를 씁니다. "낡아서"가 아니라 하드웨어 워크플로에 더 잘 맞는 점이 있어서입니다.

관점Git (분산)Perforce / SVN (중앙집중)
저장소 모델전체 히스토리를 각자 복제중앙 서버에 보관, 필요한 것만 받음
초대용량 자산LFS 같은 보조 장치 필요TB급 단일 저장소를 기본으로 잘 다룸
권한repo/브랜치 단위 위주파일·폴더 단위 세밀한 권한
바이너리 충돌머지 충돌 위험파일 락(lock)으로 동시 편집 차단

핵심 직관: 머지가 불가능한 거대 바이너리(레이아웃·라이브러리)는 "두 사람이 동시에 고치면 합칠 방법이 없다" → 그래서 선점 락이 있는 중앙집중형이 유리합니다.

게임 업계가 대용량 에셋 때문에 Perforce를 쓰는 것과 같은 이유입니다. "분산이 항상 정답은 아니다 — 자산 특성이 도구를 정한다"가 면접에서 빛나는 한마디.

실전 · 한 장 체크리스트

하드웨어 repo, 이것만 지키면 사고 안 난다

✅ 넣고 빼기

  • RTL·테스트벤치·스크립트 → Git
  • 꼭 보존할 큰 바이너리 → LFS
  • 파형·로그·시뮬 빌드 → .gitignore
  • 절대 생성물 통째 커밋 금지

✅ 협업·출하

  • 회귀 통과 + 리뷰 승인 = 머지 게이트
  • 회귀 결과를 커밋 SHA에 연결
  • tape-out은 tag로 영구 고정
  • 서브모듈 커밋까지 함께 핀 고정

한 줄 멘탈 모델: "소스는 가볍게(Git), 자산은 똑똑하게(LFS), 출하는 못 박게(tag) — 모든 커밋이 어떤 칩이었는지 추적 가능해야 한다."

면접 예상 질문

이렇게 물어보면, 이렇게 답한다

왜 RTL을 Git으로 관리하나요? 대용량 파일은 어떻게 다루나요?
RTL과 검증 코드는 결국 텍스트 소스라 버전 관리·리뷰·브랜치·재현성이 그대로 필요하기 때문입니다. 다만 파형·라이브러리·넷리스트 같은 큰 바이너리가 함께 다니는데, 매번 재생성되는 생성물은 .gitignore로 빼고, 꼭 보존할 큰 입력 자산만 Git LFS로 둡니다. LFS는 실제 파일을 별도 서버에 두고 repo엔 포인터만 커밋해 저장소를 가볍게 유지합니다 — SW에서 대용량 에셋·ML 모델을 다루던 방식과 같습니다.
tape-out 시 버전 관리는 어떻게 하나요?
tape-out 시점의 정확한 상태를 git tag로 영구 고정합니다. 그러면 특정 커밋 = 특정 칩의 RTL 스냅샷이 되어, 1년 뒤 실리콘에서 버그가 나와도 그 태그로 checkout해 출하된 칩과 100% 동일한 RTL에서 디버깅할 수 있습니다. SoC는 여러 IP repo의 합이라 서브모듈로 묶고, tape-out 때 각 서브모듈 커밋까지 함께 핀 고정해 칩 구성 전체를 명세합니다.
반도체 팀이 Git 대신 Perforce를 쓰기도 하는 이유는?
초대용량 자산과 워크플로 특성 때문입니다. Perforce/SVN 같은 중앙집중형은 TB급 단일 저장소를 기본으로 잘 다루고, 파일·폴더 단위의 세밀한 권한 제어가 가능하며, 머지가 불가능한 거대 바이너리에 대해 파일 락(lock)으로 동시 편집을 막아줍니다. 게임 업계가 대용량 에셋 때문에 Perforce를 쓰는 것과 같은 이유로, 자산 특성이 도구를 결정한다고 답하면 좋습니다.
핵심 요약

이 챕터, 한 손에 잡기

  • RTL·검증 코드는 텍스트 → Git의 버전관리·리뷰·재현성이 그대로 필요
  • 생성물(파형·로그)은 .gitignore, 보존할 큰 자산만 LFS
  • 특정 커밋 = 특정 칩의 RTL 스냅샷 → 결정적 재현
  • 회귀 통과 + 리뷰 승인 = 머지 게이트, 결과를 커밋에 연결
  • tape-out은 tag로 영구 고정, 서브모듈 커밋까지 핀
  • 초대용량·세밀권한·파일락 때문에 Perforce/SVN을 쓰기도

"RTL도 코드라 Git으로 관리하지만, 빌드 산출물이 실물 칩인 만큼 더 엄격합니다 — 큰 자산은 LFS, 생성물은 ignore, tape-out은 tag로 못 박아 모든 커밋이 어떤 칩이었는지 추적되게 합니다."

— "당신이 아는 Git에, 칩의 무게만 더했다"고 말하면 면접관이 끄덕입니다.
