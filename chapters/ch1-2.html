Part 1 · 언어

SystemVerilog
Verilog에 OOP와 테스트를 더하다

Verilog가 "회로를 그리는 언어"였다면, SystemVerilog는 거기에 본격적인 객체지향과 테스트 기능을 통째로 내장한 슈퍼셋입니다. 검증 엔지니어의 진짜 무기가 여기서 시작됩니다.

한 문장 정의

SystemVerilog = Verilog + OOP + 테스트 프레임워크

SystemVerilog(SV)는 Verilog의 상위호환(superset)입니다. 기존 Verilog 코드는 거의 그대로 돌아가고(SV가 새로 추가한 예약어 logic·bit 등과 충돌하는 드문 레거시만 예외), 그 위에 두 갈래의 강력한 기능이 얹혀 있습니다.

🏗️ 설계측(Design) 개선

logic 타입, always_comb/ff, enum, struct, interface — 설계를 더 안전하고 간결하게.

🔬 검증측(Verification) 무기

class(OOP), rand+constraint, fork-join, covergroup, SVA assertion — 테스트를 코드로 짠다.

왜 배우나? UVM을 비롯한 현대 검증 방법론은 전부 SystemVerilog의 클래스·랜덤·커버리지 기능 위에 세워져 있습니다. SV를 모르면 UVM은 한 줄도 못 읽습니다.
직관적으로 이해하기

SV의 검증 기능, 하는 일 한 줄로 정리

검증측 기능은 종류가 많아 보이지만, "무엇을 하려는 도구인가"로 묶으면 다섯 갈래뿐입니다. 자세한 문법은 뒤에서 하나씩 보고, 먼저 큰 그림을 잡읍시다.

SystemVerilog 기능한 줄 역할
class / 상속(extends)테스트를 하나의 부품(객체)으로 모델링하고, 변형을 만들어 재사용
rand + constraint규칙을 지키는 범위 안에서 값을 무작위로 생성
SVA assertion"항상 참이어야 할 조건"을 적어두고 어기면 즉시 알림
fork ... join여러 작업을 동시에 돌리고 끝날 때까지 기다림
covergroup어디까지 테스트했는지를 백분율로 측정
설계측 개선 ①

logic 하나로 wire·reg를 통합

Verilog에서 가장 헷갈리던 함정: "이 신호는 wire로 선언할까 reg로 선언할까?". SystemVerilog는 logic 타입 하나로 대부분 해결합니다.

타입Verilog에서의 의미문제점
wire연속 할당(assign)으로 구동되는 배선어느 걸 써야 하나 매번 고민 → 실수 유발
regalways 블록 안에서 할당되는 변수 (실제로 레지스터란 뜻 아님!)
logic둘 다 됨 — 단, "한 곳에서만 구동" 규칙을 도구가 검사해 줌
이름의 함정: reg라는 이름은 "register(레지스터)"처럼 보이지만 실제로는 그냥 변수일 뿐이라, 처음 배우는 사람을 오래 헷갈리게 했습니다. logic은 그 모호함을 없앤 명확한 단일 타입입니다. (단, 여러 곳에서 동시에 구동되는 진짜 양방향 배선엔 여전히 wire를 씁니다.)
설계측 개선 ②

의도를 이름으로 선언한다: always_*

Verilog에선 모두 그냥 always였습니다. SV는 "이 블록이 조합논리냐 순차논리냐"를 이름으로 못박아, 도구가 실수를 잡아줍니다.

⚡ always_comb

조합논리 (기억 없음, 입력→즉시 출력). 민감도 목록을 자동으로 채워줘 빠뜨림 버그 방지.

🕐 always_ff

플립플롭 (클럭에 맞춰 기억). @(posedge clk). "이건 레지스터를 만들겠다"는 의도 선언.

⚠️ always_latch

래치를 의도적으로 만들 때. 의도치 않은 래치는 도구가 경고로 잡아줌.

핵심: 회로 동작은 같더라도 "내 의도는 조합논리(또는 순차논리)다"라고 이름으로 못박아 두면, 합성 도구가 내가 적은 의도와 실제 만들어질 회로가 어긋날 때 곧바로 에러를 띄워 줍니다. 실험에서 예상값을 미리 적어두면 결과가 어긋났을 때 바로 알아채는 것과 같습니다.
설계측 개선 ③ · 가장 중요

interface = 수십 가닥 배선을 케이블 하나로

버스 하나엔 신호가 수십 개(addr, data, valid, ready, write...). 이걸 모듈마다 일일이 연결하면 실수투성이. interface는 관련 신호를 한 묶음으로 추상화합니다.

interface의 장점: ① 신호 묶음을 한 곳에서 정의 → 추가/수정 쉬움 ② modport로 방향(입력/출력) 지정 → 연결 실수 방지 ③ 검증에서 virtual interface로 클래스와 신호를 잇는 핵심 통로가 됨.
검증측 ① · 핵심 질문

왜 검증에 OOP가 필요한가?

설계(RTL)는 동시에 돌아가는 병렬 회로라 OOP가 어울리지 않지만, 테스트를 만드는 일은 다릅니다 — 한 번 만든 걸 재사용하고, 확장하고, 수천 개의 변형을 찍어내야 하죠. 이렇게 "부품을 만들어 조립·재사용"하는 작업에는 객체지향(OOP)이 딱 맞습니다.

♻️ 재사용

기본 트랜잭션 클래스를 만들어 두면 프로젝트마다 상속해 재활용. 매번 새로 안 짠다.

🧩 확장

기존 테스트를 건드리지 않고 extends로 변형. UVM의 factory override가 이걸 활용.

🎲 랜덤 자극

객체 안에 rand 변수를 두면 수천 개의 시나리오를 자동 생성. 사람이 일일이 못 만든다.

비유: 테스트벤치를 하나의 레고 작품이라 생각하세요. 부품을 그때그때 통으로 깎아 만들 수도 있지만, 규격화된 블록(객체)을 만들어 두고 끼워 맞추면 고치고 확장하기가 훨씬 쉽습니다. 복잡한 칩일수록 답은 명확합니다 — OOP로 구조화해야 유지보수가 됩니다.

검증측 ② · 랜덤화

rand + constraint = 제약 기반 랜덤

핵심 아이디어: "값을 랜덤하게 뽑되, 말이 되는 범위 안에서만". 변수에 rand를 붙이고, constraint로 규칙을 건 뒤 randomize()를 호출합니다.

class Packet;
  rand bit [7:0] addr;
  rand bit [7:0] len;

  // 규칙: addr는 짝수, len은 1~16
  constraint rules {
    addr % 2 == 0;
    len inside {[1:16]};
  }
endclass

// 사용
Packet p = new();
if (p.randomize())  // 규칙 지킨 랜덤값 채움
  drive(p);
그냥 난수가 아니다: constraint에 적은 규칙은 전용 풀이 엔진(제약 솔버)이 처리합니다. 그래서 단순한 값 범위뿐 아니라 "addr가 짝수이면서 len과는 이런 관계여야 한다" 같은 변수 사이의 복잡한 조건식까지 동시에 만족하는 값을 자동으로 찾아냅니다. 연립부등식의 해를 풀어 그중 하나를 무작위로 골라주는 셈이죠.
왜 중요한가? 사람은 "정상 케이스 + 떠오르는 코너 케이스" 정도만 짭니다. 제약 랜덤은 사람이 상상 못 한 조합을 끝없이 던져 숨은 버그를 캐냅니다. 이를 CRV(Constrained-Random Verification)라 부릅니다.
검증측 ③ · 병렬과 통신

테스트벤치는 본질적으로 여러 일이 동시에 돌아간다

자극을 넣는 흐름, 응답을 받는 흐름, 검사하는 흐름이 동시에 진행돼야 합니다. SV는 여러 작업을 동시에 다루는 도구를 기본으로 제공합니다.

SV 구문하는 일
fork ... join여러 작업을 동시에 시작하고, 모두 끝날 때까지 기다림
fork ... join_none동시에 띄워 놓고 기다리지 않음 (계속 다음 일 진행)
mailbox동시에 도는 작업끼리 데이터를 주고받는 줄서기 통로(FIFO)
semaphore공유 자원에 동시에 접근하는 수를 제한 (화장실 열쇠 같은 것)
비유: 오케스트라를 떠올리면 됩니다. 여러 연주자(작업)가 동시에 연주하되, mailbox는 악보를 건네는 보면대, semaphore는 한 번에 한 명만 쓸 수 있는 마이크 같은 역할입니다. 검증 환경의 부품들은 이렇게 서로 느슨하게 연결돼 데이터를 주고받습니다.
검증측 ④ · 측정과 감시

"얼마나 테스트했나"와 "절대 깨지면 안 되는 조건"

📊 covergroup (커버리지)

랜덤으로 마구 던지면 "어디까지 두드렸나"를 알아야 합니다. covergroup으로 관심 값/조합이 실제 발생했는지 %로 측정합니다.

covergroup cg;
  // len의 모든 구간이 나왔나?
  coverpoint len {
    bins small = {[1:4]};
    bins big   = {[5:16]};
  }
endgroup

🚨 assertion / SVA

SVA(SystemVerilog Assertion) = "이 조건은 매 순간 항상 참이어야 한다"를 선언. 깨지면 시뮬레이션이 즉시 알려줌.

// req 뜨면 2클럭 내 ack
assert property (
  @(posedge clk)
  req |-> ##[1:2] ack
);
핵심 구분: 커버리지는 "충분히 했나?"(완성도), assertion은 "규칙을 어겼나?"(정확성)를 봅니다. covergroup은 시험 범위 중 어디까지 풀어봤는지 표시한 진도표, SVA는 회로 곳곳에 붙여둔 "이 조건이 깨지면 즉시 경보를 울리는 센서"라고 생각하면 됩니다.
검증측 ⑤ · 연결의 다리

virtual interface = 클래스 세계 ↔ 신호 세계의 다리

여기서 두 세계가 부딪힙니다. class는 시뮬레이션 도중 필요할 때 생겼다 사라지는 동적인 객체, interface/신호는 칩에 고정된 정적인 배선입니다. 클래스 안에서 실제 핀(wire)을 흔들려면 둘을 이어줄 연결 고리가 필요합니다.

한 줄로: virtual interface는 "실제 배선 묶음을 가리키는 주소표(연결 고리)"입니다. 클래스(객체)가 이 연결 고리를 들고 있어서, 멀리 떨어진 실제 핀을 마치 손에 쥔 것처럼 읽고 쓸 수 있게 됩니다. 우편번호가 실제 건물을 가리키듯, 객체가 하드웨어 신호를 가리키는 것이죠. 이 다리가 없으면 OOP 테스트벤치와 RTL은 영원히 서로 못 만납니다.
면접 예상 질문

이렇게 물어보면, 이렇게 답한다

Verilog와 SystemVerilog의 차이는?
SystemVerilog는 Verilog의 상위호환(superset)입니다. 기존 Verilog는 그대로 동작하고, 설계측으로는 logic 타입·always_comb/ff·interface·enum/struct가, 검증측으로는 class 기반 OOP·제약 랜덤·covergroup·assertion 같은 테스트 기능이 추가됐습니다. 한마디로 "Verilog에 객체지향과 검증 프레임워크를 내장한 언어"입니다.
logic과 wire/reg의 차이는?
Verilog의 wire는 연속 할당으로 구동되는 배선, reg는 always 블록에서 할당되는 변수인데 둘 중 뭘 쓸지 헷갈리는 게 문제였습니다. logic은 두 용도를 모두 커버하는 단일 4-상태 타입이고, "한 곳에서만 구동" 규칙을 도구가 검사해 줍니다. 다만 여러 드라이버가 필요한 진짜 양방향 배선엔 여전히 wire를 씁니다.
rand/constraint와 assertion(SVA)이 뭔가요?
rand는 클래스 변수를 랜덤화 대상으로 표시하고, constraint는 그 랜덤값이 만족해야 할 규칙입니다. randomize() 호출 시 전용 풀이 엔진(솔버)이 규칙을 만족하는 값을 생성하죠 — "규칙을 지키는 한도 안에서 무작위로 값을 던져 본다"는 발상입니다. assertion(SVA)은 "이 조건은 매 순간 항상 참이어야 한다"를 시간 관계로 선언해, 위반하는 순간 시뮬레이션이 즉시 잡아내는 자동 감시 장치입니다.
핵심 요약

이 챕터, 한 손에 잡기

  • SV = Verilog 슈퍼셋 + OOP + 테스트 기능 내장
  • 설계측: logic(타입 통합), always_comb/ff(의도 선언), interface(배선을 케이블로)
  • 검증측: class/상속, rand+constraint(제약 랜덤), fork-join/mailbox(병렬), covergroup(측정), SVA(감시)
  • OOP가 필요한 이유 = 재사용·확장·랜덤 자극
  • virtual interface가 class와 신호를 잇는 다리

"SystemVerilog는 Verilog 슈퍼셋에 OOP·제약 랜덤·커버리지·assertion을 더한 언어로, 재사용 가능하고 자동으로 자극을 생성하는 검증 환경을 코드로 짤 수 있게 해줍니다."

— 이 한 문장이면 1-2는 합격입니다.
