Part 5 · 저전력 검증

UPF & Emulation
전원을 끄는 칩, 어떻게 검증하나

안 쓰는 블록은 전원을 통째로 꺼버리는 게 현대 칩의 상식입니다. 그런데 RTL 코드엔 "전원"이라는 개념이 없습니다. 그래서 UPF가 등장하고, 너무 느린 시뮬은 에뮬레이션이라는 터보엔진으로 가속합니다.

한 문장 정의

UPF = 설계도엔 안 적힌 "전원 의도"를 따로 기술하는 파일

UPF(Unified Power Format)는 "어느 블록이 어떤 전원으로 돌고, 언제 꺼지고, 끌 때 무슨 보호장치가 필요한가"라는 전원 의도(power intent)를 RTL과 별도로 적는 표준 포맷입니다.

🤔 왜 RTL만으론 안 되나

  • Verilog/VHDL은 논리만 기술 — "이 AND 게이트는 0.8V로 돈다" 같은 전원 정보가 없음
  • 저전력 칩은 블록마다 전압이 다르고, 안 쓰는 블록은 전원을 끔
  • 이 정보를 RTL에 박으면 코드가 더러워지고 재사용 불가 → 분리가 답

🎯 UPF가 적는 것

  • Power Domain — 전원을 따로 줄 수 있는 영역
  • Supply Net / Power Switch — 전원선과 on/off 스위치
  • Isolation / Level Shifter / Retention — 경계의 보호장치들
UPF는 IEEE 1801 표준입니다. (경쟁 포맷 CPF도 있지만 면접에선 UPF만 알아도 충분합니다.)
직관적으로 이해하기

UPF는 "전원 사용설명서", 에뮬은 "고속 시운전"

건물 도면(RTL)은 방 구조와 배선만 그릴 뿐, "어느 층은 평소 전기를 끊고, 끌 땐 어떤 안전장치를 둔다"는 운영 규칙은 담지 못합니다. 그래서 전원 운영 규칙을 별도 문서(UPF)로 분리해 적습니다. 도면은 그대로 두고, 전원 의도만 따로 관리하는 셈입니다.

에뮬레이션은 고속 시운전입니다. 정밀한 시뮬레이션은 정확하지만 너무 느려서, 실제로 전체 시스템을 오래 돌려봐야 하는 검증은 전용 가속 하드웨어 위에서 합니다 — 자동차를 한 부품씩 정밀 점검하는 것과, 완성차를 시험 트랙에서 실제로 달려보는 것의 차이죠.

개념핵심 한 줄
UPF (전원 의도 분리)설계도와 분리해 전원 운영 규칙만 적은 문서
power gating (블록 전원 차단)안 쓰는 부분의 전원을 통째로 끊어 전력 절약
simulation (느리지만 정밀)한 부분씩 천천히 정밀하게 점검
emulation (실 SW·OS 부팅)전체를 빠르게 돌려 실제 동작까지 확인
UPF가 다루는 현실

저전력 칩의 3대 무기

🔌 Power Gating

안 쓰는 블록의 전원을 통째로 차단. 누설 전력(leakage)을 거의 0에 가깝게(보통 10~1000배) 줄입니다. (완전한 0은 아님 — power switch 자체, always-on 버퍼, 항상 켜진 retention 회로 등에서 미세 누설은 남습니다.)

집에서 안 쓰는 방의 전등을 끄는 것. 그 방은 전기를 거의 안 먹죠(콘센트 대기전력처럼 아주 미세한 양만 남습니다).

🎚️ Multi-Voltage

블록마다 다른 전압을 공급. CPU는 0.9V, 저속 주변장치는 0.6V처럼 필요한 만큼만.

방마다 밝기를 다르게. 거실은 환하게, 복도는 은은하게.

💾 Retention

전원을 끄기 전에 핵심 상태를 별도 저장. 다시 켜면 그 자리에서 복구.

읽던 책에 책갈피를 끼워 두는 것. 책을 덮었다 다시 펴도 읽던 페이지로 바로 돌아오죠.

문제: 전원을 끄거나 전압이 다른 블록끼리 신호를 주고받으면 전기적 사고가 납니다. 꺼진 블록의 출력은 알 수 없는 값(X)이 되고, 전압이 다르면 신호가 깨집니다. 그래서 경계마다 보호 셀이 필요합니다 → 다음 슬라이드.

UPF의 주인공들

경계를 지키는 세 가지 특수 셀

🚧 Isolation Cell

꺼진 도메인의 출력을 격리. 도메인이 OFF면 출력이 X(쓰레기값)가 되는데, 이게 켜진 도메인으로 새어 들어가 오동작시킵니다. isolation cell이 출력을 0 또는 1로 고정(clamp)해 X 전파를 막습니다.

🗣️ Level Shifter

전압이 다른 도메인을 연결. 0.6V 도메인의 신호를 0.9V 도메인이 못 알아듣습니다. level shifter가 신호의 전압 레벨을 변환해 줍니다.

💾 Retention Register

전원이 꺼져도 값을 유지하는 특수 플립플롭. 항상 켜져 있는 보조 전원(shadow latch)에 값을 보관했다가, 전원 복귀 시 그대로 복원합니다.

isolation = 꺼진 방문을 닫아 쓰레기가 안 새게, level shifter = 다른 언어를 쓰는 두 방 사이의 통역사, retention = 불 끄기 전 책갈피를 끼워 두기. 이 셋만 기억하면 UPF의 80%는 끝입니다.

한 그림으로 보는 전원 도메인

도메인 경계에서 무슨 일이 일어나나

UPF를 실제로 검증하는 법

Power-Aware Simulation = UPF를 반영한 시뮬레이션

일반 시뮬레이션은 전원이 항상 켜져 있다고 가정합니다. Power-aware sim은 UPF를 함께 읽어, 전원이 실제로 꺼졌다 켜졌다 하는 상황을 모델링합니다.

🔬 무엇을 추가로 검사하나

  • 도메인이 꺼지면 그 로직 출력을 X로 처리 — X가 어디까지 번지나 추적
  • isolation cell이 제때 활성화돼 X 전파를 막는가
  • retention 값이 전원 복귀 후 정확히 복원되는가
  • level shifter 없이 전압 다른 도메인을 직접 연결한 실수가 있는가
  • 전원 on/off 시퀀스 순서(끄기 전 격리·저장 먼저)가 지켜지는가

🐞 어떤 버그를 잡나 (코너 버그)

  • 격리를 깜빡해 꺼진 GPU의 X값이 CPU로 새는 버그
  • retention 안 걸어서 깨어나니 상태가 날아간 버그
  • 전원 켜기 전에 사용해서 잘못된 값으로 동작
  • 격리 신호 타이밍이 어긋나는 레이스 버그

한 줄로: 전원이 꺼진 부분은 "응답할 수 없는 상태"인데, 옆 블록이 그걸 모르고 그 출력을 멀쩡한 값으로 믿고 쓰다가 오동작합니다. power-aware sim은 바로 이 "꺼진 부분을 잘못 참조하는" 버그를 전원 레벨에서 잡아냅니다.

한눈에 보는 X 전파

꺼진 도메인은 X를 뿜고, ISO가 그걸 막는다

디지털 검증에서 X는 "0인지 1인지 모름"을 뜻합니다. 전원이 꺼진 회로의 출력이 바로 X입니다. X가 정상 로직에 닿으면 결과 전체가 오염됩니다.

// 격리 없이 꺼진 GPU 출력을 그대로 사용
assign result = cpu_data & gpu_out;
// GPU OFF → gpu_out = X
// result = cpu_data & X = X  ← 오염!

// isolation cell이 켜지면 (clamp to 0)
// gpu_out → 0 으로 고정
// result = cpu_data & 0 = 0  ← 안전

isolation은 "꺼진 블록의 출력을 0/1로 묶어 X가 못 새게" 하는 게 전부입니다.

시뮬은 너무 느리다

Emulation = 시뮬레이션의 터보엔진

대형 SoC를 소프트웨어 시뮬레이터로 돌리면 OS 부팅 한 번에 며칠이 걸립니다. 그래서 설계를 전용 하드웨어에 통째로 올려 수백만 배 빠르게 돌리는 게 에뮬레이션입니다.

🐢 왜 시뮬은 느린가

  • 시뮬레이터는 CPU가 회로 동작을 흉내내는 소프트웨어 — 게이트 수억 개를 한 클럭씩 계산
  • 속도: 대략 수십 ~ 수천 Hz 수준 (실칩은 GHz)
  • 실 OS 부팅·드라이버 같은 긴 시나리오는 사실상 불가능

🚀 에뮬레이터는 어떻게 빠른가

  • 설계를 대규모 FPGA/전용칩 배열에 매핑해 실제 회로처럼 병렬로 동작
  • 속도: MHz 급 — 시뮬 대비 수천~수백만 배
  • 그래서 리눅스/안드로이드 부팅, 실 펌웨어·드라이버를 실제로 돌려볼 수 있음

비유하자면: 시뮬은 실험실에서 부품을 한 점씩 정밀 측정하는 것이고, 에뮬은 완성한 기계를 시험 트랙에서 실제로 가동해 보는 것입니다. 대신 트레이드오프가 있습니다 — 빠르게 통째로 돌리는 만큼, 에뮬은 시뮬처럼 내부 신호를 속속들이 들여다보기는 어렵습니다.

면접 예상 질문

이렇게 물어보면, 이렇게 답한다

UPF가 왜 필요한가요?
RTL은 논리만 기술할 뿐 전원 정보가 없습니다. 저전력 칩은 블록마다 전압이 다르고 안 쓰는 블록은 전원을 끄는데, 이런 전원 의도를 RTL에 박으면 코드가 더러워지고 재사용이 안 됩니다. UPF는 power domain·power switch·isolation·level shifter·retention 같은 전원 의도를 별도 표준 파일로 분리해, 설계는 그대로 두고 전원 동작을 기술·검증하게 해줍니다.
isolation cell, level shifter, retention register의 역할은?
isolation cell은 꺼진 도메인의 출력을 0/1로 고정해 X값이 켜진 도메인으로 새는 걸 막습니다. level shifter는 전압이 다른 두 도메인 사이에서 신호의 전압 레벨을 변환해 통신을 가능하게 합니다. retention register는 전원이 꺼져도 보조 전원으로 값을 보관했다가 복귀 시 상태를 그대로 복원합니다. 격리·통역·자동저장으로 기억하면 쉽습니다.
power-aware simulation은 어떤 버그를 잡나요?
전원 on/off에 얽힌 코너 버그입니다. 격리를 빼먹어 꺼진 블록의 X가 정상 로직으로 전파되는 버그, retention을 안 걸어 깨어났더니 상태가 날아간 버그, 전원 켜기 전에 사용하거나 격리/저장 시퀀스 순서가 어긋나는 버그를 잡습니다. 일반 시뮬은 전원이 항상 켜졌다고 가정하므로 이런 버그를 놓칩니다.
에뮬레이션은 시뮬레이션과 언제·왜 다르게 쓰나요?
대형 SoC를 소프트웨어 시뮬로 돌리면 OS 부팅에 며칠이 걸려 사실상 불가능합니다. 에뮬레이션은 설계를 전용 하드웨어에 매핑해 MHz급으로 가속하므로, 실제 OS 부팅이나 펌웨어·드라이버 같은 긴 SW 시나리오를 돌려볼 수 있습니다. 정밀 디버깅이 필요한 블록 검증은 시뮬, SW 통합과 실 실행 검증은 에뮬을 씁니다. 트레이드오프는 에뮬이 시뮬보다 셋업이 무겁고 신호 가시성이 떨어진다는 점입니다.
핵심 요약

이 챕터, 한 손에 잡기

  • 저전력 3대 기법: power gating(전원 차단)·multi-voltage·retention(상태 보존)
  • RTL엔 전원 정보가 없다 → UPF로 전원 의도를 별도 기술
  • 보호 셀 3종: isolation(X 격리)·level shifter(전압 변환)·retention reg(상태 보존)
  • Power-aware sim = UPF 반영 → X 처리·격리·복원의 코너 버그 검출
  • Emulation = 전용 HW로 가속해 실 OS 부팅·SW 통합 검증
  • 시뮬(정밀·느림) · 에뮬(SW 통합) · FPGA(실속도·저가시성)

"RTL엔 없는 전원 의도를 UPF로 기술하고, power-aware 시뮬레이션으로 격리·복원의 코너 버그를 잡으며, 너무 느린 검증은 에뮬레이션으로 가속해 실 SW까지 돌려봅니다."

— UPF + power-aware sim + 에뮬, 세 키워드를 한 문장에.
