HDL을 "돌려보는" 엔진

설계도(Verilog)를 실제 칩 없이 컴퓨터에서 실행하고, 그 결과를 파형으로 들여다보는 도구. 당신의 gcc + gdb가 하드웨어 세계로 넘어오면 어떤 모습인지 보여 드립니다.

한 문장 정의

시뮬레이터 = HDL을 실행하는 이벤트 기반 엔진

시뮬레이터는 Verilog/SystemVerilog로 쓴 설계와 테스트벤치를 받아, 신호가 변하는 순간(event)마다 회로를 계산해 시간 순서대로 동작을 재현하는 프로그램입니다.

⚙️ 왜 필요한가

칩은 만들기 전엔 만질 수 없습니다. tape-out 전에 설계가 스펙대로 도는지 증명할 유일한 현실적 수단이 소프트웨어 시뮬레이션입니다.

🔍 왜 면접에 나오나

검증 엔지니어가 하루 종일 쓰는 도구입니다. "어떤 시뮬레이터 써봤나", "VCS와 Xcelium 차이" 는 거의 단골 질문입니다.

개발자 직관으로 번역

시뮬레이터 = 하드웨어용 툴체인 + IDE

소프트웨어를 만들 때 gcc로 컴파일하고 gdb로 디버깅하죠. 하드웨어 검증의 도구들도 정확히 그 역할을 나눠 가집니다.

당신이 아는 것하드웨어 검증하는 일
gcc (컴파일+링크)VCS / XceliumHDL을 컴파일·연결(elaborate)해 실행 가능한 시뮬레이션 모델로
./a.out (실행)simulation 실행테스트벤치로 자극을 넣고 시간 순서대로 동작
gdb (디버거)Verdi / SimVision멈추고, 들여다보고, 신호를 추적 — 단 파형으로
실행 트레이스 로그FSDB / VCD"언제 어떤 신호가 변했나"를 기록한 파형 덤프 파일
핵심: 소프트웨어는 한 줄씩 순차 실행이라 "지금 몇 번째 줄"이 디버깅 단위지만, 하드웨어는 모든 회로가 동시에 도니까 디버깅 단위가 "시간(클럭)에 따른 신호 값" = 파형입니다.
엔진의 동작 원리

왜 "이벤트 기반(event-driven)"인가

매 클럭마다 수억 개 게이트를 전부 다시 계산하면 너무 느립니다. 그래서 시뮬레이터는 값이 실제로 바뀐 신호와, 그 영향을 받는 회로만 골라서 계산합니다.

시간 점프

엑셀 스프레드시트와 같습니다. 셀 하나를 고치면 그 셀을 참조하는 수식만 다시 계산되고, 무관한 셀은 건드리지 않죠. 시뮬레이터도 "바뀐 것 → 영향받는 것"만 연쇄적으로 갱신하는 이벤트 큐(event queue)를 돌립니다.

대안으로 cycle-based 시뮬레이션(매 클럭 전체 계산)도 있지만, 상용 검증 시뮬레이터는 정밀한 타이밍·딜레이를 다루기 위해 이벤트 기반이 표준입니다.
실행 흐름

compile → elaborate → simulate

시뮬레이션은 보통 3단계입니다. 소프트웨어의 compile → link → run과 거의 1:1로 대응합니다.

① Compile
문법 분석 (analyze)
→
② Elaborate
모듈 연결·인스턴스화
→
③ Simulate
시간 진행하며 실행
Compile
각 소스 파일의 문법을 검사. gcc -c에 해당.
Elaborate
모듈 계층을 펼쳐 실제 인스턴스로 "조립". 파라미터·연결을 확정. 링크 단계에 해당.
Simulate
조립된 모델을 시간 0부터 굴림. ./a.out 실행에 해당.

요즘은 한 명령으로 세 단계를 묶는 single-command 흐름이 흔합니다.

# Xcelium: 한 방에 컴파일+엘라보+실행
xrun tb_top.sv dut.v +access+r

# VCS: 빌드 후 실행 (2단계)
vcs -sverilog tb.sv dut.v -o simv
./simv
시장의 양대 산맥

VCS · Xcelium · (Questa)

상용 로직 시뮬레이터 시장은 사실상 세 회사(Big 3 EDA)가 나눠 가집니다. 이름과 명령어, 디버거 짝꿍을 외워두면 면접에서 강합니다.

🟢 VCS

Synopsys 제품. 실행 명령 vcs. 빠른 성능으로 유명. 디버거는 Verdi, 파형은 FSDB.

🔵 Xcelium

Cadence 제품. 통합 명령 xrun. (이전 이름 Incisive/NCSim). 디버거는 SimVision / Indago.

🟣 Questa

Siemens EDA(구 Mentor) 제품. 명령 vsim. 보너스로 알아두면 좋음. 입문용 ModelSim의 형.

세 도구 모두 SystemVerilog·UVM·SVA·커버리지를 지원합니다. 회사마다 어떤 걸 쓰는지는 라이선스 계약에 달려 있어, 보통 한 회사는 한두 개를 표준으로 정해 씁니다.

⚠️ 주의: 셋 다 고가의 유료 라이선스(license)가 필요합니다. 시뮬레이션 동시 실행 수가 라이선스 토큰 수로 제한되고, regression 수천 개를 돌릴 땐 이 토큰이 곧 돈이자 병목입니다. 무료로 쓰려면 학습용은 오픈소스 Verilator / Icarus가 있지만 UVM 지원이 제한적입니다.

파형 덤프 포맷

VCD vs FSDB — 실행 트레이스 로그

시뮬레이션이 돌면서 "언제 어떤 신호가 어떤 값으로 변했는지"를 파일로 남깁니다. 이게 파형 덤프(waveform dump)이고, 나중에 디버거로 열어 봅니다.

포맷정체특징
VCDValue Change Dump (표준·텍스트)모든 시뮬레이터가 지원. 단순하지만 용량 크고 느림. 큰 설계엔 부적합.
FSDBFast Signal DB (Synopsys/Verdi)압축 바이너리. 작고 빠름. 업계 사실상 표준. Verdi와 짝.
SHMCadence(SimVision)용 DBXcelium 계열의 네이티브 파형 DB.

VCD는 사람이 읽을 수 있는 텍스트 로그(JSON 같은), FSDB는 압축된 바이너리 로그(protobuf 같은)라고 생각하면 정확합니다. 큰 데이터일수록 바이너리가 이깁니다.

// 테스트벤치에서 파형 덤프 켜기 (VCD)
initial begin
  $dumpfile("wave.vcd");
  $dumpvars(0, tb_top);
end

FSDB는 $fsdbDumpvars를 씁니다.

디버거의 세계

Verdi — 파형으로 보는 비주얼 디버거

Verdi(Synopsys)는 검증 엔지니어가 가장 많이 쓰는 디버그 툴입니다. FSDB를 열어 파형을 보고, 신호를 클릭하면 그 값이 어디서 왔는지 RTL 소스까지 역추적해 줍니다.

파형의 각 줄이 신호 하나, 가로축이 시간. 버그란 결국 "어느 클럭에 어떤 신호가 기대와 다른 값"이고, Verdi는 그 다른 값을 만든 원인을 신호 → 신호 → 소스로 거슬러 올라가게 해줍니다(trace/backtrace).
실제 디버깅 흐름

어떻게 파형으로 버그를 잡나

  1. 테스트가 FAIL 또는 어서션(SVA) 위반으로 멈춤
  2. 로그에서 몇 ns / 몇 번째 클럭에서 깨졌는지 확인
  3. Verdi로 FSDB 열고 그 시각으로 커서 이동
  4. 기대와 다른 신호를 찾고, 그 신호의 원인 신호로 역추적
  5. RTL 소스의 잘못된 로직(또는 테스트벤치 버그)을 특정

🧭 개발자 비유

gdb에서 변수가 이상한 값일 때 그 변수에 watchpoint를 걸고 어디서 바뀌었는지 추적하죠. Verdi의 신호 역추적이 바로 그 watchpoint·backtrace의 하드웨어 버전입니다.

차이: 시간을 앞뒤로 자유롭게 오갈 수 있다는 것. 시뮬레이션은 이미 다 기록(FSDB)됐으니까요.

"실패 로그에서 시각을 찾고 → Verdi로 그 시각 파형을 열어 → 잘못된 신호를 원인 신호로 역추적해 RTL/TB 버그를 특정합니다."

시뮬레이터가 떠받치는 것들

UVM · SVA · Coverage DB

현대 시뮬레이터는 단순 실행기를 넘어, 검증 방법론 전체를 떠받치는 플랫폼입니다.

🧱 UVM

SystemVerilog 기반 검증 프레임워크. 시뮬레이터가 UVM 라이브러리를 내장·실행합니다. (Part 2 주제)

✅ SVA

SystemVerilog Assertion. "이 조건은 항상 참이어야 한다"를 검사하는 런타임 단언. 위반하면 에러를 리포트하고(기본 severity는 $error라 시뮬레이션은 계속됨), $fatal로 지정했을 때만 즉시 중단.

📊 Coverage DB

"어디까지 두드렸나"를 누적 기록. 여러 시뮬레이션 결과를 합쳐(merge) 커버리지 리포트를 만듦.

소프트웨어로 치면 UVM은 JUnit/pytest 프레임워크, SVA는 코드 곳곳의 assert(), Coverage DB는 코드 커버리지 리포트입니다. 시뮬레이터는 이 셋을 한 엔진 안에서 동시에 굴립니다.

면접 예상 질문

이렇게 물어보면, 이렇게 답한다

로직 시뮬레이터가 하는 일이 뭔가요?
Verilog/SystemVerilog로 작성한 설계와 테스트벤치를 컴파일·엘라보레이션한 뒤, 이벤트 기반으로 시간을 진행시키며 회로 동작을 재현하는 엔진입니다. 실물 칩 없이 설계가 스펙대로 도는지 검증하고, 파형 덤프를 남겨 디버깅하게 해줍니다.
VCS와 Xcelium의 차이는?
VCS는 Synopsys 제품으로 실행 명령이 vcs이고 디버거는 Verdi(FSDB 파형)와 짝을 이룹니다. Xcelium은 Cadence 제품으로 xrun 단일 명령으로 컴파일·실행을 통합하며 디버거는 SimVision/Indago입니다. 둘 다 SystemVerilog·UVM·커버리지를 지원하고, 회사의 EDA 라이선스 계약에 따라 선택됩니다.
VCD와 FSDB는 뭐가 다른가요? Verdi는요?
둘 다 파형 덤프 포맷인데, VCD는 표준 텍스트 포맷이라 호환성은 좋지만 용량이 크고 느립니다. FSDB는 Synopsys의 압축 바이너리 포맷으로 작고 빨라 사실상 업계 표준입니다. Verdi는 그 FSDB를 열어 파형을 보고 신호를 RTL 소스까지 역추적하게 해주는 비주얼 디버거입니다.
핵심 요약

이 챕터, 한 손에 잡기

  • 시뮬레이터 = HDL을 이벤트 기반으로 실행하는 엔진
  • 흐름: compile → elaborate → simulate (gcc→link→run)
  • 양대 상용: VCS(Synopsys, vcs) · Xcelium(Cadence, xrun) · 보너스 Questa(Siemens)
  • 파형 포맷: VCD(텍스트 표준) vs FSDB(빠른 바이너리)
  • 디버거: VCS↔Verdi, Xcelium↔SimVision/Indago
  • UVM·SVA·Coverage DB를 한 엔진에서 지원, 라이선스는 비싸고 곧 병목

"시뮬레이터는 HDL용 gcc+gdb입니다. VCS/Xcelium으로 설계를 실행하고, Verdi로 FSDB 파형을 열어 신호를 역추적하며 버그를 잡습니다."
