칩은 자기 자신을 어떻게 검사하나

공장 출하 전 전수검사부터, 자동차 시동 걸 때 계기판이 한 번에 켜지는 자가점검까지. 만든 칩에 불량이 없는지 어떻게 알아낼까요? 칩 스스로 테스트하게 만드는 기술, DFT입니다.

← → 또는 Space 로 넘기기
한 문장 정의

DFT = 칩을 "테스트하기 쉽게" 설계하는 기술

DFT(Design for Test)는 제조된 칩 하나하나에 물리적 불량이 있는지 빠르게 가려낼 수 있도록, 설계 단계에서 테스트 전용 회로를 미리 심어두는 것입니다. 오늘 배울 3대 도구가 Scan · MBIST · POST/IST입니다.

🏭 왜 필요한가

  • 칩 설계가 맞아도 제조 공정에서 불량이 생김 (먼지, 단선, 단락)
  • 핀은 수백 개인데 내부 플립플롭·메모리는 수억 개 → 바깥에서 못 들여다봄
  • 불량 칩을 걸러내지 못하면 제품에 들어가 필드에서 고장

🧪 무엇과 헷갈리면 안 되나

  • 검증(Verification) = "설계 자체가 맞는가" (시뮬레이션)
  • 테스트(Test) = "이 제조된 개체가 멀쩡한가" (제조 후)
  • DFT는 후자를 위한 회로 — 하지만 그 DFT 동작이 맞는지는 검증의 몫
즉 DFT는 "제조 불량 잡기"용 회로이고, 그 회로가 설계대로 동작하는지를 시뮬레이션으로 확인하는 게 검증 엔지니어의 일입니다.
개발자 직관으로 번역

이미 당신은 self-test를 매일 돌리고 있다

서버가 부팅될 때 /healthz 엔드포인트로 self-test/헬스체크를 돌려본 적 있나요? DB 연결·디스크·메모리를 스스로 점검하고, 정상이어야 트래픽을 받죠. 그게 바로 칩의 POST(Power-On Self Test)입니다.

배포 파이프라인의 CI smoke test도 떠올리세요. 진짜 동작 전에 "기본은 깨지지 않았나"를 빠르게 확인하죠. 칩도 본격 동작 전에 메모리·로직을 스스로 두드려 봅니다.

핵심 도구 ① Logic Scan Test

모든 플립플롭을 한 줄로 꿰어 거대한 시프트 레지스터로

로직(조합회로) 불량을 잡는 문제의 핵심은 관찰 불가능성입니다. 칩 깊숙한 곳의 플립플롭 값을 바깥 핀으로 어떻게 보나요? 해법: 테스트 모드에선 모든 플립플롭을 직렬로 연결해 하나의 긴 사슬(scan chain)로 만듭니다.

개발자 비유: 함수 내부 지역변수를 직접 못 보니, 디버거로 모든 변수를 한 줄씩 주입(set)하고 한 스텝 실행 후 다시 읽는(get) 것과 같습니다. scan chain은 칩 전체에 박아둔 "디버그 직렬 포트"입니다.

Scan은 어떻게 결함을 잡나

주입(shift) → 캡처(capture) → 관찰(shift) 3박자

① Shift-In
FF에 임의 패턴 주입
→
② Capture
정상모드 1클럭, 로직 결과 받기
→
③ Shift-Out
결과를 읽어 기대값과 비교

🔁 두 가지 모드

  • Shift 모드: FF들이 사슬로 연결 → 값을 밀어넣고 밀어냄
  • Capture 모드: 정상 회로 연결 → 한 클럭 동작시켜 로직 출력을 FF에 저장
  • 이 둘을 scan_enable 한 신호로 토글

🎯 결함 판정

  • 주입한 입력에 대한 기대 출력은 시뮬레이션으로 미리 계산
  • 실제 칩이 뱉은 값 ≠ 기대값 → 불량 칩
  • 수천~수만 개 패턴을 자동으로 쏟아붓는 게 다음 슬라이드의 ATPG
패턴은 누가 만드나 — ATPG

ATPG = 결함을 잡는 테스트 패턴 자동 생성기

ATPG(Automatic Test Pattern Generation)는 회로 구조를 분석해, "어떤 입력을 넣으면 특정 결함이 출력에 드러나는지"를 자동으로 계산해 패턴을 뽑아냅니다. 사람이 손으로 못 만드는 양을 기계가 생성합니다.

📌 Stuck-at Fault 모델

가장 기본 결함 모델. 어떤 신호선이 물리적 불량으로 0 또는 1에 고정(붙어버린)된 상태를 가정합니다.

  • stuck-at-0: 그 선이 항상 0
  • stuck-at-1: 그 선이 항상 1
  • ATPG는 각 결함을 출력에서 보이게 만드는 입력을 찾음

🧩 어떻게 "보이게" 하나

결함을 검출하려면 두 가지가 필요합니다.

  • 활성화: 그 선에 결함과 반대 값을 강제 (s-a-0이면 1을 넣어야 차이가 남)
  • 전파: 그 차이가 출력 FF까지 전달되도록 다른 입력 설정
다른 결함 모델: transition(느려진 경로), bridging(두 선 단락) 등도 있지만, 면접에선 보통 stuck-at만 정확히 말하면 충분합니다.
얼마나 잘 잡았나 — 커버리지

Fault Coverage = 테스트가 잡아낼 수 있는 결함 비율

코드 커버리지가 "테스트가 실행한 코드 비율"이듯, fault coverage는 "내 테스트 패턴이 검출 가능한 전체 결함의 비율"입니다. 양산 칩 품질을 좌우하는 숫자라 보통 99%대를 목표로 합니다.

개발자 비유: fault coverage ≈ 코드 커버리지. "테스트가 100%면 버그가 0"이 아니듯, fault coverage 100%여도 모델 밖 결함은 못 잡습니다. 그래도 높일수록 불량 유출(test escape)이 줄어듭니다.

핵심 도구 ② Memory BIST

메모리는 scan이 어렵다 → 칩 안에 테스트 엔진을 박는다

메모리(SRAM 등)는 셀이 빽빽한 규칙적 배열이라 scan chain으로 한 셀씩 다루기엔 비효율적이고, 셀 특유의 결함(이웃 셀 간섭 등)은 일반 패턴으로 안 잡힙니다.

그래서 MBIST(Memory Built-In Self-Test) — 메모리 옆에 전용 테스트 엔진을 칩 안에 내장합니다. 이 엔진이 정해진 알고리즘으로 메모리에 쓰고/읽으며 스스로 결함을 찾습니다.

  • 외부 장비 없이 칩 내부에서 자급자족 테스트
  • 고속 메모리는 외부 핀 속도로 못 따라가서도 BIST가 유리
  • 부팅 시·필드에서도 재실행 가능 (→ POST와 결합)
MBIST는 무엇을 돌리나 — March

March 알고리즘 — 메모리를 위아래로 쓸며 셀 결함을 잡기

March 테스트는 모든 주소를 한 방향으로 행진(march)하며 정해진 순서로 쓰기/읽기를 반복합니다. 이웃 셀 간섭·고착 같은 메모리 특유 결함을 효율적으로 검출하도록 설계된 표준 패턴입니다.

# March C- 예시 (↑오름차순, ↓내림차순 주소)
M0: ↕ w0          # 모든 셀에 0 쓰기
M1: ↑ r0, w1     # 0 읽혀야 정상 → 1 쓰기
M2: ↑ r1, w0     # 1 읽혀야 정상 → 0 쓰기
M3: ↓ r0, w1     # 내림차순으로 반대 방향 검증
M4: ↓ r1, w0
M5: ↕ r0          # 마지막 확인 → 하나라도 틀리면 FAIL

비유: 주차장 모든 칸에 "빈 종이"를 넣고(w0), 한 칸씩 돌며 종이가 그대로인지 확인 후 "빨간 종이"로 바꿔치기(r0,w1). 다시 돌며 빨간 종이가 맞는지 본다. 어떤 칸이 옆 칸 영향으로 멋대로 바뀌면 즉시 들통납니다.

핵심 도구 ③ IST / POST

부팅할 때 칩이 스스로를 점검하고 시작한다

🔑 POST & IST

  • POST(Power-On Self Test): 전원이 들어오는 순간, 부팅 초기에 자가점검 실행
  • IST(In-System Test): 시스템에 장착된 상태에서 (부팅 시 또는 필드 주기적으로) 테스트 실행
  • 내부적으로 MBIST 엔진 / scan 로직을 재활용해 돌림

🚗 왜 필드에서까지?

  • 출하 땐 멀쩡해도 사용 중 노화·열화로 고장 가능
  • 자동차 ISO 26262 기능안전: 동작 중에도 결함을 감지해야 함
  • 주행 중·시동 시 주기적 self-test로 안전 상태 보장

검증 엔지니어의 시선

이 DFT 동작들을 어떻게 검증하나

DFT 회로는 "불량 칩을 잡는" 회로지만, 그 회로 자체가 설계대로 동작하는지는 시뮬레이션으로 증명해야 합니다. 검증 엔지니어의 임무는 여기입니다.

🔬 무엇을 확인하나

  • scan chain이 끊김 없이 shift-in/out 되는가 (chain integrity)
  • MBIST 엔진이 March를 정확한 순서로 수행하고 FAIL을 제대로 깃발 세우나
  • POST/IST가 부팅 시퀀스와 올바르게 엮여 PASS 시에만 진행하나
  • 의도적으로 결함을 주입(fault injection)했을 때 정말 FAIL로 잡히나

🧰 어떻게

  • RTL/게이트 시뮬레이션으로 scan·MBIST·POST 시퀀스 재현
  • ATPG 패턴을 게이트넷리스트에 돌려 기대값과 일치 확인
  • fault coverage 리포트로 목표치(예: 99%) 달성 확인
  • 커버리지: 모든 MBIST 알고리즘 단계·모든 scan 모드를 다 밟았나

개발자 비유: 헬스체크 코드를 짜면 그게 실제로 장애를 감지하는지 테스트해보죠("일부러 DB를 끊어보기"). DFT 검증도 똑같이 일부러 결함을 넣어 self-test가 잡아내는지 확인하는 "테스트를 위한 테스트"입니다.

면접 예상 질문

이렇게 물어보면, 이렇게 답한다

Scan chain과 ATPG가 뭔가요? stuck-at fault는요?
Scan chain은 테스트 모드에서 칩 내부의 모든 플립플롭을 하나의 직렬 시프트 레지스터로 연결한 것입니다. 임의 패턴을 shift-in으로 주입하고, 한 클럭 캡처해 로직 결과를 받고, shift-out으로 읽어 기대값과 비교합니다. ATPG는 이 패턴을 회로 구조를 분석해 자동 생성하는 도구이고, stuck-at fault는 어떤 신호선이 0이나 1에 고정된 불량을 가정하는 가장 기본적인 결함 모델입니다.
메모리는 왜 scan 대신 MBIST를 따로 두나요?
메모리는 셀이 빽빽한 규칙적 배열이라 scan chain으로 다루기엔 비효율적이고, 이웃 셀 간섭 같은 메모리 특유 결함은 일반 로직 패턴으로 못 잡습니다. 그래서 메모리 옆에 전용 테스트 엔진을 내장해 March 같은 알고리즘으로 직접 쓰고 읽으며 검사합니다. 외부 장비 없이 고속으로, 그리고 부팅 시·필드에서도 재실행할 수 있는 게 장점입니다.
POST/IST가 뭐고, 부팅 시퀀스와 어떻게 엮이나요?
POST는 전원이 켜질 때 칩이 스스로 점검하는 자가테스트이고, IST는 시스템에 장착된 상태에서 부팅 시나 필드에서 주기적으로 돌리는 테스트입니다. 보통 MBIST나 scan 로직을 재활용합니다. 부팅 시퀀스에선 전원 ON 직후 MBIST·로직 점검을 수행하고, PASS여야 다음 단계로 진행하며 FAIL이면 안전 상태로 갑니다. 특히 자동차 ISO 26262 기능안전에서 동작 중 결함 감지에 중요합니다.
Test coverage(fault coverage)란 무엇인가요?
테스트 패턴이 검출할 수 있는 결함의 비율입니다. 코드 커버리지의 하드웨어판이라 생각하면 됩니다. 보통 stuck-at 기준으로 99%대를 목표로 하며, 이 수치가 높을수록 불량 칩이 양품으로 새어나가는 test escape가 줄어듭니다. 다만 모델 밖 결함은 못 잡으므로 100%여도 완벽을 보장하진 않습니다.
핵심 요약

이 챕터, 한 손에 잡기

  • DFT = 제조 후 불량을 잡기 위해 칩에 심는 테스트 전용 회로
  • Scan = 모든 FF를 사슬로 연결, shift→capture→shift, ATPG가 패턴 생성
  • stuck-at = 선이 0/1에 고정된 기본 결함 모델
  • MBIST = 메모리 전용 내장 엔진, March 알고리즘으로 셀 검사
  • POST/IST = 부팅·필드에서 self-test, PASS여야 진행 (ISO 26262)
  • fault coverage = 잡아낸 결함 비율(≈코드 커버리지), 목표 99%↑

"Scan은 로직을, MBIST는 메모리를 제조 후 점검하고, POST/IST는 그걸 부팅·필드에서 돌립니다. 저는 그 DFT 동작이 설계대로 결함을 잡아내는지를 시뮬레이션으로 검증합니다."

— 3대 도구 + 검증 관점, 한 문장에.
