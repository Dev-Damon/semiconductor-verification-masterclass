왜 이걸 배우나

채용공고가 대놓고 요구하는 부분

설계검증 직무 공고의 우대사항에는 거의 항상 Linux · shell · Tcl · Perl · Python이 들어갑니다. 검증 방법론(UVM)만큼이나 "환경을 돌리는 손"을 봅니다.

🧠 아는 것 (이미 함)

SystemVerilog·UVM·AXI·커버리지·GLS — "무엇을 검증하는가".

🛠️ 돌리는 것 (이 챕터)

리눅스에서 컴파일→시뮬→회귀→커버리지→파형디버그를 스크립트로 자동화하는 흐름.

면접에서 "회귀는 어떻게 돌리나요?", "Makefile 써봤나요?", "로그에서 fail을 어떻게 찾죠?"가 나오면 — 이 챕터의 답이 곧 실무 감각의 증거입니다.
① 리눅스 기본기

DV 엔지니어가 실제로 매일 치는 명령

검증 서버는 대부분 원격 리눅스(CentOS/RHEL)입니다. GUI 없이 터미널로 삽니다.

탐색
ls cd pwd find . -name "*.sv"
내용찾기
grep -rn "UVM_ERROR" log/
보기/편집
less sim.log · vim tb.sv
원격/잡
ssh · bsub(LSF) 로 grid에 잡 제출

가장 많이 쓰는 한 줄은 결국 이겁니다:

# 방금 돌린 로그에서 에러만 뽑기
grep -E "UVM_ERROR|UVM_FATAL|Error-" sim.log

# 여러 로그에서 실패한 테스트 찾기
grep -l "UVM_FATAL" log/*.log

"수천 줄 로그에서 fail 원인 한 줄을 찾는 법" — 실무의 절반입니다.

② 프로젝트 구조 & Makefile

Make로 컴파일·시뮬을 한 명령에

수십 개 파일을 매번 손으로 컴파일할 순 없습니다. Makefile에 타깃을 만들어 make sim TEST=... 한 줄로 돌립니다.

# Makefile (Synopsys VCS 예시)
TEST ?= axi_base_test
SEED ?= 1

comp:                         # 1) compile + elaborate
	vlogan -sverilog -full64 -ntb_opts uvm -f filelist.f
	vcs -full64 -debug_access+all -kdb -o simv

sim: comp                     # 2) simulate
	./simv +UVM_TESTNAME=$(TEST) +ntb_random_seed=$(SEED) \
	       -cm line+cond+fsm+tgl +UVM_VERBOSITY=UVM_LOW -l sim.log

regress:                      # 3) 야간 회귀
	python3 run_regress.py --tests testlist.f --seeds 50
→ make sim TEST=axi_burst_test SEED=7 처럼 인자를 바꿔 다양한 테스트/시드를 돌립니다. compile→elaboration→simulation 3단계가 comp/sim 타깃에 그대로 대응됩니다.
③ 시뮬레이터 실행 커맨드

VCS vs Xcelium — 런타임 옵션

목적Synopsys VCSCadence Xcelium

커버리지-cm line+cond+fsm+tgl-coverage all

두 툴 다 "테스트 이름 + 시드 + 커버리지 + 로그"를 인자로 준다는 구조는 동일합니다. 이름만 외우면 됩니다.
④ Tcl — 시뮬레이터를 조종하는 언어

Tcl은 EDA 툴의 공용 리모컨

Tcl은 시뮬레이터(UCLI/SimVision)뿐 아니라 합성(dc_shell)·STA(pt_shell)·PnR까지 거의 모든 EDA 툴의 제어 언어입니다. 하나 배우면 여러 툴에 씁니다.

  • 신호 강제·해제: force / release
  • 실행 제어: run, breakpoint
  • 파형 덤프 설정, 커버리지 리포트
# run.tcl (VCS UCLI 예시)
force tb.rst_n 0
run 100ns
force tb.rst_n 1
force -deposit tb.cnt 8'h00
run 10us
dump -file wave.fsdb -type FSDB
quit

→ simv -ucli -i run.tcl 로 실행. "리셋 걸고, 10us 돌리고, 파형 남기고 종료".

⑤ Python / Perl — 자동화의 접착제

회귀 러너 · 로그 파싱 · 리포트

수백 개 시드를 돌리고 결과를 모아 "무엇이 몇 개 실패했는지"를 표로 만드는 건 Python/Perl의 일입니다. (요즘은 Python이 대세, 레거시엔 Perl)

# run_regress.py — 테스트×시드 돌리고 fail 집계 (개념)
import subprocess, glob, re

tests = open("testlist.f").read().split()
fails = []
for t in tests:
    for seed in range(1, SEEDS+1):
        subprocess.run(["./simv", f"+UVM_TESTNAME={t}",
            f"+ntb_random_seed={seed}", "-l", f"log/{t}_{seed}.log"])
        log = open(f"log/{t}_{seed}.log").read()
        if re.search(r"UVM_(ERROR|FATAL)", log):
            fails.append((t, seed))          # 실패 시드 반드시 기록!

print(f"FAIL {len(fails)} / {len(tests)*SEEDS}")
핵심 실무 습관: 실패한 시드를 로깅해야 그 시드로 재현·디버그가 됩니다. "랜덤이라 재현 안 돼요"는 실격.

"밤새 회귀 → 아침에 fail 리스트 + 커버리지 리포트 확인 → 구멍 메우기" — 이 하루 루틴을 말할 수 있으면 실무자로 보입니다.

⑦ 파형 디버깅

Verdi / FSDB — fail을 눈으로 쫓기

테스트가 fail하면 파형을 봅니다. 신호 값이 시간축으로 어떻게 변했는지 추적해 원인 지점을 찾습니다.

  • FSDB: 파형 파일 포맷(빠름). $fsdbDumpvars로 덤프
  • Verdi(Synopsys): 대표 파형/디버그 툴. 신호 추적·드라이버 역추적
  • Xcelium은 SimVision/Indago

디버그 순서: 에러 로그의 시각(time) 확인 → 그 시각으로 파형 점프 → 관련 신호 추가 → 값이 틀어진 지점을 위로 역추적.

// TB에서 파형 덤프 켜기 (SV)
initial begin
  $fsdbDumpfile("wave.fsdb");
  $fsdbDumpvars(0, tb_top);  // 전 계층 덤프
end

주의: 전 신호를 덤프하면 파일이 거대해지고 느려집니다 — 필요한 계층만 덤프하는 게 실무 감각.

# tape-out/릴리스 스냅샷을 태그로 고정 (재현성)

면접 포인트: "특정 커밋/태그 = 특정 칩 RTL"이라는 재현성 개념. 회귀 결과를 커밋과 연결해 추적합니다.
면접 예상 질문

도구·실무 흐름으로 이렇게 답한다

회귀는 어떻게 돌리나요?
testlist에 테스트 목록을 두고, Makefile/Python 러너로 각 테스트를 여러 시드로 LSF grid에 병렬 제출합니다. 야간에 수백~수천 잡을 돌린 뒤 로그를 파싱해 pass/fail을 집계하고, 각 run의 커버리지 DB를 urg/imc로 merge해 통합 리포트를 봅니다. 실패한 시드는 반드시 로깅해 재현·디버그합니다.
시뮬레이션이 fail했습니다. 어떻게 디버깅하나요?
먼저 로그에서 UVM_ERROR/FATAL과 그 발생 시각을 찾고, FSDB 파형을 Verdi로 열어 그 시각으로 점프합니다. 관련 신호를 추가해 값이 틀어진 지점을 드라이버 역추적으로 위로 따라가며 원인(자극·체크·RTL)을 좁힙니다. 재현되면 그 시드로 반복해 수정합니다.
Tcl이나 Makefile은 어디에 쓰나요?
Makefile로 compile→elaboration→simulation 타깃을 만들어 make sim TEST= 한 줄로 돌립니다. Tcl은 시뮬레이터(UCLI)뿐 아니라 합성 dc_shell·STA pt_shell 등 EDA 툴 공용 제어 언어라, 리셋 강제·실행 제어·파형 덤프 스크립트에 씁니다.
핵심 요약

실무 도구 — 한 손에

  • Linux: grep/find/less/vim, 로그에서 fail 찾기
  • Makefile: comp/sim/regress 타깃 = 3단계 자동화
  • 시뮬: +UVM_TESTNAME +seed -cm/-coverage -l log
  • Tcl: 시뮬·합성·STA 공용 리모컨(force/run/dump)
  • Python/Perl: 회귀 러너·로그 파싱·리포트(실패 시드 로깅)
  • 회귀: LSF grid → merge(urg/imc) → 구멍 분석
  • 디버그: FSDB + Verdi 역추적 · Git/Perforce 재현성

"저는 리눅스에서 Makefile로 compile→sim→회귀를 돌리고, LSF로 병렬화해 커버리지를 merge하며, fail은 FSDB 파형을 Verdi로 역추적해 디버그합니다." — 이 한 문장이 '실무 준비됨'의 신호입니다.
