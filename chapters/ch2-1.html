왜 배우나 · 한 문장 정의

UVM = SystemVerilog로 만든 표준 검증 프레임워크

UVM(Universal Verification Methodology)은 검증 환경을 만드는 SystemVerilog 클래스 라이브러리이자 표준 방법론입니다. Accellera가 표준화했고, 사실상 디지털 검증의 공용어입니다.

😵 UVM 없이 (맨바닥)

  • 회사·사람마다 테스트벤치 구조가 제각각
  • 다른 프로젝트로 옮기면 재사용 불가
  • 자극 생성·드라이브·체크가 한 덩어리로 엉킴

😎 UVM 있으면

  • 누가 짜도 같은 계층 구조 → 바로 읽힘
  • 컴포넌트 단위로 재사용·확장·이식
  • 역할이 분리돼 유지보수·디버깅이 쉬움
즉 UVM은 새로운 언어가 아니라 SystemVerilog 위에 얹힌 약속입니다. 면접에선 "표준화된 재사용 가능한 검증 방법론"이라고 한 줄로 정의할 수 있어야 합니다.
개발자 직관으로 번역

왜 "프레임워크"라고 부르는가

웹 개발에서 Spring·Django를 쓰는 이유와 똑같습니다. 라우팅·DI·계층 구조를 매번 새로 만들지 않고, 정해진 골격에 비즈니스 로직만 채워넣죠. UVM도 검증 환경의 골격(컴포넌트 계층·실행 순서·통신 규약)을 제공하고, 당신은 "이 칩을 어떻게 두드릴까"라는 알맹이만 채웁니다.

한 장면으로 이해하기

UVM 테스트벤치 = 영화 제작 스튜디오

DUT(검증 대상 칩)는 "촬영장"이고, 모두가 한 편의 영화(테스트)를 찍습니다.

🎬 감독 = test

"어떤 영화를 찍을지" 결정. 환경을 세팅하고 시나리오를 고른다.

📜 시나리오 = sequence

장면들의 순서·내용. 자극(stimulus)의 흐름을 정의.

🎭 배우 = driver

대본을 받아 실제 연기(전기 신호)로 칩 핀을 흔든다.

📷 카메라 = monitor

촬영장에서 실제 벌어진 일(신호)을 관찰·기록.

🧐 평론가 = scoreboard

"각본대로 됐나?" 기대값과 실제값을 비교·채점.

📋 조감독 = sequencer

대본(sequence)을 배우(driver)에게 순서대로 전달·조율.

이 6명을 묶은 한 팀이 agent, 팀들을 모은 제작사가 env, 한 편의 영화 기획이 test입니다.

가장 헷갈리는 한 쌍

driver vs monitor — 방향이 정반대

📤 driver (능동)

트랜잭션 → 신호. sequence가 만든 추상적 item("쓰기 요청")을 받아 실제 핀을 토글해 DUT를 자극합니다.

방향: 테스트벤치 → DUT (입력 구동)

📥 monitor (수동)

신호 → 트랜잭션. 핀에서 실제로 벌어진 일을 관찰만 하고, 추상 트랜잭션으로 복원해 scoreboard로 흘려보냅니다. 구동하지 않습니다.

방향: DUT → 테스트벤치 (관찰)

정답을 가리는 곳

scoreboard — 합격/불합격을 판정한다

monitor가 보낸 "실제 DUT 출력"과, reference model(또는 예측 로직)이 만든 기대 출력을 비교합니다. 다르면 에러 — 이게 검증의 결론입니다.

  • 입력은 monitor로 받아 예측 모델에 통과 → 기대값
  • 출력도 monitor로 받음 → 실제값
  • 둘을 비교, 불일치 시 uvm_error 보고
  • self-checking 환경의 심장

scoreboard 덕분에 사람이 파형을 일일이 눈으로 안 봐도, 수천 개 랜덤 테스트가 스스로 합·불을 판정합니다.

실행 순서의 약속

UVM phases — 생명주기 훅

모든 컴포넌트가 같은 순서로 빌드되고 연결되고 실행되도록 정해둔 단계들입니다. 프레임워크의 라이프사이클 콜백(onCreate → onStart → onDestroy)과 똑같은 개념.

위 흐름도는 핵심 단계만 추렸습니다. 표준 common phase의 full 순서는 build → connect → end_of_elaboration → start_of_simulation → run → extract → check → report → final 9단계로, 여기선 start_of_simulation·extract·check·final을 생략했습니다.
build_phase
위에서 아래(top-down)로 컴포넌트 객체를 create()로 생성. 여기서 factory·config_db가 작동.
connect_phase
아래에서 위(bottom-up)로 TLM 포트를 서로 connect()로 연결.
run_phase
시간을 소모하는 task 기반 단계. sequence가 돌고 driver가 핀을 흔든다. build/connect 같은 function phase는 0시간에 실행되고, run 계열(task) phase에서만 시뮬레이션 시간이 흐른다.
report_phase
pass/fail, 에러 수, 커버리지 등을 정리해 보고.
왜 단계를 나눌까? "모두 다 만든 뒤(build) → 다 연결한 뒤(connect) → 그제서야 실행(run)" 순서를 강제하면, 절반만 만들어진 환경에서 신호가 도는 사고를 막습니다.
의존성 주입 (DI)

factory와 config_db — 코드를 안 고치고 바꿔치기

🏭 factory (override)

객체를 new로 직접 만들지 않고 factory에게 요청해 생성합니다. 그러면 test에서 한 줄로 "A 대신 B를 만들어라" 교체 가능.

// driver를 손상 버전으로 교체
set_type_override_by_type(
  base_driver::get_type(),
  error_driver::get_type());

🔌 config_db

상위에서 하위로 설정값·핸들을 주입하는 전역 사전(맵). interface 핸들, 모드 플래그 등을 깊은 계층까지 전달.

// top에서 driver로 interface 주입
uvm_config_db#(virtual my_if)::set(
  null, "*.drv", "vif", my_vif);

정확히 의존성 주입(DI)입니다. Spring의 @Bean 교체나 mock 주입처럼, factory override로 테스트마다 다른 구현체를 끼워넣어 에러 주입·재사용을 합니다. config_db는 환경설정 주입에 해당합니다.

컴포넌트 간 통신

TLM · analysis port — 느슨하게 연결하기

TLM(Transaction-Level Modeling)은 컴포넌트끼리 핀 신호가 아니라 트랜잭션 객체 단위로 대화하게 합니다. 서로의 내부를 모른 채 포트로만 연결돼, 갈아끼우기 쉽습니다.

구분의미
put/get port컴포넌트 간 1:1 블로킹 통신 (한 곳이 보내면 한 곳이 받음)
analysis port1:N 브로드캐스트. monitor가 하나 쏘면 scoreboard·coverage가 동시에 구독
seq_item pull portdriver↔sequencer 전용 양방향 1:1 pull (driver가 get_next_item()으로 item을 능동적으로 당겨옴)

analysis port는 Pub/Sub(이벤트 버스)입니다. monitor가 "트랜잭션 발생!"을 publish하면, 구독자(scoreboard, 커버리지 수집기)가 각자 받아 처리합니다.

면접 예상 질문

이렇게 물어보면, 이렇게 답한다

UVM을 왜 쓰나요?
SystemVerilog 기반의 표준화된 검증 방법론이기 때문입니다. 정해진 계층 구조와 실행 순서(phase), factory·config_db 같은 의존성 주입 메커니즘을 제공해, 테스트벤치를 매번 새로 짜지 않고 컴포넌트를 재사용·확장·이식할 수 있습니다. 또 업계 공용어라 협업과 IP 재사용에 유리합니다.
agent는 무엇으로 구성되나요? driver와 monitor의 차이는?
agent는 sequencer + driver + monitor를 묶은 단위입니다. driver는 sequence가 만든 트랜잭션을 받아 실제 핀 신호로 변환해 DUT를 구동하고(능동), monitor는 반대로 핀 신호를 관찰해 트랜잭션으로 복원하며 구동하지 않습니다(수동). active/passive 모드로 driver·sequencer를 켜고 끌 수 있습니다.
scoreboard 역할과 factory override의 장점은?
scoreboard는 reference model의 기대값과 monitor가 캡처한 실제값을 비교해 합·불을 자동 판정하는 self-checking의 핵심입니다. factory override는 코드를 수정하지 않고 test 레벨에서 특정 컴포넌트나 트랜잭션을 다른 구현체로 교체할 수 있게 해줍니다 — 에러 주입, 변형 시퀀스, 재사용에 강력합니다. 의존성 주입과 같은 개념입니다.
핵심 요약

이 챕터, 한 손에 잡기

  • UVM = SystemVerilog 클래스 라이브러리 + 표준 방법론
  • 계층: sequence → sequencer → driver → DUT → monitor → scoreboard
  • agent = sequencer+driver+monitor (active 기준; passive는 monitor만) / env가 묶고 / test가 지휘
  • phases로 build→connect→run 순서를 강제
  • factory/config_db = 의존성 주입, TLM/analysis port = 느슨한 통신

"UVM은 검증계의 Spring입니다. 표준 계층과 phase, 의존성 주입(factory·config_db)으로 재사용 가능한 self-checking 테스트벤치를 짭니다."
