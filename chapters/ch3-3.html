Part 3 · 버스와 시스템

Cache Coherency
여러 코어가 같은 값을 보게 만드는 법

캐시는 빠른 사본입니다. 그런데 코어마다 사본을 따로 들고 있다면? 누가 고친 걸 누가 못 본다면? 멀티코어의 가장 미묘한 약속, 캐시 일관성을 한 장의 지도로 펼칩니다.

← → 또는 Space 로 넘기기 · 화면 좌/우 끝 클릭도 가능
한 문장 정의

"모든 코어가 같은 주소에 대해 같은 최신 값을 보게 보장하는 것"

캐시(cache)는 느린 메인 메모리의 일부를 코어 곁에 둔 빠른 사본입니다. 사본이 코어마다 따로 존재하는 순간, "누가 고친 값을 다른 사본이 못 보는" 불일치(stale) 위험이 생깁니다.

⚡ 캐시가 있는 이유

메인 메모리(DRAM)는 코어 입장에서 수십~수백 사이클이나 느립니다. 자주 쓰는 데이터는 코어 옆 작은 고속 SRAM(=캐시)에 사본으로 둬서 가속합니다.

🧩 그래서 생기는 문제

코어가 4개면 같은 주소의 사본도 4개일 수 있습니다. 한 코어가 그 값을 고치면, 나머지 사본은 옛값(stale)이 됩니다. 이걸 자동으로 정리하는 게 coherency입니다.

검증 관점에서 왜 중요한가 → 멀티코어 SoC에서 coherency는 가장 버그가 잘 숨는 영역입니다. 타이밍·순서에 따라 어쩌다 한 번 틀리는(corner case) 버그라, 검증 엔지니어가 집중 공략하는 단골 주제입니다.
직관부터 잡기

공유 칠판 vs 각자 노트

모두가 함께 보는 공유 칠판(coherent): 누군가 한 글자 고치면 그 자리에 있는 모두가 즉시 최신으로 봅니다. 모두가 항상 같은 한 진실을 봅니다.

↔ 각자 자기 노트에 베껴 적고 따로 고침(incoherent): 내 노트만 고쳤으니 옆 사람은 옛 내용을 봅니다. 나중에 맞춰볼 때 서로 값이 달라 충돌·불일치가 터집니다. Cache coherency는 이 어긋남을 하드웨어가 자동으로 정리해 주는 것입니다.

문제의 그림

코어1이 쓰면, 코어2는 옛값을 본다

주소 X의 원래 값은 5. 두 코어가 각자 캐시에 5를 사본으로 들고 있습니다. 코어1이 X=10으로 바꾸면, 조정 장치가 없으면 코어2는 여전히 5를 읽습니다.

이게 그냥 "느려서"가 아니라 틀린 결과를 만든다는 게 핵심입니다. 여러 코어가 함께 쓰는 공유 데이터(예: 자원을 누가 차지했는지 표시하는 깃발 값)가 옛값이면 시스템이 통째로 오작동합니다.

해결의 원칙

"내가 고치기 전에 남의 사본을 정리한다"

coherency 프로토콜의 규칙은 의외로 단순합니다. 두 가지 불변식만 지키면 됩니다.

Write Propagation
한 코어의 쓰기는 결국 다른 코어들에게 전파되어야 한다 (남이 그 변화를 알게 됨)
Write Serialization
같은 주소에 대한 쓰기들은 모든 코어가 같은 순서로 본다 (순서가 뒤집히지 않음)

🗑️ 방법 A · Write-Invalidate

내가 쓰기 전에 "다른 사본 다 버려!(invalidate)" 신호를 보냄. 그 뒤부턴 나만 최신본을 가짐. 대부분의 실제 칩이 채택(MESI가 이 방식).

📢 방법 B · Write-Update

내가 쓴 새 값을 다른 사본들에게 바로 갱신해 뿌림. 트래픽이 많아 잘 안 씀.

Write-Invalidate의 발상은 한 문장입니다: "값이 바뀌었으니 너희가 들고 있는 사본은 버려라, 다음에 필요하면 새로 받아가라." 도서관에서 책 내용이 개정되면 옛 인쇄본을 폐기하고 새 판을 다시 빌려 보게 하는 것과 같습니다.

MESI 프로토콜 · 네 가지 상태

모든 캐시 라인은 4개 상태 중 하나

각 캐시 라인(블록)에 상태 비트를 붙여 추적합니다. M·E·S·I 네 글자가 곧 그 상태입니다.

기억법: M=나만+고침(dirty), E=나만+안고침(clean), S=같이 읽는중, I=버려진 사본. "나만 갖고 있나(M/E)" vs "같이 갖나(S)" vs "버렸나(I)"로 묶으면 외우기 쉽습니다.
MESI · 상태가 움직이는 순간

읽고·쓰고·남이 건드릴 때 어떻게 바뀌나

상황내 캐시 라인 변화왜
내가 처음 읽음 (남도 안 가짐)I → E나 혼자 깨끗하게 가짐
내가 읽음 (이미 남도 가짐)I → S같이 공유
내가 씀 (E 상태에서)E → M나만 가졌으니 조용히 고침
내가 씀 (S 상태에서)남 사본 invalidate 후 S → M고치기 전 남의 사본 정리
남이 그 주소를 씀내 라인 → I내 사본은 이제 옛값, 버림
남이 그 주소를 읽는데 내가 M이면M → S (최신값을 남에게 공급 + 메모리에도 write-back)남이 읽기 전 메모리에도 최신값을 다시 적어 둘 다 clean한 S가 됨. (dirty 채로 소유권을 넘기는 건 순수 MESI가 아니라 MOESI의 Owned 상태)

각 캐시 라인은 상태도(상태 다이어그램)를 따라 움직이는 작은 부품이라고 보면 됩니다. "내 코어의 읽기/쓰기"와 "버스에서 들려온 다른 코어의 읽기/쓰기"가 입력 신호이고, 그 신호에 따라 M·E·S·I 네 상태 사이를 정해진 규칙대로 옮겨 다닙니다. 신호등이 정해진 순서로만 색을 바꾸는 것과 같은 구조입니다.

누가 감시하나 · Snoop vs Directory

"남이 뭘 건드렸는지"를 알아내는 두 방식

상태를 바꾸려면 "다른 코어가 이 주소에 무슨 짓을 했는가"를 알아야 합니다. 이를 알아내는 방법이 두 가지입니다.

👂 Snooping (스누핑)

모든 캐시가 공유 버스를 엿듣습니다(snoop). 누가 어떤 주소를 읽고/쓰는지 방송되면, 각 캐시가 "어, 그거 나도 가진 주소인데?" 하고 스스로 상태를 바꿉니다.

  • 단순·빠름, 소수 코어에 적합
  • 코어가 많아지면 버스가 방송 트래픽으로 포화 → 확장성 한계

📒 Directory 기반

중앙 디렉터리(명부)가 "어떤 주소를 어떤 코어가 갖고 있나"를 기록. 쓰기가 생기면 해당 코어에게만 콕 집어 invalidate를 보냅니다.

  • 방송 대신 1:1 메시지 → 대규모 멀티코어에 확장성 좋음
  • 디렉터리 저장·조회 오버헤드가 있음

Snooping = 단톡방에 전체 공지를 뿌리는 것(작은 방엔 OK, 수천 명이면 도배). Directory = 주소록을 보고 관련된 사람에게만 DM 보내는 것.

실제 SoC에서 · AMBA의 coherent 확장

버스 프로토콜이 coherency를 책임진다

Part 3에서 본 AMBA(AXI 등)는 원래 coherency를 다루지 않았습니다. 멀티코어 시대에 ARM이 coherency를 버스 차원에서 처리하도록 확장한 프로토콜이 ACE와 CHI입니다.

프로토콜정체특징
AXI기본 고성능 버스 (non-coherent)읽기/쓰기 전송만, 캐시 일관성(스눕·캐시상태 추적) 기능 없음 — 전송 순서 규칙과 캐시 가능/버퍼 속성(AxCACHE)은 있지만 다른 캐시를 들여다보진 않음
ACEAXI Coherency ExtensionsAXI에 snoop 채널·캐시 상태 신호 추가 → 캐시 일관성 지원
CHICoherent Hub Interface중앙 허브 기반, 다수 코어 확장에 유리한 차세대 coherent 인터커넥트

"버스가 coherency를 지원한다"는 건, 사본을 정리하는 절차를 버스 규약(약속) 자체에 표준으로 못 박았다는 뜻입니다. 각 부품(IP)이 제각각 알아서 처리하는 대신, 프로토콜에 정해진 형식으로 "그 주소 가진 사람?" 하고 묻고 답하는 신호(snoop 요청·응답)를 주고받습니다.

검증 관점: ACE/CHI 검증은 "온갖 코어가 동시에 같은 주소를 read/write할 때 MESI 상태가 규약대로 전이하는가"를 두드리는 일. corner case가 폭발하는 고난도 영역입니다.

실무 함정 한 가지 · False Sharing

"서로 다른 변수인데도" 성능이 무너지는 이유

coherency는 캐시 라인 단위(보통 64바이트)로 동작합니다. 서로 무관한 두 변수가 우연히 같은 64바이트 라인에 들어가면, 한쪽만 고쳐도 라인 전체가 invalidate됩니다.

두 코어가 각자 자기 변수만 바쁘게 고쳐도, 같은 라인이라 서로 끊임없이 무효화시켜 캐시 핑퐁(ping-pong)이 발생합니다. 논리적으로는 맞지만 성능이 급락합니다.

false sharing을 피하는 방법은 의외로 직관적입니다. 두 코어가 자주 고치는 변수들 사이에 빈 공간(패딩)을 채워 넣어, 각 변수가 서로 다른 캐시 라인에 떨어지게 배치하면 됩니다. 한 책상에 둘이 붙어 앉아 팔이 부딪히던 것을, 책상을 따로 두어 해결하는 셈입니다.
면접 예상 질문

이렇게 물어보면, 이렇게 답한다

Cache coherency가 왜 필요한가요?
멀티코어에서 각 코어가 같은 메모리 주소를 자기 캐시에 사본으로 둘 수 있는데, 한 코어가 그 값을 고치면 다른 코어 사본은 옛값(stale)이 됩니다. coherency는 모든 코어가 같은 주소에 대해 일관된 최신 값을 보도록, 쓰기를 전파하고 쓰기 순서를 직렬화해 보장합니다.
MESI의 네 상태를 설명해 보세요.
Modified는 나만 갖고 내가 고쳐서 메모리보다 새 값(dirty), Exclusive는 나만 갖고 아직 안 고친 깨끗한 값, Shared는 여러 코어가 같이 가진 읽기 전용 값, Invalid는 무효라 다시 받아와야 하는 상태입니다. 남이 같은 주소를 쓰면 내 라인은 Invalid로 전이합니다.
snoop이 뭔가요? directory 방식과의 차이는?
snoop은 각 캐시가 공유 버스를 엿들으며 다른 코어의 read/write를 감지해 스스로 상태를 갱신하는 방식입니다. 단순하지만 방송 트래픽 때문에 코어가 많아지면 확장성이 떨어집니다. directory 방식은 중앙 명부가 어느 코어가 어떤 라인을 가졌는지 기록해 관련 코어에만 1:1로 무효화를 보내, 대규모 멀티코어에 더 잘 확장됩니다.
ACE/CHI가 뭔가요? false sharing은요?
ACE는 AXI Coherency Extensions로, AMBA AXI에 snoop 채널과 캐시 상태 신호를 더해 버스 차원에서 캐시 일관성을 지원합니다. CHI는 허브 기반의 차세대 coherent 인터커넥트로 다수 코어 확장에 유리합니다. false sharing은 서로 무관한 두 변수가 같은 캐시 라인에 들어가, 각자 다른 코어가 고쳐도 라인 전체가 무효화되며 캐시 핑퐁으로 성능이 급락하는 현상입니다.
핵심 요약

이 챕터, 한 손에 잡기

  • 캐시 = 느린 메모리의 빠른 사본 → 코어마다 사본이 따로면 stale 위험
  • coherency = 모든 코어가 같은 주소에 같은 최신값을 보게 보장 (write propagation + serialization)
  • MESI = 라인 상태 4개: Modified·Exclusive·Shared·Invalid, 정해진 규칙대로 전이
  • 감시 방식: snooping(버스 엿듣기, 소수코어) vs directory(명부, 대규모 확장)
  • AMBA의 coherent 확장 = ACE(AXI 확장) / CHI(허브 기반)
  • false sharing = 같은 라인에 낀 무관한 변수가 서로 무효화 → 성능 핑퐁

"멀티코어에서 각 코어의 캐시 사본이 어긋나지 않도록, MESI 상태와 snoop/directory로 일관성을 보장하는 게 cache coherency이고, SoC에선 ACE/CHI 같은 coherent 버스가 이를 책임집니다."

— 최신값 공유·옛 사본 버리기·정해진 규칙에 따른 상태 변화, 이 세 가지가 핵심입니다.
