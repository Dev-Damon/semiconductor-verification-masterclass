C-test vs UVM-test
칩을 두드리는 두 가지 손

바깥에서 로봇팔로 버튼을 누를 것인가, 직접 운전석에 앉아 시동을 걸 것인가. 같은 칩을 검증하는 두 세계의 결정적 차이를 한 장의 비교표로 정리합니다.

왜 배우나 · 한 문장 정의

같은 칩, 두 개의 검증 무대

검증에는 바깥에서 자극하는 방식(UVM-test)과 칩 안의 CPU가 직접 코드를 실행하는 방식(C-test)이 있습니다. 면접에서 "둘의 차이와 언제 무엇을 쓰는지"를 묻습니다.

🦾 UVM-test 외부 자극

테스트벤치(SystemVerilog/UVM)가 칩 바깥에서 버스 프로토콜로 신호를 넣고 결과를 검사. 개별 IP/블록·코너케이스·랜덤에 강함.

🚗 C-test 내부 실행

SoC 안의 진짜 CPU 코어가 베어메탈 C 코드를 실행하며 스스로 시스템을 자극. SoC 통합·부팅·실사용 시나리오에 강함.

핵심은 "자극을 누가 넣느냐"입니다. UVM은 외부 테스트벤치가, C-test는 내부 CPU가 넣습니다.
개발자 직관으로 번역

모킹된 통합테스트 vs 실제 런타임 E2E

UVM-test는 의존성을 모킹하고 외부에서 API를 호출해 검증하는 통합테스트와 같습니다. 대상 블록만 떼어내, 주변은 가짜 드라이버(BFM)로 대신하고 입력을 정밀하게 통제합니다.

C-test는 실제 서버를 띄우고 진짜 클라이언트로 돌리는 E2E 테스트와 같습니다. 시스템 전체를 진짜로 부팅시켜, 실제 CPU가 실제 펌웨어를 실행하게 둡니다.

물리적으로 비유하면 — UVM은 로봇팔로 차 바깥에서 버튼을 눌러보는 것이고, C-test는 사람이 운전석에 앉아 직접 시동 걸고 운전하는 것입니다. 후자가 더 "현실"에 가깝지만, 특정 버튼만 1만 번 눌러 한계를 시험하긴 어렵습니다.

펌웨어 = bare-metal 프로그램. OS 없이 하드웨어 위에서 곧바로 도는 C 코드. 부팅 직후 CPU가 가장 먼저 실행하는 그것입니다.
UVM-test · 바깥에서 두드리기

테스트벤치가 버스로 자극을 주입한다

대상(DUT)을 둘러싼 UVM 환경이 드라이버 → 인터페이스 → 버스 프로토콜 경로로 신호를 만들어 넣고, 모니터·스코어보드가 결과를 자동 비교합니다. CPU는 필요 없거나, 그냥 박스 취급합니다.

강점: 입력을 완전히 통제 → 제약 랜덤(constrained random)·코너케이스 폭격·기능 커버리지 측정이 쉽다. 약점: 실제 펌웨어가 도는 통합 시나리오를 흉내내긴 번거롭다.
C-test · 운전석에 앉기

진짜 CPU가 진짜 코드를 fetch & execute

C-test는 SoC에 박힌 실제 CPU RTL이 시뮬레이션 안에서 명령어를 하나씩 가져와(fetch) 실행(execute)하게 합니다. 자극의 출처가 외부 테스트벤치가 아니라 칩 내부의 프로그램입니다.

CPU가 스스로 구동

Cross-compile는 x86 PC에서 ARM/RISC-V 같은 타깃 아키텍처용 바이너리를 빌드하는 것. 임베디드 개발의 그 크로스컴파일과 똑같습니다.

Backdoor load = 부팅 과정(플래시 읽기 등)을 시뮬레이션으로 흉내내지 않고, 메모리 모델에 기계어를 곧바로 써넣어 빠르게 시작점에 도달시키는 기법.

Backdoor vs Frontdoor

왜 "뒷문"으로 메모리를 채우나

방식어떻게속도 / 현실성
Frontdoor load실제 버스 트랜잭션으로 한 워드씩 정상 경로로 기록 (실제 부트로더가 플래시에서 읽어오듯)느림 · 현실에 가장 가까움
Backdoor load시뮬레이터가 메모리 배열에 직접 값을 꽂음 ($readmemh 프리로드 등). 버스를 거치지 않는 이런 직접-주입을 통칭 backdoor라 부른다. 단 외부에서 계층 경로(dut.ram.mem)로 남의 메모리를 채우는 것은 시뮬레이터마다 허용도가 다르며, 엄밀한 UVM backdoor는 HDL path 기반 uvm_hdl_deposit/force(DPI 경유)로 동작한다.매우 빠름 · 부팅 단축
// 컴파일된 펌웨어 이미지를 메모리 모델에 backdoor로 주입
initial $readmemh("test.hex", dut.ram.mem);  // 버스 안 거치고 곧바로

// 그 다음 CPU 리셋만 풀면 → PC가 진입점부터 fetch 시작
cpu_rst_n = 1;  // 이제부터 진짜 코드가 돈다
실무에선 부팅 시퀀스 자체를 검증할 땐 frontdoor, 그 외 빠르게 본론으로 가고 싶을 땐 backdoor를 씁니다. 면접에선 "둘의 트레이드오프(속도 vs 현실성)"를 말하면 좋습니다.
DPI-C · Co-simulation

SystemVerilog ↔ C, 두 세계를 잇는 다리

DPI(Direct Programming Interface)는 SystemVerilog에서 C 함수를 직접 호출하거나 그 반대를 가능하게 하는 표준 인터페이스입니다. import "DPI-C"에서 끝의 -C는 약어의 일부가 아니라 "C 언어 연동(C linkage) 계층"을 가리키는 식별자입니다. 두 언어가 같은 시뮬레이션 안에서 함수처럼 서로를 부릅니다.

  • import: SV가 C 함수를 호출 (예: 복잡한 알고리즘·레퍼런스 모델을 C로)
  • export: C가 SV 함수를 호출
  • 이렇게 RTL 시뮬레이션과 C 모델이 함께 도는 걸 co-simulation이라 부릅니다
// SystemVerilog 쪽
import "DPI-C" function int ref_model(int a);

// → 시뮬레이션 중 C로 구현된
//   ref_model()을 곧바로 호출
expected = ref_model(stimulus);
/* C 쪽 (ref_model.c) */
int ref_model(int a){
  return golden_compute(a); // 정답 모델
}

개발자에겐 FFI(Foreign Function Interface)나 Python의 ctypes로 C 라이브러리를 부르는 것과 같은 그림입니다. "검증 환경(SV)이 C 코드와 함수 단위로 대화한다" — 이게 DPI-C입니다.

둘은 경쟁이 아니라 보완입니다. 블록은 UVM으로 촘촘히, 통합은 C-test로 실제처럼 — 두 손으로 같은 칩을 잡습니다.

면접 예상 질문

이렇게 물어보면, 이렇게 답한다

C 기반 테스트가 무엇이고, 언제 UVM 대신 쓰나요?
SoC 안의 실제 CPU 코어가 베어메탈 C 펌웨어를 실행하며 스스로 시스템을 자극하는 검증입니다. 부팅·블록 간 통합·실제 사용 시나리오처럼 "소프트웨어가 도는 흐름" 자체를 검증할 때, 외부에서 핀을 두드리는 UVM보다 적합합니다. 반대로 개별 IP의 코너케이스나 제약 랜덤·커버리지가 필요하면 UVM을 씁니다.
Backdoor load란 무엇인가요?
컴파일된 펌웨어 기계어 이미지(.hex/.bin)를 실제 버스 트랜잭션 없이 시뮬레이터가 메모리 모델에 직접 써넣는 기법입니다. 부팅 과정을 흉내내지 않고 곧장 실행 시작점에 도달하므로 시뮬레이션이 빠릅니다. 트레이드오프는 현실성으로, 부팅 시퀀스 자체를 검증할 땐 frontdoor를 씁니다.
DPI-C는 무엇이고 왜 쓰나요?
SystemVerilog와 C 함수를 직접 연결하는 표준 인터페이스입니다. SV에서 C 함수를 import해 호출하거나 그 반대로 export합니다. 정답(레퍼런스) 모델이나 복잡한 알고리즘을 C로 구현해 RTL 시뮬레이션과 함께 돌리는 co-simulation에 쓰며, 개발자의 FFI와 같은 개념입니다.
핵심 요약

이 챕터, 한 손에 잡기

  • UVM-test = 외부 테스트벤치가 버스로 자극 → IP/코너케이스/랜덤에 강함 (≈ 모킹 통합테스트)
  • C-test = 내부 실제 CPU가 베어메탈 C를 실행 → SoC 통합/부팅 시나리오에 강함 (≈ 실제 E2E)
  • C-test 흐름: cross-compile → backdoor load → CPU fetch&execute
  • Backdoor = 메모리에 직접 주입(빠름) ↔ frontdoor = 정상 경로(현실적)
  • DPI-C = SV↔C 함수 연결, C 모델과 함께 도는 게 co-simulation

"블록은 UVM으로 정밀하게, SoC 통합은 실제 CPU가 펌웨어를 돌리는 C-test로 검증합니다 — 모킹된 통합테스트와 실제 E2E를 함께 쓰는 것과 같습니다."

— 이 한 문장이면 두 환경의 차이를 다 담습니다.
