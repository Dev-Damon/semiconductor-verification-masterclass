한 문장 정의

검증 = "설계가 스펙대로 도는지 증명하는 일"

검증(Design Verification)이란, 아직 실물이 아닌 설계(RTL)를 컴퓨터 위에서 온갖 입력으로 두드려 스펙과 일치함을 보이는 활동입니다.

🎯 무엇을 증명하나

  • "이 입력에 이 출력이 나와야 한다" — 기능의 정확성
  • "어떤 입력에도 멈추거나 깨지지 않는다" — 견고함
  • "스펙의 모든 경우를 다 확인했다" — 빠짐없음

검증은 신약 임상시험과 같습니다. 약(설계)을 출시하기 전, 온갖 환자군(입력 케이스)에 투여해 부작용이 없는지, 효능이 스펙대로인지 두드려 봅니다.

"안 두드려 본 경우 = 임상 안 한 환자군" — 거기서 사고가 납니다.

개발자 직관으로 번역

당신은 이미 검증을 해봤습니다 — "테스트"라는 이름으로

당신의 세계 (SW 테스트)검증 엔지니어의 세계 (HW)
테스트 대상 함수·모듈 (SUT)DUT (Design Under Test)
테스트 코드 / test harness테스트벤치 (Testbench)
assert(result == expected)scoreboard / checker 비교
코드 커버리지 (line/branch)code coverage + functional coverage
퍼징 / property-based testconstrained-random 검증 (CRV)
invariant 단언 (불변식)assertion (SVA)

핵심 멘탈 모델: 검증은 새로운 외계 학문이 아니라, 당신이 짜던 단위·통합·E2E 테스트를 하드웨어에 옮긴 것입니다. 용어만 갈아끼우면 머릿속 지도의 90%는 이미 그려져 있습니다.

테스트벤치 구조

DUT를 둘러싸는 테스트 환경의 해부도

테스트벤치는 DUT를 감싸는 껍질입니다. 입력을 만들어 넣고, 출력을 지켜보고, 정답과 비교합니다. 흐름은 늘 같습니다.

흐름 한 줄: Stimulus가 입력을 만들어 → DUT에 넣고 → Monitor가 실제 출력을 뽑아 → Scoreboard가 Golden Model의 기대 출력과 비교해 PASS/FAIL을 판정합니다.
Golden / Reference Model

"정답"은 누가 알려주나 — 레퍼런스 모델

scoreboard가 "맞다/틀리다"를 판정하려면 기대 출력(정답)이 있어야 합니다. 그 정답을 만들어 주는 것이 골든/레퍼런스 모델입니다.

  • 대개 C/C++/SystemC/파이썬으로 짠 동작 모델
  • RTL과 독립적으로 스펙만 보고 구현 → 같은 버그를 공유하지 않음
  • 같은 입력을 DUT와 모델 양쪽에 넣고 출력을 비교

개발자 비유: 테스트에서 expected 값을 손으로 적는 대신, 검증된 다른 구현(또는 명세 그대로의 참조 구현)으로 정답을 계산해 비교하는 것과 같습니다. "두 개의 독립 구현이 같은 답을 내면 신뢰도가 올라간다"는 발상입니다.

주의: 골든 모델 자체에 버그가 있으면 정답이 틀립니다. 그래서 모델은 최대한 단순·명세 충실하게 짜고, RTL 설계자와 다른 사람이 작성하는 것이 이상적입니다.

커버리지 — "어디까지 검증했나"

코드 커버리지 vs 기능 커버리지

검증을 "언제 멈춰도 되는가"의 핵심 척도입니다. 두 종류를 반드시 구분해야 합니다.

구분Code CoverageFunctional Coverage
측정 대상RTL 코드의 어떤 줄·분기·상태가 실행됐나스펙상 의도한 시나리오·경우가 일어났나
생성 방식도구가 자동으로 계측 (line/branch/toggle/FSM)엔지니어가 직접 정의 (covergroup/coverpoint)
답하는 질문"코드를 빠짐없이 돌렸나?""의미 있는 경우를 다 봤나?"
SW 대응line/branch coverage요구사항 추적 매트릭스 / 시나리오 체크리스트

커버리지 = 체크리스트 소진율. 코드 커버리지는 "모든 방의 전등을 켜봤나", 기능 커버리지는 "비 오는 날·정전·동시 입력 같은 의미 있는 상황을 다 시험했나"입니다. 코드를 100% 실행해도, 두 입력이 동시에 들어오는 경우는 안 봤을 수 있습니다.

검증 완료 판단 & 자극 전략

언제 끝내나, 그리고 어떻게 두드리나

🧭 Directed Test

"이 입력 → 이 출력" 케이스를 사람이 하나하나 콕 집어 작성.

  • 특정 코너 케이스를 확실히 짚을 때 강력
  • 예상 못 한 버그는 못 잡음 · 수가 많아지면 손이 안 감
  • SW 비유: 손으로 짠 단위 테스트

🎲 Constrained-Random (CRV)

제약(constraint) 안에서 난수로 입력을 대량 생성해 두드림.

  • 사람이 상상 못 한 조합·코너를 우연히 발견
  • 어디까지 봤는지는 functional coverage로 측정
  • SW 비유: 퍼징(fuzzing) / property-based test

"검증 완료"의 판단 = 커버리지가 목표치에 도달 + 모든 테스트 PASS + 회귀(regression) 통과. 단순히 "버그가 안 나온다"가 아니라 "볼 것을 다 봤다는 증거"가 있어야 끝납니다.

Assertion · SVA

"이건 절대 일어나면 안 돼" — 불변식 단언

Assertion은 설계가 항상 지켜야 할 규칙(불변식)을 코드로 박아두고, 시뮬레이션 내내 자동 감시하는 장치입니다. SystemVerilog로 쓰면 SVA(SystemVerilog Assertions).

  • 규칙을 어기는 순간 그 자리에서 FAIL → 디버깅이 쉬움
  • 설계자가 RTL에 직접 박아 두기도 함 (white-box)
  • 포멀 검증의 "증명할 명제"로도 그대로 쓰임

완전히 당신이 아는 assert(invariant)입니다. 단, "이 시점"이 아니라 시간(클럭)에 걸친 규칙도 표현합니다: "req가 뜨면 반드시 2클럭 안에 ack가 떠야 한다" 처럼요.

// SVA 한 줄 맛보기: req 다음엔 반드시 ack가 온다
assert property (@(posedge clk)
    req |-> ##[1:2] ack);
// "req가 1이면, 1~2클럭 뒤 ack가 1이어야 한다. 아니면 FAIL"
검증 플랫폼 지형도

같은 칩을 검증하는 4가지 무대 — 트레이드오프

플랫폼한 줄 정의속도장점 / 약점
SimulationSW로 RTL을 한 클럭씩 흉내느림유연·디버깅 최고 / 대규모는 너무 느림
Emulation전용 하드웨어 박스에 설계를 매핑빠름대규모·OS 부팅 가능 / 장비 매우 비쌈
FPGA Prototyping실제 FPGA에 설계를 올려 구동매우 빠름실속도에 근접 / 디버깅 가시성 낮음·세팅 오래
Formal입력 안 넣고 수학으로 증명해당없음모든 경우 한 번에 증명 / 큰 블록엔 상태폭발

Simulation→Emulation→FPGA는 같은 검증을 점점 빠른 무대로 옮기는 것. 속도를 얻는 대신 "무대 안을 들여다보기(디버깅)"가 어려워지고 비용이 오릅니다.

Formal은 테스트를 "실행"하는 게 아니라 수학적으로 증명합니다. 가능한 모든 입력을 따로 안 넣어도 "이 규칙은 절대 안 깨진다"를 보장 — SW의 정적 분석·모델 체킹과 같은 결입니다.

트레이드오프 한눈에

속도를 얻으면 가시성을 잃는다

실무에선 한 가지만 쓰지 않습니다. 초기엔 Simulation으로 빠르게 디버깅하고, 규모가 커지면 Emulation/FPGA로 OS 부팅까지 돌리며, 핵심 안전 속성은 Formal로 못 박는 — 조합으로 갑니다.

테스트벤치의 구성요소를 설명해 보세요.
자극을 만드는 stimulus(driver), 검증 대상인 DUT, 출력을 뽑는 monitor, 그리고 골든/레퍼런스 모델의 기대값과 실제 출력을 비교해 PASS/FAIL을 판정하는 scoreboard로 구성됩니다. 입력 생성 → DUT → 출력 관찰 → 기대값 비교의 흐름이 핵심입니다.
코드 커버리지와 기능 커버리지의 차이는?
코드 커버리지는 도구가 자동 계측하며 RTL 코드의 줄·분기·상태가 실행됐는지를 봅니다. 기능 커버리지는 엔지니어가 covergroup으로 직접 정의하며, 스펙이 의도한 시나리오·경우가 실제로 발생했는지를 봅니다. 코드를 100% 실행해도 의미 있는 조합은 빠질 수 있어, 둘 다 봐야 합니다.
directed test와 constrained-random 검증의 차이, 그리고 시뮬레이션·에뮬레이션·포멀은?
directed는 사람이 케이스를 콕 집어 짜는 방식이고, CRV는 제약 안에서 난수 입력을 대량 생성해 예상 못 한 코너까지 두드린 뒤 functional coverage로 진척을 측정합니다. 플랫폼은, 시뮬레이션은 느리지만 유연·디버깅이 쉽고, 에뮬레이션/FPGA는 빠르고 대규모에 유리하나 비싸고 가시성이 낮으며, 포멀은 입력 없이 수학적으로 속성을 증명합니다.
핵심 요약

이 챕터, 한 손에 잡기

  • 검증 = 설계가 스펙대로 도는지 증명 (≈ 신약 임상시험)
  • 테스트벤치: stimulus → DUT → monitor → scoreboard, 정답은 골든 모델
  • 커버리지 = 체크리스트 소진율 · 코드(자동)와 기능(직접 정의)을 구분
  • directed(콕 집기) vs CRV(퍼징식 난수) · assertion=invariant 단언
  • 플랫폼: Simulation(유연·느림)·Emulation/FPGA(빠름·대규모·고비용)·Formal(수학 증명)

"저는 테스트벤치로 DUT를 두드리고, 커버리지로 완료를 증명하며, 케이스 성격에 따라 directed·CRV와 simulation·emulation·formal을 골라 쓰는 검증 엔지니어입니다."
